# フェーズ 18: 開発ループと再現

- 作成日: 2026-10-04
- 前提フェーズ: 16、17
- 完了条件: 常時記録（介入を含む）を `repro.export` で書き出して再生すると最後のフレームの状態ハッシュが一致し、同じ ROM で `rom.reload` + Re-Reach を行うと読み直す前と同じ状態ハッシュになる

## 1. 背景

Agent Interface の最優先の用途は、AI と共同で開発することである（設計書 14 編 §14.1）。AI は ROM を直し、ビルドし、読み直し、不具合の出た場面へ戻って確かめる。この往復を短くするのがこのフェーズの目的である。

フェーズ 9 で入力ムービー（SHGM）と決定論を整えてある。これを土台に、すべての Instance で入力と介入を常に記録し（§14.16）、ROM を作り直した後に同じ場面まで再生して戻る（Re-Reach、§14.15.3）。エージェントが見つけた現象は Repro（§14.16.3）として書き出し、人間が GUI で再現できるようにする。

フェーズ 15 で `mem.write`・`cpu.set`・`mem.freeze` を作ってあるが、それらは記録に残っていない。入力以外の介入を記録に含めないと、再生しても同じ状態にならない。

## 2. 方針とその理由

### 2.1 常時記録の形式を SHGM のバージョン 2 にする

新しい形式を作らず、既存の SHGM に介入のレコード（`recordPoke`・`recordSetRegister`・`recordFreeze`・`recordUnfreeze`・`recordOverlay`）を加える（設計書 08 編 §8.7.2、14 編 §14.16.2）。

理由: 再生器・desync 検出・GUI の「ムービーを再生」をそのまま使える。Repro を人間が開く経路が既存のムービー再生と同じになる。

### 2.2 介入のレコードにフレーム内の CPU サイクル数を持たせる

各介入のレコードに、フレームの開始から数えた CPU サイクル数（4 バイト）を付け、再生ではそのサイクル数以上の最初の命令境界で適用する。

理由: Agent-Paced では `exec.step_unit` でフレームの途中に止まって書き込むことがある。フレームの開始時に適用すると、記録時と結果が変わる。

### 2.3 Re-Reach は電源投入から始まる記録だけを対象にする

記録がセーブステートから始まっているときは Re-Reach を断り、`notes` に `re_reach_unavailable` を入れて電源投入の直後で止める（§14.15.3）。

理由: ROM が変わると ROM ハッシュが変わり、元のセーブステートを読めない。無理に読むと Machine State と ROM の内容が食い違い、誤った場面を見せる。

### 2.4 ROM の監視は時刻と大きさのポーリングで行う

500 ミリ秒ごとに更新時刻と大きさを調べ、変化が止まったことを 500 ミリ秒待って確かめてから扱う（§14.15.2）。fsnotify などを使わない。

理由: 依存を増やさず、3 OS で同じに動く。ビルドの途中の書きかけのファイルを読まない。

### 2.5 GUI 版の既定動作を通知にとどめる

`agent.romWatchAction` の既定値を `notify` とする。

理由: 人間が遊んでいる最中に、ビルドのたびに画面が切り替わるのを避ける。

### 2.6 常時記録はビューアの編集禁止の規則の対象にしない

既存のビューアは、ムービーの記録中に編集を断る（設計書 09 編 §9.4.5）。常時記録は利用者のムービー記録ではないので、この規則を適用しない。

理由: 常時記録は常に動いている。規則を適用すると、ビューアで一切編集できなくなる。

## 4. 完了判定

| 判定項目 | 確認方法 |
|---|---|
| 介入を含む再生 | `repro.export` した SHGM を再生し、最後のフレームの状態ハッシュが一致すること |
| Re-Reach（フレーム） | 同じ ROM で読み直して Re-Reach し、読み直す前と同じ状態ハッシュになること |

| ROM の監視 | ビルドで ROM を書き換えると、`rom_changed` が 1 回積まれること |
| GUI での Repro | GUI で `repro.shgm` を開き、最後のフレームで一時停止すること |
| 決定論 | 常時記録を有効にしても決定論テストのハッシュが変わらないこと |

## 6. つまずきやすい点

| 点 | 対処 |
|---|---|
| 再生すると状態ハッシュが合わない | 介入の記録漏れを疑う。ビューアからの編集とレジスタの編集が記録されているか確認する |
| フレーム途中の書き込みだけ結果が変わる | 介入をフレームの開始時に適用している。フレーム内サイクル数での適用を確認する |
| Re-Reach で違う場面に着く | ROM の変更で処理落ちのフレームが変わっている。`re_reach: condition` を使う |
| ビルド直後に読み直すと ROM の読み込みに失敗する | 書きかけのファイルを読んでいる。変化が止まるまで待つ処理を確認する |
| ビューアで編集できなくなった | 常時記録を編集禁止の規則の対象にしている。方針 2.6 を確認する |
| 古い `.dbg` の Symbol が表示される | ROM より古い `.dbg` を読んでいる。更新時刻の比較を確認する |
| バージョン 1 のムービーが読めない | フォーマットバージョンの分岐を確認する |

## 7. 記録

| 判断 | 内容 | 理由 |
|---|---|---|
| 常時記録の置き場所 | `internal/emu` のジャーナル | フレームの開始と介入がエミュレーションゴルーチンで起きる。agent に置くと、フレームの境界と介入の順序を取り出す口が増える |
| 境界で止まっている間の介入 | 次のフレームのサイクル数 0 の介入。書き出す時点で次のフレームが始まっていなければ「フレームの終わり」（`0xFFFFFFFF`） | Agent-Paced はフレームの開始の処理を最初の命令まで遅らせる。書き出しの直前の介入を失わないため |
| リセットの記録 | 利用者のムービー記録と常時記録の両方に記録する | 既存の記録はリセットを記録しておらず、再生で desync していた |
| レジスタの編集 | `Emulator.SetRegister` を通し、ムービーの記録中と再生中は断る | メモリの編集と同じ規則にそろえ、常時記録に残す |
| `rom.reload` の読み直し | 共有する Symbols の「読み込み済み」の印を外す | フェーズ 16 で読み込みを 1 回に限ったため |

| 計測 | 結果 |
|---|---|
| 1 時間（216000 フレーム）の記録の大きさ | 664 KiB |

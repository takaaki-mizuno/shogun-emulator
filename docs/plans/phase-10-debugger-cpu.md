# フェーズ 10: デバッガ（逆アセンブル・ブレークポイント・メモリ）

- 作成日: 2026-09-21
- 前提フェーズ: 9
- 完了条件: サイクル単位ステップ・条件付きブレークポイント・PPU 位置ブレークポイント・イベントブレークポイントが動作し、メモリビューアで書き換わった位置が色で示される

## 1. 背景

project.md が要求するデバッグ機能のうち、CPU 側（逆アセンブル、ブレークポイント、ステップ実行、メモリ 16 進ダンプ）を実装する。

逆アセンブラとトレース出力はフェーズ 1 で既に作ってある（nestest との比較に必要だった）。ここではそれを GUI へ載せ、ブレークポイントと実行制御を加える。

ブレークポイントは「実行中の状態を止めて調べる」ための機能であり、エミュレーション結果に影響を与えてはならない。フェーズ 9 で確定させた決定論を壊さないことを確認する。

## 2. 方針とその理由

### 2.1 デバッガは `Peek` と `Poke` のみを使う

`Bus.Read` と `Bus.Write` を呼ばない。

理由: メモリを表示するために `$2002` を読むと VBlank フラグがクリアされ、ゲームの動作が変わる。デバッガの観測がエミュレーション結果を変えてはならない。

### 2.2 ブレークポイントが 1 つも無いときフックを `nil` にする

`BreakpointSet` が種別ごとの有効件数を保持し、0 件の種別に対応するフックを設定しない。

理由: `OnCPURead` と `OnCPUWrite` は毎秒 180 万回呼ばれる。条件の評価を毎回行うと通常のプレイに影響する。

### 2.3 変更追跡を時間で減衰させる

書き込みフレーム番号を記録し、経過フレーム数から色の濃さを決める。

理由: 変更フラグ（bool）では 1 フレームだけ色が変わって人間の目に映らない。色を残したままでは画面全体が色付く。

### 2.4 逆アセンブルの命令境界を実行履歴から確定させる

実行されたアドレスを PRG-ROM のファイルオフセットで記録する。未実行の領域は線形逆アセンブルで推定し、推定であることを薄い色で示す。

理由: 6502 はコードとデータを区別できない。線形逆アセンブルだけでは、データの途中から命令を読み始めて以降がすべてずれる。バンク切り替えがあるため、CPU アドレスではなくファイルオフセットで記録する。

### 2.5 サイクル単位ステップを `Hooks.OnCycle` の中の停止要求で実現する

CPU サイクルの終わりに呼ばれる `Hooks.OnCycle` の中で停止要求を確認し、要求があれば `internal/emu` の側でチャネル待ちに入る。`internal/nes` は並行処理の仕組みを持たない。

理由: CPU を「自然なコード + tick コールバック」方式で実装している（設計書 03 編 §3.1）。ステートマシンではないため、サイクル単位の停止はこの方法で行う。この状態ではスナップショットを取れないので、フェーズ 9 で実装した「命令境界まで進めてから保存する」処理と組み合わせる。

## 6. つまずきやすい点

| 点 | 対処 |
|---|---|
| ビューアを開くとフレームレートが落ちる | フックが必要なときだけ設定されているか確認する。スナップショットのコピー量を確認する |
| メモリを表示するとゲームが壊れる | `Bus.Read` を呼んでいる。`Peek` に置き換える |
| サイクル単位ステップで保存できない | 命令境界まで進めてから保存する。この動作を UI に表示する |
| 逆アセンブルがずれる | データ領域から線形逆アセンブルしている。実行履歴による命令境界の確定を確認する |
| 変更追跡の色が見えない | `decayFrames` が小さすぎる。既定値 30 を確認する |
| ブレークポイントを設定すると決定論が崩れる | 条件式の評価で `Read` を呼んでいないか確認する |

# フェーズ 20: 解析（トレース・プロファイル・Diagnostic）

- 作成日: 2026-10-04
- 前提フェーズ: 16
- 完了条件: `trace.query`・`trace.summary`・`profile.report` が Symbol とソース行つきの結果を返し、Diagnostic の 11 項目がそれぞれのテスト ROM で検知され、全項目を有効にしても決定論テストのハッシュが変わらず 60 fps を維持する

## 1. 背景

一般的なエミュレータは「動かない」ことを再現するだけで、「なぜ動かないか」は人間が調べる。エージェントにトレースの全行を渡すことはできない（1 フレームで数万行）。このフェーズでは、エージェントが原因に近づくための材料を、絞り込んだ形と要約した形で渡す。

| 機能 | 答える問い |
|---|---|
| トレースの絞り込みと要約（設計書 14 編 §14.18） | このフレームで何が呼ばれ、どこに時間を使ったか |
| プロファイル（§14.19） | 処理は 1 フレームや VBlank に収まっているか。処理落ちはどこか |
| Diagnostic（§14.20） | ファミコン特有の誤りの疑いはどこにあるか |

フェーズ 16 で Symbol・ソース行・式を作ってあるので、結果を名前とソースの位置で返せる。

## 2. 方針とその理由

### 2.1 TraceRecord を大きくしない

フレーム番号を `TraceRecord` に持たせず、フレームの開始時の累積サイクル数の表を `Tracer` が持ち、サイクル数から引く（§14.18.1）。

理由: `TraceRecord` を 32 バイトに保つ。100 万命令で 32 MiB という見積もり（設計書 09 編 §9.7）を崩さない。

### 2.2 バスアクセスの絞り込みは要求されたときだけ記録する

`trace.enable` に `bus: true` を渡したときだけ、既存の `buslog.go` で別のリングバッファにバスアクセスを記録する。

理由: バスアクセスは毎秒 180 万回ある。常時記録すると実行が遅れる。

### 2.3 アイドルループの判定を 3 段階にし、使った方法を返す

引数 `idle` → Symbol の名前 → 自動判定の順に決め、`idle_detection` に使った方法を入れる（§14.19）。

理由: 自動判定は誤ることがある。判定の方法が見えれば、エージェントが誤判定に気付いて `idle` を指定し直せる。

### 2.4 Diagnostic のフックは有効な項目があるときだけ設定する

項目ごとに必要なフックを決め、どの項目も有効でないときは Diagnostic のためのフックを `nil` に保つ（§14.20.2）。

理由: `OnCPURead`・`OnCPUWrite` は毎秒 180 万回呼ばれる（設計書 09 編 §9.6 と同じ理由）。

### 2.5 warn.compat と判定を共有する

不安定な命令・色 `$0D`・未初期化 RAM の読み出しは、既存の `warn.compat` とブレークポイントの判定を関数として切り出し、Diagnostic とログの両方から使う。

理由: 同じ事象を 2 か所で別々に判定すると、片方だけ直したときに食い違う。

### 2.6 テスト ROM を自作し、ビルド済みのものをリポジトリに含める

各 Diagnostic を起こす小さな ROM を ca65 のソースで書き、ビルド済みの `.nes` と `.dbg` を `testdata/agent/` に置く（§14.24）。

理由: CI に cc65 を入れずに済む。既存のエミュレータやゲームのコードを使わないクリーンルームの規則を守る。開発環境に cc65 が無い場合は、ビルドするときだけ入れる。

## 6. つまずきやすい点

| 点 | 対処 |
|---|---|
| Diagnostic を有効にするとフレームレートが落ちる | 有効な項目に不要なフックまで設定していないか確認する。項目ごとのベンチマークで原因を特定する |
| Diagnostic を有効にすると決定論が崩れる | 判定で `Bus.Read` を呼んでいる。`Peek` に置き換える |
| `vram_access_during_render` が VBlank 中の正しいアクセスで出る | プリレンダーラインと VBlank の境界の判定を確認する。表示が無効のときは対象外 |
| `stack_overflow` がリセット直後に出る | 電源投入時の S の初期値（`$FD`）から始まる 3 回の空の積み込みを検知している。リセットシーケンスを対象から外す |
| `trace.summary` の関数の区切りがずれる | RTS による間接ジャンプを使うプログラム。推定である旨を `notes` に入れているか確認する |
| アイドルループの自動判定が誤る | `idle_detection` を見て、`idle` 引数か Symbol で指定する |
| トレースのフレーム番号が合わない | フレームの開始時のサイクル数の表が、リングバッファの範囲と揃っているか確認する |

## 7. 記録

| 判断 | 内容 | 理由 |
|---|---|---|
| 互換性の事象の共有 | CPU と PPU に `Compat`（事象の種類とアドレス）の知らせ口を加え、`Warn` と同じ判定の場所から呼ぶ。描画中の `$2006` の書き込みと起動直後の書き込みも PPU で判定する | 方針 2.5。判定を 1 か所に置き、ログの文字列を解析しない |
| ダミーリード | CPU に `DummyRead()` を加え、未初期化 RAM の判定（ブレークポイントと Diagnostic）はダミーリードを数えない | `LDA $10,X` の `$0010` や `PLA` の前のスタックの読み出しを誤検知した（テストで見つけた）。ブレークポイントの既存の誤検知も直る |
| セーブステートの読み込み後 | 内蔵 RAM をすべて書き込み済みとみなす | 書き込みの記録はセーブステートに無く、Fork・`state.load`・巻き戻しの後に誤検知する |
| 有効になる時点 | headless は作成の時点で既定の種類を有効、GUI 版は `diag.configure` まで無効 | 人間の遊びの速さを変えない |
| スタックの判定 | 命令の前後の S を比べる（積み込みで増えた・取り出しで減った）。次の命令の開始で判定するため、止めるときは次の命令を実行せずに止める | 書き込みのフックだけではスタックへの積み込みと STA $01xx を区別できない |
| `execute_data` のデータの位置 | `.dbg` のセグメントの名前（RODATA・DATA・CHARS・VECTORS）と利用者の `data` 指定 | ld65 の `.dbg` はセグメントがコードかを持たない |
| トレースの有効・無効 | GUI のトレース表示（`Features.Tracing`）と別に `AgentTrace` を持つ | GUI はデバッガの機能をまとめて差し替えるため、エージェントのトレースを消してしまう |
| バスアクセスの持ち主 | 開始のサイクル数がアクセスより小さい最後の命令 | バスはサイクルを終えてから数えるため、最後のサイクルのアクセスが次の命令の開始と同じ値になる（テストで見つけた） |
| プロファイルのフック | `OnInstructionStart` ではなく `OnBeforeExec` | `OnInstructionStart` は CPU の状態の写しを作り、毎命令では重い |
| 関数の集計 | trace.summary とプロファイルで `callAccum` を共有する。包含サイクル数は JSR の開始から RTS の終わり（+6） | 方針どおり判定を共有する |
| Fork | Diagnostic の指定・トレースの指定・測っているプロファイルの指定を写す。記録の内容は写さない | §14.3.2 |
| テスト ROM の対照 | `control` は RAM を消してから使い、NMI と JSR を持つ。トレースとプロファイルのテストにも使う | 1 本で 0 件と構造の確認を兼ねる |

| 計測（Apple M1 Max、dpcmletterbox、1 フレーム） | 結果 |
|---|---|
| なし | 4.23 ms |
| Diagnostic 既定 | 4.58 ms |
| Diagnostic 全項目 | 4.62 ms |
| トレース（bus: true） | 4.77 ms |
| プロファイル | 4.79 ms |
| 解析すべて | 5.12 ms（60 fps の 16.6 ms に収まる） |

| 残り | 内容 |
|---|---|
| 3 OS の CI | Git を使わない方針のため、macOS でだけ確認した |
| GUI での確認 | GUI 版で `diag.configure` を呼んだときの遊びの速さは目視していない（ベンチマークで代えた） |
| バンク切り替えのある ROM の trace.summary の名前 | 要約した時点のバンクで引く。トレースにバンクを持たせるには TraceRecord を大きくする必要があり、扱わない |

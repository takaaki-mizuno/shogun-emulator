# フェーズ 16: Symbol と Game State

- 作成日: 2026-10-04
- 前提フェーズ: 15
- 完了条件: テスト用 ca65 プロジェクト（`testdata/agent/`）の `.dbg` から、バンクを区別した Symbol とソース行を得られる。バージョン 1 のシンボルファイルがバージョン 2 へ移行される。§14.6 の位置の書き方と §14.11.4 の式の拡張が動作する。Game State Definition の全型と修飾が解釈され、Observation の `gamestate_changed` に差分が出る

## 1. 背景

エージェントは「$0300 の値」ではなく「自機の X 座標」で考える。開発中の ROM にはアセンブラが出力したデバッグ情報があり、変数の名前・サイズ・ソースの行がすべて分かる。これを読み込めば、エージェントはアドレスを覚えずに名前で読み書きでき、「この PC は `main.s` の 120 行目」とソースコードで話せる。

現在のシンボルファイル（`internal/debug/symbols.go`）はラベルを CPU アドレス（`uint16`）だけで持ち、バンクを区別しない。同じファイルのコードとデータの指定は PRG-ROM のオフセットで持っており、作りが揃っていない。MMC1 や MMC3 の ROM では、同じ CPU アドレスが複数のバンクを指すため、ラベルが誤った位置を示す。このフェーズで Symbol の位置を空間とオフセットの組に作り直す（設計書 14 編 §14.11.1）。

Game State（§14.12）は、Symbol だけでは分からない値の意味（型、BCD、列挙、ビットの名前）を利用者とエージェントが定義するものである。エージェントは解析しながら定義を足し、ファイルに残していく。

## 2. 方針とその理由

### 2.1 Symbol の位置を `SymbolLoc`（空間とオフセット）で持つ

`$0000`–`$7FFF` は `SpaceCPU`、`$8000`–`$FFFF` は `SpacePRGROM`（PRG-ROM のオフセット）、移行で位置の分からないものは `SpacePRGAny` とする。

理由: 同じ CPU アドレスが複数のバンクを指す ROM で、名前が誤った位置を示さないためである。逆アセンブラの実行済みアドレスの記録（設計書 09 編 §9.4.6）がすでに PRG-ROM のオフセットを使っており、それと揃う。

### 2.2 `.dbg` の PRG-ROM の位置は `ooffs` から求める

`sym` の CPU アドレス（`val`）ではなく、セグメントの出力ファイルでのオフセット（`ooffs`）から iNES ヘッダの 16 バイトを引いて求める（§14.11.2）。

理由: CPU アドレスからは、どのバンクの位置かが分からない。

### 2.3 `.dbg` から読んだ Symbol はファイルに保存しない

ROM を読み込むたびに `.dbg` から読み直す。利用者が付けた Symbol だけを `symbols/<rom-hash>.json` に保存する。

理由: ビルドのたびに `.dbg` の内容は変わる。保存すると古い位置が残り続ける。

### 2.4 ROM より古い `.dbg` は自動では読み込まない

ROM と同じディレクトリの `.dbg` の更新時刻が ROM より古ければ読み込まず、`notes` で知らせる。

理由: ビルドが途中で失敗したとき、古いデバッグ情報が新しい ROM の誤った位置を示すことを防ぐ。

### 2.5 式の解析を 1 つに統合する

既存の条件式（`internal/debug/condition.go`）を拡張し、ブレークポイントの条件・`exec.run_until`・Scenario のアサーション・位置の指定で同じ解析器を使う（§14.11.4）。

理由: 用途ごとに式の文法が違うと、エージェントが書いた式がある場所では通り、別の場所では通らない。

### 2.6 Game State Definition は ROM 名で探す

ROM と同じディレクトリの `<ROM 名>.gamestate.json` を、データディレクトリの `gamestate/<rom-hash>.json` より優先する（§14.12.1）。

理由: 開発中の ROM はビルドのたびにハッシュが変わる。ハッシュで探すと、ビルドするたびに定義を失う。ROM と並べて置けば、リポジトリに含めて共有できる。

### 2.7 テスト用の ROM はビルド済みのものをリポジトリに含める

`testdata/agent/` に自作の ca65 のソースと、ビルドした `.nes`・`.dbg` を置く。

理由: CI に cc65 を入れずに済ませる（設計書 14 編 §14.24）。開発する環境に cc65 が無い（2026-10-04 時点で `ca65` が見つからない）ため、ビルドの手順を残しておく。

## 6. つまずきやすい点

| 点 | 対処 |
|---|---|
| `.dbg` の Symbol の位置が 16 バイトずれる | `ooffs` は iNES ヘッダを含むファイルのオフセットである。16 を引いているか確認する |
| バンクの違う同じアドレスに同じ名前が出る | `val` から位置を求めている。`ooffs` から求める |
| 修飾名が作れない | `scope` の `parent` をたどっているか確認する |
| ソース行がマクロの定義の行を指す | `line` の `type` でマクロの行を後回しにしているか確認する |
| 既存のブレークポイントの条件式の結果が変わった | 64 bit への拡張で、8 bit の値の比較に符号拡張が混ざっていないか確認する |
| ビルドのたびに Game State の定義が消える | ROM ハッシュで探している。ROM 名で探す順を先にする |
| 古い `.dbg` で誤った位置を示す | 更新時刻の比較が効いているか確認する |
| 式の評価で `panic` する | 0 での除算、範囲外の空間の読み出しを確認する |

## 7. 計測と判断の記録

2026-10-05、macOS（Apple Silicon）。

| 計測 | 結果 | 補足 |
|---|---|---|
| 条件式 `game.mode == 'play' && [score].w >= 1000 && A == $42` の評価 | 1 回 約 141 ナノ秒（`BenchmarkConditionEval`） | 1 秒あたり 30 万回で約 42 ミリ秒。エミュレーションは実時間の約 9 倍の速さで進むため、`check: instruction` でも 60 fps を十分に保てる。Game State の位置の式は Symbol の版ごとに解析結果を覚え、評価のたびに解析し直さない |

| 判断 | 内容 | 理由 |
|---|---|---|
| 値の式での名前の意味 | RAM 側の名前は 1 バイトの値、ROM 側の名前（コードのラベル）は CPU アドレス、定数はその値 | `PC == update_mode` のようにコードのラベルはアドレスとして比べる。テストで `PC == update_mode` が成り立たないことから見直した。設計書 14 編 §14.11.4 を更新 |
| レジスタ・フラグと同じ綴りの名前 | レジスタ・フラグとして読む（Symbol は式で使えない） | 既存の条件式で `pc` などを小文字で書けた。設計書 14 編 §14.11.4 に記載 |
| 数値のリテラル | 32 bit まで受け付ける | 既存のテストの `$10000` を誤りとする項目を `$100000000` に変えた |
| `.dbg` と Game State Definition の読み込み | 共有する Symbols ごとに 1 回 | Fork や 2 つ目の Instance で読み直すと、実行中の定義が消える |

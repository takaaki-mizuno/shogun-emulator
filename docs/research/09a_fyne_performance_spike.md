# Fyne 性能・機能スパイクの実測結果

> 実施日: 2026-09-21 / 実行環境: macOS (darwin/arm64)、Go 1.25.3、Fyne v2.8.1、oto v3.5.1
> ディスプレイ: 1920×1080 @ 60.00 Hz（副ディスプレイに 75 Hz あり）
> `09_go_gui_frameworks.md` §8 で計画した 2 つのスパイクと、追加の UI 機能確認の結果。

## 1. 目的

Fyne を選定した際に唯一残った重大リスク「**256×240 を拡大して 60 fps で更新できるか**」を実測で決着させる。
加えて、デバッガ設計の前提（別ウィンドウ、ネイティブメニュー、セル単位の色付け）が実際に動くことを確認する。

## 2. 結論（先に書く）

| # | 検証項目 | 結果 | 判定 |
|---|---|---|---|
| 1 | Fyne で 256×240 を拡大して 60 fps 描画 | **実ペイント 60.00 fps（3x）、59.83 fps（6x = 1536×1440）** | **合格** |
| 2 | 拡大率を上げたときの性能劣化 | 2x〜6x で**有意な差なし**（GPU が拡大するのでコストは一定） | **合格** |
| 3 | oto で 48 kHz ステレオを低レイテンシ再生 | 20 ms / 50 ms バッファで**アンダーラン 0** | **合格** |
| 4 | 別ウィンドウを複数開く | 3 枚同時に開けた | **合格** |
| 5 | 同じビューアを 1 ウィンドウ内タブに畳む | `container.AppTabs` で可能 | **合格** |
| 6 | ネイティブメニューバー | `Window.SetMainMenu` で設定できた | **合格** |
| 7 | `widget.TextGrid` のセル単位の前景色/背景色 | `SetStyleRange` + `CustomTextGridStyle` で可能 | **合格** |

**→ Fyne の選定を維持する。** `09_go_gui_frameworks.md` §4.2 で挙げた既知の性能問題（issue #3052 等の「5〜10 fps」報告）は、**v2.8.1 では再現しなかった。**

そして、スパイクの副産物として**設計に直接影響する 3 つの事実**が判明した（§5）。これが本スパイクの最大の収穫である。

## 3. 描画性能の実測

### 3.1 測定方法とその落とし穴

最初の測定では 9,000 fps 以上という非現実的な値が出た。原因は:

> **`canvas.Image.Refresh()` は「再描画が必要」と印を付けて即座に返るだけで、実際の描画は行わない。** 実測で Refresh 単体のコストは p50 = 0.01 ms、p95 = 0.03 ms。

つまり「Refresh を呼んだ回数」は描画レートではない。**実際にペイントされた回数を数える必要がある。**

そこで `canvas.NewRaster(func(w, h int) image.Image)` を使い、**generate 関数が呼ばれた回数 = Fyne が実際にラスタライズした回数**として計測した。

### 3.2 結果: Refresh を全力で呼ぶ（`mode=max`）

Fyne のペイントループが出せる上限を測る。

| 拡大率 | 画面サイズ | Refresh 呼び出し | **実ペイント** | ペイント/Refresh |
|---|---|---|---|---|
| 3x | 768×720 | 9,321.71 /s | **60.00 /s** | 0.006 |
| 6x | 1536×1440 | 9,090.50 /s | **59.83 /s** | 0.007 |

**Fyne のペイントループは vsync にロックされており、ディスプレイの 60 Hz を正確に維持する。** 1536×1440 でも落ちない。

### 3.3 結果: 60.088 Hz の Ticker で Refresh（`mode=vsync`）

NES の実フレームレート（60.0988 Hz）に近い周期で Refresh する。

| 拡大率 | 画面サイズ | Refresh 呼び出し | 実ペイント | ペイント/Refresh | Refresh 間隔 p99 |
|---|---|---|---|---|---|
| 3x | 768×720 | 59.92 /s | 57.59 /s | 0.961 | 16.65 ms |
| 4x | 1024×960 | 59.91 /s | 56.42 /s | 0.942 | 16.70 ms |
| 6x | 1536×1440 | 59.91 /s | 57.91 /s | 0.967 | 16.64 ms |

**ここで 3〜6% のペイントが落ちているのは Fyne の性能問題ではない。** 自前の `time.Ticker`（60.088 Hz）とディスプレイの vsync（60.000 Hz）のビート（うなり）により、一部の Refresh が同じ vsync 区間に入って合流（coalesce）されるため。

`mode=max` が 60.00 fps を出していることから、**Fyne 側には余力しかない**ことが分かる。

### 3.4 ピクセル生成のベースライン

| 項目 | 実測 |
|---|---|
| 256×240 の全ピクセルを書き換えるコスト | **0.082〜0.083 ms/frame**（約 12,000 frames/sec） |
| 60 fps の予算 16.67 ms に対する比率 | **0.5%** |

**フレームバッファの生成コストは無視できる。** エミュレーション本体（CPU/PPU/APU）に 16 ms のほぼ全部を使える。

### 3.5 描画に関する設計上の帰結

1. **エミュレータのフレームペーシングを描画側に合わせてはいけない。** Fyne のペイントは vsync 固定 60 Hz、NES は 60.0988 Hz。**オーディオ駆動にする**という `07_timing_and_synchronization.md` §6.1 の判断が実測で裏付けられた
2. **Refresh は「vsync より少し多め」に呼んでよい。** コストが 0.01 ms なので、余分に呼んでも問題にならない。取りこぼしは Fyne が自然に合流させる
3. **拡大率を上げても劣化しない**ので、拡大率の上限をユーザーに開放してよい（6x = 1536×1440 まで確認済み）

## 4. オーディオの実測（oto v3.5.1）

### 4.1 測定方法

エミュレータを模した生成ゴルーチン（1/60 秒ごとに 800 サンプル生成 + CPU 負荷を模擬）→ リングバッファ → oto の `io.Reader`。
再生前にバッファをプライミングし、開始 500 ms 後にカウンタをリセットして**定常状態のみ**を 3 秒間測定。

### 4.2 結果

| 要求バッファ | 生成レート（理想 48000/s） | アンダーラン | oto 内部バッファ残 | リング充填 | 判定 |
|---|---|---|---|---|---|
| 20 ms | 47,830 /s | **0 サンプル** | 3,840 B = 20.0 ms | 73.3〜80.0 ms | 合格 |
| 35 ms | 48,217 /s | 80 サンプル（0.055%） | 9,024 B = 47.0 ms | 33.3〜83.3 ms | 軽微 |
| 50 ms | 47,992 /s | **0 サンプル** | 15,360 B = 80.0 ms | 50.0〜83.3 ms | 合格 |
| 100 ms | 48,256 /s | 800 サンプル（0.552%） | 21,504 B = 112.0 ms | 83.3〜133.3 ms | 軽微 |

- **20 ms という短いバッファでもアンダーランなしで動く。** レイテンシ要件には十分な余裕がある
- 要求したバッファサイズと oto 内部バッファ残がほぼ一致する（20 ms 要求 → 20.0 ms 実測）。**レイテンシが予測可能**

### 4.3 最重要の発見: 固定レート生成はドリフトする

生成レートの実測が **47,830〜48,256 /s** とばらついている（理想は 48,000 /s）。

原因: `time.Ticker(time.Second/60)` で「1 フレームごとに 800 サンプル」を生成しても、**OS のタイマ精度とオーディオデバイスの実クロックは一致しない。** 累積すると必ずバッファが枯れるか溢れる。

上の表で 35 ms と 100 ms にアンダーランが出たのは、この**ドリフトが吸収されなかった**ため（リング充填の min が下がっている）。

> 当初はこれを「充填率フィードバックで ±0.5% 補正すれば足りる」と判断したが、**§4.4 の追加実験でその判断は誤りだと分かった。** 「1 フレーム = 800 サンプル」と決め打つ実装は必ず音が途切れるという点は正しかったが、対策が不十分だった。

### 4.4 追加実験: ドリフトを実際に壊れるまで再現した（2026-09-21）

§4.3 の「ドリフトする」だけでは対策の妥当性が確認できないため、**60 秒間の耐久試験を 4 方式で実施した**（コード: `tools/spikes/audio-drift`）。
「音切れ回数」は**ユーザーに「プチッ」と聞こえる回数**（連続した無音区間を 1 回と数える）。

| 方式 | 生成レート | 音切れ | 満杯で破棄 | 充填の挙動 | 判定 |
|---|---|---|---|---|---|
| A: ティッカー駆動・無補正 | 47,879 /s | **137 回** | 0 | 目標 2400 に対し 716〜3195 で振動 | 不合格 |
| B: A + 充填率フィードバック（±0.5%） | 47,998 /s | **6 回** | 0 | 1057〜4433 で振動 | 不合格 |
| C: **バックプレッシャ（プル）モデル** | 48,039 /s | **0 回** | – | **平均 2400 / 最小 2400 / 最大 2400** | **合格** |
| D1: C + 重負荷・スラックなし | 48,039 /s | 1 回 | – | 最小 0 | 不合格 |
| **D2: C + 重負荷・高水位 = 目標×2** | 48,038 /s | **0 回** | – | 平均 4798 / 最小 2818 | **合格** |
| D3: C + 重負荷・高水位 = 目標×3 | 48,039 /s | 0 回 | – | 平均 7200 / 最小 6717 | 合格（余裕過剰） |

**重要な発見 1: ±0.5% のフィードバック補正だけでは直らない。**
A の不足は約 −0.25%〜−1.7% で変動し、しかも**振動**する。B は補正比が上下限（±0.5%）に張り付いて飽和し、追いつけない。

**重要な発見 2: 真の原因はオーディオクロックのドリフトではなく「ティッカー駆動」そのもの。**
`time.Ticker` の精度は測定すると十分だった（下表）。問題は**チャンネル容量が 1 なので、生成が重いとティックを取りこぼす**こと。取りこぼした分は永久に失われ、そのまま音切れになる。

| 要求 | 実測 | 誤差 |
|---|---|---|
| `time.Ticker` 60.0988 Hz | 60.0842 Hz | **−0.024%**（十分） |
| `time.Ticker` 60.0 Hz | 59.9858 Hz | −0.024%（十分） |
| `time.Ticker` 240.0 Hz | 221.5833 Hz | **−7.674%**（高頻度では破綻） |
| `time.Sleep` を 60.0988 Hz 相当でループ | 53.8221 Hz | **−10.444%**（論外） |

**重要な発見 3: バックプレッシャ（プル）モデルは完璧に動く。**

- オーディオデバイスの消費だけがクロック源。**壁時計のティッカーを一切使わない**
- エミュレータはリングバッファが高水位に達したら `sync.Cond` でブロックし、`Read` が消費したら起きる
- 結果: 60 秒間で充填が **2400 サンプルに完全固定**（最小 = 最大 = 2400）。生成レート誤差 +0.08%
- **CPU 負荷を 10 倍にしても崩れない**（D2）。エミュレータは「作れるだけ作ってブロックする」だけなので、負荷に対して本質的に頑健

**重要な発見 4: 高水位は「オーディオバッファの 2 倍」必要。**
高水位 = オーディオバッファと同じ（D1）だとスラックがゼロで、一瞬の処理落ちをそのまま音切れにする。**2 倍にすると重負荷でも音切れゼロ**（最小充填 2818 = 59 ms の余裕が残っていた）。3 倍は余裕過剰でレイテンシだけ増える。

### 4.4.1 この実験から確定した設計

| 項目 | 決定 | 理由 |
|---|---|---|
| クロック源 | **オーディオデバイスの消費（バックプレッシャ）** | ティッカー駆動は負荷でティックを落として音切れする |
| ティッカーの用途 | **エミュレーションのペーシングには使わない。** UI の再描画要求にのみ使う | 60 Hz なら精度は足りるが、駆動源にすると破綻する |
| オーディオバッファ | **25 ms** | 高水位 2 倍で合計レイテンシ 50 ms に収める（`09a` §4.2 で 20 ms でも動くことを確認済み） |
| リングの高水位 | **オーディオバッファの 2 倍**（= 50 ms 相当） | D1/D2/D3 の比較より。1 倍は不合格、3 倍は余裕過剰 |
| リングの容量 | 高水位の 2 倍 | 書き込み側がブロックする前に余地を持たせる |
| ±0.5% 動的リサンプル | **不要になった**（バックプレッシャが同じ役割を果たす） | ただし「NES 正確な速度」に固定したい場合には必要（下記） |

**副作用として受け入れること**: バックプレッシャモデルではエミュレータの速度が**オーディオデバイスの実クロックに従う**。実測では 60.132 fps（NES の 60.0988 Hz に対し **+0.055%**）だった。
これは 1 時間で約 2 秒のずれに相当するが、音のピッチ変化は 0.95 セント（検知限の 1/10 以下）で、ゲームプレイ上も知覚できない。
**「NES と厳密に同じ速度で動かす」ことを優先したい場合のみ**、±0.5% の動的リサンプルを併用してデバイスクロックとの差を吸収する。デフォルトはオーディオ同期（音質優先）とし、設定で切り替えられるようにする。

### 4.5 オーディオに関する設計上の帰結

1. **`oto.NewContext` はプロセスで 1 回だけ呼べる。** 2 回目は `oto: context is already created` エラー。**アプリ起動時に 1 個だけ作り、サンプリングレートやバッファサイズの変更は `Player` の作り直しで行う**（`Context` は作り直せない）。設定 GUI でサンプリングレートを変えたら再起動を求める、または `Player.SetBufferSize` で対応できる範囲に限定する
2. **オーディオバッファ 25 ms + リング高水位 2 倍（合計レイテンシ約 50 ms）** にする（§4.4.1）。設定で調整できるようにするが、**高水位は常にバッファの 2 倍以上を保つ**
3. **プライミング必須**: 再生開始前にリングを高水位まで埋める。埋めないと起動時にバッファ 1 杯ぶんの無音が入る（実測で 50〜100 ms）
4. **エミュレーションのペーシングはバックプレッシャで行う。ティッカー駆動にしてはいけない**（§4.4）。±0.5% の動的リサンプルは「NES 厳密速度」モードのときだけ併用する

## 5. 設計に影響する重大な発見

### 5.1 Fyne v2.8 のスレッドモデル（最重要）

初回の測定で次の警告が大量に出た。

```
*** This application has not been migrated to the fyne.Do threading model ***
*** The next major Fyne release will remove this safety! ***
*** Read more at https://docs.fyne.io/started/goroutines ***
*** Error in Fyne call thread, this should have been called in fyne.Do[AndWait] ***
*** This error needs to be addressed as it could cause concurrent errors soon ***
```

**Fyne v2.8 では、メインゴルーチン以外から UI を操作する場合、`fyne.Do(func())` または `fyne.DoAndWait(func())` 経由で行わなければならない。** 現在は警告だが、**次のメジャーリリースでこの安全網が外される**（= 未対応のコードは壊れる）。

本プロジェクトは「エミュレータを独自のゴルーチンで回す」設計なので、**これは全 UI 更新箇所に影響する。**

設計への織り込み:

```go
// internal/ui に UI スレッドへのディスパッチを 1 箇所に集約する
// エミュレータ側は「UI を触る」という概念を持たない。
// 必ずこのヘルパを経由させ、生の Refresh をエミュレータ側から呼ばせない。
func postToUI(fn func())      { fyne.Do(fn) }         // 非同期
func postToUIAndWait(fn func()) { fyne.DoAndWait(fn) }  // 同期（測定・スクリーンショット用）
```

- `fyne.Do` は**非同期**（キューに積んで返る）。毎フレームの画面更新はこちら
- `fyne.DoAndWait` は**同期**（UI スレッドでの実行完了を待つ）。スクリーンショット取得や、状態の一貫性が必要な場面のみ
- **`fyne.DoAndWait` を毎フレーム使うとエミュレーションが UI に同期して遅くなる。** 実測では `DoAndWait` でも 9,000 回/秒こなせたので致命的ではないが、原則 `fyne.Do` を使う

### 5.2 `Refresh()` は非同期である

`Refresh()` はダーティフラグを立てるだけ（0.01 ms）。**「Refresh を呼んだから画面に出た」とは限らない。**

- スクリーンショット機能（`12_config_and_packaging.md` の `--screenshot`）は、Refresh 後に画面から読むのではなく、**自分のフレームバッファから直接 PNG を書く**べき。そのほうが正確で速い
- テスト自動化（`08_test_roms_and_validation.md` §6.2 のフレームハッシュ比較）も同様に**フレームバッファのハッシュを取る**。画面キャプチャに依存しない

### 5.3 バイナリサイズとビルド時間

| 項目 | 実測 |
|---|---|
| Fyne を含むバイナリ | **29.6〜29.8 MB** |
| `-ldflags="-s -w"` でストリップ後 | **21.6 MB** |
| oto のみのバイナリ | 2.8 MB |
| 依存モジュール数（Fyne + oto） | **65 モジュール** |
| 初回ビルド時間（Fyne、cgo あり） | **約 26 秒**（クリーンビルド） |

- 21.6 MB は「シングルバイナリ」として許容範囲（Electron アプリが 100 MB 超なのと比べれば十分小さい）
- リリースビルドでは `-s -w` を付ける
- ビルド時にリンカ警告 `ld: warning: ignoring duplicate libraries: '-lobjc'` が出るが無害（Fyne の既知の挙動）

## 6. 再現手順

スパイクのコードは **`tools/spikes/` にリポジトリへ残した**（後から環境を変えて再測定できるようにするため）。
エミュレータ本体とは別モジュールにしてあるので、本体の依存関係には影響しない。

```bash
cd tools/spikes

# 描画性能（実ペイント回数を計測）
go run ./fyne-render 3 max 6     # 拡大率 3x、全力 Refresh、6 秒
go run ./fyne-render 6 vsync 6   # 拡大率 6x、60.088Hz Ticker、6 秒

# オーディオ（20/35/50/100 ms バッファでアンダーランを計測）
go run ./oto-latency

# UI 機能（別ウィンドウ、AppTabs、メニュー、TextGrid のセル色）
go run ./fyne-ui
```

詳細は `tools/spikes/README.md`。

# セーブステートと入力ムービーの設計調査

> 調査日: 2026-09-21 / 人間の判断により**第 1 弾に含めることが決定**（2026-09-21）
> 本書は既存エミュレータの実装を参照せず、`01`〜`13` の調査結果から導出した設計である。

## 1. 背景・目的

`13_future_topics.md` §8 で「第 1 弾に含めることを検討する価値がある」とした 2 機能を、**第 1 弾に含めることが決定した**。

含める理由:

1. **どちらも後付けするとエミュレータの全コンポーネントに手を入れることになる。** セーブステートは「全状態を直列化できること」、ムービーは「実行が決定論的であること」を要求し、どちらも設計の前提に踏み込む
2. **入力ムービーはテスト自動化の基盤である**（`08_test_roms_and_validation.md` §6.1）。これがないとテスト ROM の自動実行とリグレッション検出ができない
3. **セーブステートはデバッグに直結する。** 「バグの直前の状態を保存して何度でも再現する」ことができないと、タイミングバグの調査は現実的でない
4. **巻き戻し（rewind）が両者の組み合わせで自然に実現できる**（§8）

**そして最も重要な理由**: セーブステートは **CPU の実装方式を縛る**（§3）。これを後から知ると CPU を書き直すことになる。

## 2. セーブステートの要件

| ID | 要件 |
|---|---|
| S1 | ある瞬間のエミュレータの全状態を保存し、完全に同じ状態に復元できる |
| S2 | 復元後の実行が、保存しなかった場合とビット単位で一致する（= **状態の取りこぼしがない**） |
| S3 | 複数スロット（例: 10 個）+ クイックセーブ/ロード |
| S4 | ROM が違う / マッパーが違う状態のロードを安全に拒否する |
| S5 | デバッグ用途に耐える（ブレークポイントで止めた状態を保存・復元できる） |
| S6 | 巻き戻し（§8）のために高速・省メモリであること |

## 3. 最重要の制約: どこでスナップショットを取れるか → CPU 実装方式が決まる

`07_timing_and_synchronization.md` §7.1 で lock-step（1 CPU サイクル = 1 バスアクセス）を選んだ。この CPU をどう書くかで、スナップショットできる粒度が変わる。

### 3.1 2 つの実装方式

| 方式 | 書き方 | スナップショット可能な粒度 | 実装コスト |
|---|---|---|---|
| **(A) 明示的ステートマシン** | 1 サイクル = ステートマシンの 1 ステップ。**全状態がフィールド**（マイクロコード表 + サイクル内位置） | **任意のサイクル** | 大。コード量が 2〜3 倍、可読性が落ちる |
| **(B) 自然なコード + tick コールバック** | `02_cpu_6502.md` §8 の表をそのままコードにする。`read()`/`write()` の中で `tick()` を呼ぶ | **命令境界のみ**（サイクル途中の状態はホストのコールスタックにある） | 小。Wiki の記述と 1 対 1 対応するので検証しやすい |

**(B) を採用する。** 理由:

1. **`02_cpu_6502.md` §8 の tick 単位の表をそのままコードにできる。** Wiki の記述との対応が 1 対 1 で、`nestest.log` との突き合わせで誤りを特定しやすい。正確さを最優先する本プロジェクトでは、「仕様書と見比べられること」が実装コストより重要
2. ユーザー向けセーブステートは**フレーム境界で取れれば十分**。命令境界はそれより細かい
3. (A) の唯一の利点である「任意サイクルでの保存」が必要な場面は、デバッグ中の「サイクル単位ステップ実行の途中で保存」だけであり、§3.3 の規則で回避できる

### 3.2 スナップショット点の定義

> **スナップショット点 = 命令境界。厳密には「次の命令の opcode フェッチの直前」。**

この点を選ぶと次が保証される。

- CPU の状態は全部フィールドにある（A/X/Y/PC/S/P と各種 pending フラグ）
- **DMA は開始前である。** OAM DMA（513 サイクル）と DMC DMA（3〜4 サイクル）はどちらも「命令の最初のリードサイクル」で CPU を停止させる（`07` §3.3, §3.4）。命令境界の時点では「要求は立っているが未開始」の状態なので、`dmaPending` フラグとして表現できる
- 割り込みは pending フラグとして保持されている（`02` §11.3）
- PPU / APU / マッパーの状態はすべてフィールド（これらは元から明示的ステートマシンとして書く）

### 3.3 サイクル単位ステップ実行との両立

`11_debugger_features.md` §5.3 で「Step Cycle（1 CPU サイクル）」を提供すると決めた。方式 (B) でこれを実現するには、`tick()` の中でデバッガの停止要求を見てブロックする（エミュレータは専用ゴルーチンで動くので、チャネル待ちでよい）。

**ただしこの状態ではスナップショットが取れない**（ホストのコールスタックに状態がある）。

> **規則: セーブステート要求は命令境界まで実行してから処理する。** サイクル単位ステップの途中で保存を要求された場合、現在の命令を完了させてから保存し、**UI に「命令境界（$XXXX）まで進めてから保存しました」と明示する。**

これは「黙って少しずれた状態を保存する」ことを避けるための設計である。ユーザーを騙さないことのほうが、数サイクルの精度より重要。

### 3.4 コマンドキュー

上記の帰結として、**エミュレータゴルーチンは命令境界でのみ外部コマンドを処理する。**

```go
// 概念スケッチ
type Command interface{ isCommand() }

type CmdSaveState struct{ Slot int; Done chan error }
type CmdLoadState struct{ Slot int; Done chan error }
type CmdStep       struct{ Kind StepKind }   // Cycle / Instruction / Over / Out / Scanline / Frame
type CmdSetSpeed   struct{ Factor float64 }
type CmdReset      struct{ Hard bool }

// エミュレータのメインループ
for {
    // ① 命令境界: ここだけでコマンドを処理する
    e.drainCommands()
    // ② 1 命令実行（内部で tick() が PPU 3 ドット + APU 1 サイクルを進め、
    //    オーディオリングが高水位ならブロックする = バックプレッシャ）
    e.cpu.StepInstruction()
}
```

この構造には副次的な利点がある。「実行中にステートをロードする」「実行中に速度を変える」が**ロックなしで安全に書ける**。

## 5. 直列化の形式

### 5.1 形式の選択

| 候補 | 評価 |
|---|---|
| `encoding/gob` | 楽だが、型を変えると古いステートが読めなくなる。リフレクションが遅い。**不採用** |
| JSON | 巨大で遅い。**不採用** |
| **明示的なバイナリ（採用）** | 各コンポーネントが自分の状態を明示的に書き出す。速く、フィールドの追加に対して制御できる |

各コンポーネントが次のインタフェースを実装する。

```go
type Snapshotter interface {
    // 自分の状態をライタに書く。フォーマットバージョンは呼び出し側が管理する
    SaveState(w *StateWriter)
    LoadState(r *StateReader) error
}
```

`StateWriter` / `StateReader` はセクション単位のタグ付きバイナリにする。**未知のセクションはスキップできる**ようにしておくと、バージョン違いでの部分的な互換が取れる。

### 5.2 ファイルヘッダ

| フィールド | 用途 |
|---|---|
| マジック `"SHGS"` + フォーマットバージョン | |
| エミュレータのバージョンとコミットハッシュ | 不一致時に警告する（`12` §4.7） |
| **ROM ハッシュ**（ヘッダを除いた PRG+CHR の SHA-1） | S4。`12` §2.3 と同じ方式 |
| マッパー番号 + サブマッパー、リージョン | S4 |
| 決定論シード（RAM 初期化シード、CPU/PPU アライメント、DMA 位相） | §6.2 |
| 保存時の累積 CPU サイクル数とフレーム数 | 表示用 |
| スクリーンショット（任意、PNG） | セーブスロット一覧のサムネイル |

### 5.3 サイズと圧縮

状態量の見積もり:

| 項目 | サイズ |
|---|---|
| 内蔵 RAM | 2 KiB |
| CIRAM | 2〜4 KiB |
| OAM + secondary OAM + パレット | 約 0.3 KiB |
| PRG-RAM（あれば） | 8〜32 KiB |
| CHR-RAM（あれば） | 8 KiB |
| CPU/PPU/APU/マッパーのレジスタ類 | 約 1 KiB |
| **合計** | **約 13〜47 KiB** |

- 単体のセーブステートは**非圧縮**でよい（数十 KiB なので圧縮の利益が小さく、複雑さだけ増える）
- **巻き戻し用のリングバッファだけ圧縮する**（§8）。標準ライブラリの `compress/flate` で十分

### 5.4 デバッガの編集内容（オーバーレイ）を含めるか

`11_debugger_features.md` §6 の CHR/PRG オーバーレイは「ROM を書き換えずに編集を実現する層」である。

**決定: セーブステートには含めない。オーバーレイは別ファイル（`patches/<rom-hash>.json`）として独立に管理する。**

理由: オーバーレイは「ROM の一部」に近い性質で、セーブステートより寿命が長い。セーブステートに含めると「ステートをロードしたら編集内容が巻き戻った」という直感に反する挙動になる。ただし**ロード時にオーバーレイのハッシュを検証し、保存時と違っていれば警告する**（違う ROM 内容で復元すると挙動が変わるため）。

### 5.5 バージョン互換性の方針

| 対象 | 方針 |
|---|---|
| セーブステート | **エミュレータのバージョン間での互換を保証しない。** 精度向上のたびに状態が増えるため。バージョン不一致はエラーにし、理由を明示する |
| バッテリーバックアップ SRAM（`.sav`） | **常に互換。** 単なるバイト列なので |
| 入力ムービー | **互換を目指すが保証しない**（§7.5） |

「保証しない」と明言することが重要。中途半端に読めてしまって挙動が変わるのが最悪。

## 6. 決定論（determinism）の要件

入力ムービーと巻き戻しは、**同じ初期状態 + 同じ入力 → 同じ結果**が成り立たないと成立しない。

### 6.1 決定論を壊す可能性のある要因（ホスト側）

| 要因 | 対策 |
|---|---|
| **Go の map のイテレーション順** | **エミュレーションのロジックで map をイテレートしない。** `11` §6 のオーバーレイは `map` だが読み出しのみなので問題ない。直列化するときは**キーをソートする** |
| ゴルーチンのスケジューリング | **エミュレーション状態は単一ゴルーチンだけが触る。** 並列化しない |
| 壁時計（`time.Now`） | **エミュレーションロジックから一切参照しない。** 速度制御はバックプレッシャ（`09a` §4.4）で行うので、そもそも不要 |
| `math/rand` のグローバル状態 | **シード付きの専用 PRNG を使い、シードをステート/ムービーに記録する** |
| 浮動小数点 | 四則演算は IEEE-754 で決定論的だが、`math.Sin` 等は実装依存の可能性がある。**APU ミキサーの出力はエミュレーション状態にフィードバックしない**ので影響しない。ただし「浮動小数点の値で分岐してエミュレーション状態を変える」ことは禁止する |
| PAL の 3.2 ドット/サイクル | **浮動小数点の累積ではなく有理数（分子/分母の整数カウンタ）で実装する**（`07` §7.1）。誤差累積がなく、決定論も明確 |
| ホストの CPU 速度・負荷 | バックプレッシャにより実時間あたりの進みは変わるが、**エミュレート時間あたりの結果は不変**。ムービーは実時間ではなくエミュレート時間で索引する（§7.2） |

### 6.2 決定論を壊す要因（エミュレートされる側の「不定値」）

調査で洗い出した「実機では不定」な状態。**すべてを明示的に決定し、記録する。**

| 不定な状態 | 出典 | 扱い |
|---|---|---|
| 内蔵 RAM / PRG-RAM の初期値 | `02` §10 | 設定で `$00` / `$FF` / パターン / **シード付きランダム**。シードをステートとムービーに記録 |
| OAM の初期値 | `03` §11 | 同上 |
| パレット RAM の初期値 | `03` §11 | 同上 |
| CIRAM / CHR-RAM の初期値 | `03` §11 | 同上 |
| PPUSTATUS の VBlank フラグ（電源投入時ランダム） | `03` §11 | 設定 + 記録 |
| **CPU/PPU アライメント**（3 通り） | `03` §11 / `07` §3.1 | 設定 + 記録。デフォルトは「特殊ケースが最も少ない」値（`03` §11） |
| **DMA の get/put 初期位相**（2 通り） | `07` §3.1 | 設定 + 記録 |
| APU Noise LFSR の初期値 | `04` §6（Wiki 内に $0000 と $0001 の 2 つの記述あり） | **$0001 を採用**し、テスト ROM で検証（`04` §10） |
| APU フレームカウンタ LFSR | `04` §6 | $7FFF |
| APU DMC LFSR | `04` §6 | 0 |
| Triangle の位相 | `04` §6 | 0 |
| マッパーの CHR/PRG バンク初期値 | `03` §11 / `05` §5.6 | マッパーごとに決定し文書化。MMC1 は PRG バンクモード 3（最後のバンク） |
| OAM の DRAM 減衰 | `03` §4.9 | **再現しない**（Wiki も「ほとんどのエミュレータは再現せず互換性問題も起きていない」としている） |
| PPU I/O バスラッチの減衰 | `03` §4.1 | **デフォルト無効**。有効化した場合は減衰も決定論的に（サイクル数ベースで）実装する |

> **「デフォルト RAM 初期値 = ランダム」（`02` §10）と決定論は矛盾しない。** シードを固定・記録すれば再現できる。開発時に「未初期化 RAM に依存したゲームのバグ」を見つけられる利点を保ちつつ、ムービーの再現性も得られる。

### 6.3 決定論のテスト

**これが S2 と決定論を守る唯一の現実的な手段である。**

| テスト | 内容 | 検出できるもの |
|---|---|---|
| **ステート往復テスト** | フレーム N でステートを保存 → そのまま M フレーム進めて状態 X を得る。別インスタンスでステートをロード → M フレーム進めて状態 Y を得る。**X と Y をバイト単位で比較** | **保存漏れしている状態フィールド**。最も強力 |
| 全フレーム往復テスト | 1000 フレームぶん、毎フレームで上記を実行（M=1） | 上記をしらみつぶしに |
| ムービー再現テスト | 同じムービーを 2 回再生し、チェックサム列が一致するか | ホスト側の非決定論（map、ゴルーチン、壁時計） |
| クロスプラットフォームテスト | macOS / Windows / Linux で同じムービーのチェックサムが一致するか | 浮動小数点・アーキテクチャ依存 |

**ステート往復テストは CI に入れる。** これがあると「新しい状態フィールドを追加したのに直列化を忘れた」という最も起こりやすいバグが必ず検出される。

## 7. 入力ムービーの設計

### 7.1 要件

| ID | 要件 |
|---|---|
| M1 | プレイ中の入力を記録し、後から完全に同じ再生ができる |
| M2 | テスト自動化に使える（`08` §6）。`--movie` で再生し、`--headless` と併用できる |
| M3 | desync（再生がずれること）を検出し、**最初にずれたフレームを報告する** |
| M4 | TAS 的な編集がしやすい（フレーム単位でテキスト的に扱える） |
| M5 | 電源投入から、またはセーブステートから開始できる |

### 7.2 入力の記録粒度: フレーム単位

| 候補 | 評価 |
|---|---|
| **フレーム単位（採用）** | 1 フレームにつき各ポートのボタン状態を記録。編集しやすく（M4）、サイズが小さい |
| ポーリング単位（$4016 strobe ごと） | 最も忠実だが、再生時にポーリング列が完全一致しないと使えず、編集も不可能 |

**決定: フレーム単位を正式形式とする。** 追加で、desync 調査用に「ポーリング単位のトレース」を別ファイルに出せるデバッグオプションを用意する。

**ラッチ点の定義**（ここを曖昧にすると再現しない）:

> **ムービーのフレーム N の入力は、エミュレートされたフレーム N の scanline 0 / dot 0 でラッチされ、そのフレーム中は不変。** ゲームが $4016 に strobe を書いたとき、この値が読まれる（`06` §3.1 の実機挙動はそのまま維持される）。

**重要**: ターボ（連射）は**ホスト側の機能**なので、記録時には「ターボ適用後の状態」を記録する。再生時にターボを再適用してはいけない（`06` §7.2）。

### 7.3 ファイル形式

ヘッダ（バイナリまたは JSON）+ 入力ログ（バイナリ）の 2 部構成にする。

| ヘッダのフィールド | 用途 |
|---|---|
| マジック `"SHGM"` + フォーマットバージョン | |
| エミュレータのバージョンとコミットハッシュ | 不一致で警告（§7.5） |
| **ROM ハッシュ**（PRG+CHR の SHA-1）+ ROM ファイル名（情報のみ） | 検証 |
| リージョン、マッパー番号 + サブマッパー | 検証 |
| **決定論シードと設定の全部**（§6.2 の表の全項目） | 再現に必須 |
| 開始方法: `power-on` または `savestate`（埋め込み） | M5 |
| ポート 1 / 2 のデバイス種別 | |
| 総フレーム数、再記録回数、作者、コメント | |

入力ログ:

- 1 フレーム 1 レコード。標準コントローラ 2 個なら **2 バイト/フレーム**
- 60 fps で 120 B/s = **約 7 KiB/分**。圧縮不要
- **イベントレコード**も同じ列に混ぜる（リセット、ハードリセット、ディスク交換など）。フレーム N で起きたイベントとして記録する。**これがないとムービー中のリセットを再現できない**

### 7.4 desync 検出（M3）

**ムービーに定期的なチェックサムを埋め込む。**

- N フレームごと（デフォルト 60 = 1 秒ごと）に、状態のハッシュを記録する
- ハッシュ対象: 内蔵 RAM + CIRAM + OAM + パレット + CPU レジスタ + 累積サイクル数（PRG-RAM も含める）
- 再生時に比較し、**不一致を検出したフレーム番号と、どのセクションが違ったかを報告する**

これはテスト自動化（`08` §6.2）でそのまま使える。「スクリーンショットのハッシュ比較」より軽く、原因の切り分けもしやすい。

### 7.5 バージョン間互換

精度バグを直すとムービーは desync しうる（これは正しい挙動である。実機に近づいた結果なので）。

- ヘッダのエミュレータバージョンが異なる場合は**警告を出して再生を続ける**
- desync を検出したら**その時点で停止し、フレーム番号を報告する**（黙って続けない）
- テスト用のムービーは、精度を直したときに**意図的に再記録する**。再記録が必要になったことは「挙動が変わった」という有用な情報

## 8. 巻き戻し（rewind）

セーブステートと決定論が揃うと、巻き戻しは自然に実装できる。

### 8.1 方式

| 方式 | メモリ | 実装 |
|---|---|---|
| 毎フレーム保存 | 40 KiB × 60 × 60 秒 = **144 MiB**（過大） | 単純 |
| **N フレームごと保存 + 前方再生（採用）** | 10 フレームごとなら 60 秒で **14 MiB**（flate 圧縮で数 MiB） | 決定論が前提。「最も近いステートをロードして必要フレーム数だけ進める」 |
| 差分保存 | 小さいが実装が複雑 | 将来 |

**決定: 10 フレームごとにステートを保存し、リングバッファに保持する。** 巻き戻し時は目標フレームの直前のステートをロードし、記録しておいた入力で前方再生する。

- これは**入力を記録し続けている**ことが前提 → **ムービー記録の仕組みをそのまま使う**（常時、直近 N 秒ぶんの入力を記録している）
- 保持時間はデフォルト 60 秒、設定で変更可
- 圧縮は `compress/flate`（`05` の見積もりから、RAM 領域が大半なので圧縮が効く）

**この「ムービー記録の仕組みを巻き戻しが再利用する」構造が、2 機能を同時に入れる最大の利点である。**

### 8.2 run-ahead との関係

`13_future_topics.md` §8 の run-ahead（入力遅延削減）も同じ機構（ステート保存 + 再実行）で実現できる。**第 1 弾では実装しないが、同じ基盤の上に載る**ことを確認しておく。

## 10. 実装順序への影響

セーブステートは**各コンポーネントの実装と同時に書く**のが唯一現実的である。後からまとめて書くと必ず漏れる。

| 段階 | やること |
|---|---|
| CPU 実装時 | `StateWriter`/`StateReader` の基盤 + CPU の Save/Load + **ステート往復テスト**（§6.3）をこの時点で CI に入れる |
| PPU 実装時 | PPU の Save/Load。往復テストが自動的に PPU もカバーする |
| APU 実装時 | 同様 |
| マッパー実装時 | 各マッパーが自分の状態を申告する。**新しいマッパーを足したら往復テストが自動でカバーする** |
| 入力実装後 | ムービーの記録・再生。この時点でテスト自動化の基盤が完成する |
| 上記の後 | 巻き戻し（既存機構の組み合わせ） |

> **`docs/plans/` では「セーブステートを実装する」という独立したフェーズを作らない。** 各コンポーネントのタスクに「Save/Load と往復テスト」を含める。独立フェーズにすると「あとで」になり、結局漏れる。

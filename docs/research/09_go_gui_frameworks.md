## 0. 決定（2026-09-21、人間の判断）

| 項目 | 決定 |
|---|---|
| **GUI フレームワーク** | **Fyne v2.8.1**（案 A） |
| **オーディオ** | `github.com/ebitengine/oto/v3` v3.5.1 |
| **デバッグビューアのウィンドウ形態** | **別ウィンドウと「1 ウィンドウに畳んだ形」の両方をサポートする** |
| **シングルバイナリの厳密さ** | **OS 標準ランタイムへの依存は許容する** |

決定に伴う設計上の帰結:

1. **ビューアを「別ウィンドウ」と「1 ウィンドウ内のタブ/分割」の両方で出せるようにする。**
   - Fyne は `App.NewWindow()` による別ウィンドウと、`container.AppTabs` / `container.Split` による 1 ウィンドウ内配置の両方を持つ
   - **各ビューアを「`fyne.CanvasObject` を返すコンポーネント」として実装し、それを「別ウィンドウに入れる」か「タブに入れる」かを実行時に切り替える設計にする。** ビューアのロジックは配置形態を一切知らない
   - 設定で `"ui.viewerLayout": "windows" | "docked"` を切り替える。デフォルトは `"windows"`（project.md の記述どおり）
   - レイアウト（各ウィンドウの位置・サイズ・開閉、またはタブの構成）を設定ファイルに保存・復元する

2. **OS 標準ランタイム依存が許容されたので、次を README に明記するだけでよくなった。**
   - Linux: PulseAudio または `libasound.so.2`（oto）、OpenGL、X11 または Wayland（Fyne）
   - macOS / Windows: 追加依存なし（Fyne が OpenGL を、oto が OS 標準オーディオ API を使う）
   - Wails v3 を選ばなかったので WebView への依存は発生しない

3. **最大のリスク（R4: 60 fps 描画）を最初に検証する。** → §8 のスパイク。結果は `docs/research/09a_fyne_performance_spike.md` に記録する

## 1. 背景・目的

Shogun Emulator は「エミュレータ本体」と「デバッガ GUI」という性質の違う 2 つの UI を同時に持つ。フレームワーク選定はプロジェクト全体の形を決めるので、要件を先に固定してから比較する。

> 注: ユーザーの CLAUDE.md は「最新のライブラリは context7 MCP で確認する」としているが、**この環境には context7 MCP が入っていない**ため、Go module proxy（`proxy.golang.org/<module>/@latest`）と各プロジェクトの公式サイトで直接確認した。バージョンと日付はすべて 2026-09-21 時点の実測値。

## 4. 各候補の評価

### 4.1 Ebitengine v2.10.2 — R3 を満たせない

2D ゲーム向けライブラリ。ピクセル描画・オーディオ・入力が全部入りで、NES エミュレータの「画面」部分には理想的。

**利点**

- R4 ◎ ピクセルバッファの毎フレーム更新がまさに想定用途。60 fps は何の工夫もなく出る
- R5 ◎ オーディオが内蔵（内部で oto を使う）。ストリーミング再生の API が用意されている
- R6 ◎ キー入力・ゲームパッドの API が充実。`inpututil` でキーの押下/離上の判定も容易
- R1 ◎ クロスコンパイルが現実的。プラットフォームごとの依存が少ない
- R8 ◎ ウィンドウアイコン設定 API あり
- アクティブに開発されている（2026-09-11 リリース）

**欠点**

- **R3 ✗ 複数ウィンドウを扱う方法がない。** 「多くの設計・実装変更が必要になる」として長年サポートされていない（`hajimehoshi/ebiten` Discussion #1831）。この Discussion では **まさに「エミュレータのデバッグはタイルマップやスプライトリストなどを現在のゲーム画面とは別に描くことが多く、別ウィンドウを作れたら素晴らしい」という要望が出ている**が、実現していない
- R2 △ ネイティブメニューがない。ウィンドウ内に自前の UI を描く必要がある。公式に **`debugui`**（デバッグ目的が主眼の Ebitengine 用 UI ツールキット。2026 年 9 月に更新）があり、これを使えばウィンドウ内にパネルとして各ビューアを出せる
- R9 △ 16 進ダンプや逆アセンブルの長いリストを扱うウィジェットはないので全部自作

**結論**: 「別ウィンドウ」を「1 つのウィンドウ内のドッキングパネル / タブ」に読み替えてよいなら最有力。読み替えないなら不可。

### 4.2 Fyne v2.8.1 — GUI は理想的、描画性能が要検証

Material Design 風のウィジェットツールキット。OpenGL でレンダリングする。

**利点**

- **R3 ◎ `App.NewWindow(title)` で複数ウィンドウを自由に作れる**（実測でドキュメント確認済み）
- **R2 ◎ `Window.SetMainMenu(*fyne.MainMenu)` でトップレベルメニュー。macOS ではネイティブメニューバーにレンダリングされる**（v2.8 で「macOS でウィンドウ切り替え時にネイティブメニューを再構築」という修正が入っている = 実際に使われている証拠）
- **R9 ◎ `widget.TextGrid` が「等幅グリッド + セル単位のスタイル（`BackgroundColor()` / `TextColor()`）」を提供する。** 16 進ダンプの「書き換わった箇所をフラッシュ」と逆アセンブルの「現在位置ハイライト」がそのまま実装できる。`widget.Table` / `widget.List` は長さ関数 + コールバックによる遅延生成なので 64 KiB のメモリダンプも扱える
- R8 ◎ `App.SetIcon(Resource)`、`Window.SetIcon`。`fyne bundle` でアセットを Go ソースに埋め込めるのでシングルバイナリになる
- R1 ○ `fyne-cross` でクロスビルド。Wayland がデフォルトサポート（v2.8）
- ダークモード・テーマ・DPI スケーリングが最初から入っている

**欠点**

- **R4 △〜✗ 画像の高頻度更新に関する性能問題が複数報告されている。** 「画像リフレッシュ時のひどいスタッタ（期待の 60 FPS ではなく 5〜10 FPS に近い）、特に 1080p 以上のディスプレイで顕著」（issue #3052）、「`SetContent` が遅く CPU 1 コアを 100% 使う」（discussion #5373）、「アクティブなリサイズ中は `canvas.Image` / `canvas.Raster` のテクスチャが更新されない」（issue #531）。v2.7/v2.8 で「レンダリングの大幅な性能向上」が入っているが、**この用途で 60 fps 出るかは実測しないと分からない**
- **R5 ✗ オーディオ API が無い。** `oto` を直接使う（これ自体は問題ない。むしろ制御しやすい）
- R6 △ キーイベントは取れるが、ゲームパッドは無い（別ライブラリが必要）。同時押しの扱いは自前で状態管理する
- ウィジェットの描画モデルが「変更があったら Refresh」なので、60 fps で毎フレーム更新する使い方は設計思想と逆行する

**結論**: R2 / R3 / R9 に対して最も素直に答えが出るが、**R4 が最大のリスク**。選ぶなら最初に性能スパイクを打つ。

### 4.3 Gio v0.10.2 — 自由度は最高、作る量が最も多い

イミディエイトモードの GPU レンダリング GUI。

**利点**

- R3 ◎ `app.Window` を複数作れる（ゼロ値が安全に使えるようになり、`Event` をループで呼ぶモデル）
- R4 ○ GPU 描画。毎フレーム画像をアップロードする実装が可能
- R1 ◎ 依存が少なくクロスコンパイルしやすい
- 描画が完全に自分の制御下にあるので、60 fps の更新も「毎フレーム再描画」が自然

**欠点**

- **R2 △ ネイティブメニューバーが無い。** メニューも自分で描く
- **R9 ✗ ウィジェットをほぼ全部自作。** 16 進ダンプのための仮想スクロール表、逆アセンブルリスト、設定ダイアログ、キーバインド UI をすべてゼロから書く
- R5 ✗ オーディオなし（oto）
- ドキュメントが薄く、学習コストが高い

**結論**: 実装工数が他の 2〜3 倍になる見込み。**この規模のデバッガ UI をゼロから書くのは現実的でない。**

### 4.4 Wails v3.0.0-beta.23 — デバッガ UI の生産性は最高、配布が最も難しい

Go バックエンド + OS の WebView をフロントエンドにする。

**利点**

- **R3 ◎ ネイティブなマルチウィンドウサポート。** 「設定ウィンドウ、ドキュメントウィンドウ、ツールパレット、インスペクタウィンドウ」が想定用途として明記されている。v2 の「単一ウィンドウ・コンテキスト駆動」から、**アプリケーション・ウィンドウ・サービス・イベントが明示的なオブジェクトになるモデル**に変わった
- R2 ◎ ネイティブメニュー
- **R9 ◎◎ HTML/CSS/JS でデバッガ UI を書ける。** 16 進ダンプの仮想スクロール、逆アセンブルのリスト、パレットのカラーピッカー、キーバインド設定 UI — すべて Web の世界では解決済みの問題。**生産性が桁違いに高い**
- R8 ◎

**欠点**

- **R1 △ WebView ランタイムへの依存。** macOS は WKWebView 内蔵で問題なし。Windows は WebView2 ランタイム（Windows 11 は同梱、それ以外はインストーラが必要）。**Linux は webkit2gtk が必要で、実質「シングルバイナリ」にならない**
- **R4 △ フレーム転送のリスク。** Go 側で生成した 256×240 のピクセルデータを 60 fps で JS 側に渡す必要がある。184 KB/フレーム × 60 = 約 11 MB/s。IPC 経由では現実的でなく、ローカル HTTP / WebSocket ストリームや共有メモリなどの工夫が必要。**設計上の大きな未知**
- **R5 △ Web Audio API 経由。** 低レイテンシには AudioWorklet が必要で、Go からのサンプル供給と合わせて実装が複雑
- **ベータ版。** 「デスクトップ API は安定しており本番利用しているチームもあるが、ベータ期間で最終的な互換性とワークフローの問題をコミュニティと洗い出している」段階
- Go 単一言語ではなく TypeScript/CSS も書くことになり、AI/人間の開発者が扱う技術スタックが増える

**結論**: デバッガ UI の作りやすさは圧倒的だが、**R1（シングルバイナリ）と R4（60 fps）という project.md の明示要件で最もリスクが高い。**

### 4.5 SDL / GLFW + Dear ImGui（cimgui-go v1.6.0）— エミュレータとしては王道、配布が面倒

Dear ImGui はエミュレータのデバッガ UI に広く使われている定番。cimgui-go が Go バインディングを提供する。

**利点**

- R4 ◎ テクスチャ更新は生の OpenGL なので当然 60 fps
- R5 ◎ SDL のオーディオ（または oto）
- R6 ◎ SDL はゲームパッドも含めて入力が充実
- R2 ○ ImGui のメニューバー（ウィンドウ内描画。**macOS のネイティブメニューバーではない**）
- R3 ○ SDL の複数ウィンドウ、または ImGui のマルチビューポート
- R9 ◎ ImGui には Table（ソート・仮想スクロール対応）、テキスト、カラーピッカーなど、デバッガに必要なものが揃っている。**16 進ダンプ用の定番実装パターンが業界的に確立している**

**欠点**

- **R1 ✗〜△ ビルドと配布が最も面倒。**
  - cimgui-go は cgo（C++ の Dear ImGui をリンクする）。クロスコンパイルにはプラットフォームごとのツールチェーン（zig cc や CI マトリクス）が必要
  - GLFW バックエンドと SDL バックエンドを同時に有効化するとリンカがクラッシュする可能性があり、ビルドタグ（`enable_cimgui_glfw` / `enable_cimgui_sdl2`）で選ぶ
  - `go-sdl2` は **2024-05-30 から更新が止まっている**。SDL3 の purego バインディング（`go-sdl3`、`purego-sdl3`）は新しいが v0.1.x で成熟度が低く、**SDL3 の共有ライブラリが実行時に必要**（= シングルバイナリにならない）
- R2 △ macOS でメニューバーがウィンドウ内に出るのは、macOS ユーザーには「移植アプリ感」が強い
- ファイルダイアログは別ライブラリ（`ncruces/zenity` は cgo 不要で使える）

**結論**: 技術的には最適だが、**project.md の R1（シングルバイナリ）と正面から衝突する。**

## 6. 推奨案

### 案 A（推奨）: Fyne 単独 + oto

**理由**

1. **project.md の要件のうち、最も曲げにくい R1・R2・R3・R9 を 1 つのフレームワークで素直に満たせるのは Fyne だけ。** 他の候補はいずれかを諦めるか、設計を project.md と違う形に変える必要がある
2. R9（16 進ダンプ、逆アセンブル、リアルタイム同期ビューア）は工数の大きい部分で、`widget.TextGrid`（セル単位の前景色・背景色）と `widget.Table`（遅延生成）がそのまま使える
3. Go 単一言語で完結するので、AI と人間が交代で開発する前提（project.md の記述）に合う
4. 唯一の重大リスク（R4 の描画性能）は、**開発の最初に小さなスパイクで測れる**。「256×240 を 3 倍に拡大して 60 fps で更新し続けられるか」を数十行で確認できる

**リスクと緩和策**

| リスク | 緩和策 |
|---|---|
| R4: 60 fps 出ない | フェーズ 0 で性能スパイクを打つ。`canvas.Image` の `ScaleMode` と「Refresh の粒度」を試す。ダメなら案 B に切り替える（切り替えコストはエミュレータコアに影響しない。GUI 層だけを差し替える設計にしておく） |
| R5: オーディオが無い | `github.com/ebitengine/oto/v3` v3.5.1 を直接使う。これは**むしろ利点**で、バッファサイズとレイテンシを自分で制御できる |
| R6: ゲームパッドが無い | 第 1 弾はキーボードのみ（project.md の要件はキーボード）。パッドは後から別ライブラリで足す |

### 案 B（代替）: Ebitengine + debugui（1 ウィンドウ内パネル）

**R3 を「1 つのウィンドウ内のドッキング可能なパネル / タブ」に読み替える場合**の最短経路。

- R4 / R5 / R6 が完璧。エミュレータ部分の実装が最も安全
- メニューとデバッグ UI は `debugui` で作る
- **project.md の「それぞれ別ウインドウとする」に反するので、人間の承認が必要**
- 実際のメリット: ウィンドウ管理のバグがゼロになり、全体のレイアウトを保存/復元しやすい。デメリット: 大きなディスプレイで各ビューアを好きな位置に置けない

### 案 C（将来の逃げ道）: GUI 層を差し替え可能にしておく

どの案を採っても、**エミュレータコア（`internal/nes/...`）は GUI に一切依存させない。**

```
internal/nes/        CPU / PPU / APU / mapper / bus（GUI 非依存、テスト可能）
internal/emu/        エミュレータのライフサイクル（ロード、実行、ステップ、状態）
internal/ui/         GUI 層（fyne / ebiten / … の実装をここに閉じ込める）
internal/config/     設定ファイル
cmd/shogun/          main（GUI 起動 / CLI 起動の分岐）
```

この境界を守れば、フレームワークの選択が間違っていたときに GUI 層だけを書き直せる。**選定の失敗コストを下げるのが最も重要な設計判断。**

## 7. 人間に確認したいこと

1. **「別ウィンドウ」を厳密に OS のウィンドウとするか、1 ウィンドウ内のドッキングパネル/タブでもよいか**
   - 厳密に別ウィンドウ → 案 A（Fyne）
   - パネルでもよい → 案 B（Ebitengine）も選択肢に入り、描画性能のリスクがゼロになる
2. **「シングルバイナリ」の厳密さ**
   - 完全に 1 ファイル → Wails v3 と SDL 系は除外
   - OS 標準の WebView に依存してよい → Wails v3 が選択肢に入る（デバッガ UI の生産性が最高）
3. **macOS のネイティブメニューバーが必要か**
   - 必要 → Fyne / Wails v3
   - ウィンドウ内メニューでよい → Ebitengine / ImGui も可

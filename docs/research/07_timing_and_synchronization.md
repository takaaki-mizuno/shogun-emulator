# タイミング・DMA・オープンバス・同期設計の調査

> 調査日: 2026-09-20 / 一次情報源: NESdev Wiki（https://www.nesdev.org/wiki/）

## 1. 背景・目的

CPU・PPU・APU・マッパーは実機では**並列に動く**。エミュレータはこれを逐次実行に落とし込まなければならない。
本書は次の判断に使う。

- コンポーネント間の同期をどの粒度で行うか
- DMA（OAM DMA / DMC DMA）による CPU 停止をどう表現するか
- オープンバスをどうモデル化するか
- 実時間との同期（映像フレームレート / オーディオバッファ）をどう設計するか
- 実行速度の可変（2 倍 / 1.5 倍 / 1/2 倍 …、project.md の要件）をどこで実装するか

結論: **CPU 1 サイクルごとに PPU 3 ドット・APU 1 サイクルを進める「lock-step」方式を採り、オーディオ駆動で実時間に同期する。** 理由は §7。

**PAL は 3.2 ドット/サイクルなので整数比にならない。** 実装は「PPU ドットのアキュムレータを分数で持つ」か「マスタークロック単位で回す」のどちらか。マスタークロック単位（NTSC: CPU=12, PPU=4）で回すのが素直だが遅い。

> **エミュレータ実装の小技**（NESdev フォーラム由来）: NTSC CPU を 21441960 Hz（= (341×262−0.5)×4×60）で回すと、フレームレートがちょうど 60 fps に固定されて安定する。本来は 60.0988 Hz。オーディオ/ビデオ同期の選択肢として `07.6` で扱う。

## 3. DMA

2A03 は 2 個の DMA ユニットを持つ。1 個はスプライトデータを PPU OAM にコピーし（OAM DMA）、もう 1 個は DPCM サンプルデータを APU の DMC サンプルバッファにコピーする（DMC DMA）。

### 3.1 get サイクルと put サイクル（cadence）

**DMA ユニットは好きなサイクルで読み書きできない。** get サイクル（読める）と put サイクル（書ける）を交互に行き、許されないサイクルでは待つ。

- **get / put は APU クロックの前半 / 後半に揃っている**（Visual2A03 では apu_clk1 / apu_clk2）
- 「偶数 / 奇数 CPU サイクル」と説明されることがあるが**正確ではない**。CPU と APU は電源投入時に 2 通りのアライメントのどちらかにランダムに入るため、get / put が現れる CPU サイクルのパリティは電源投入ごとに変わりうる
- **電源投入時、最初の CPU サイクルが get か put かはランダム**

### 3.2 停止（halt）の規則

- **DMA は CPU のリードサイクルでのみ停止できる。** ライトサイクルでは停止に失敗し、次の CPU サイクルで再試行する（成功するまで繰り返す）
- 最大 3 サイクルの遅延が起こりうる（RMW 命令は連続 2 回のライト、割り込みは連続 3 回のライトを持つ）
- 停止処理そのものに 1 CPU サイクルかかる（有用な仕事はしない）
- CPU は内部の RDY 入力で停止される。**RDY がデアサートされると 6502 コアは最後のリードサイクルを無限に繰り返し**、前進もせず割り込みも処理しない
- **2A03 ではこの繰り返しリードが外部から見える**（no-operation な DMA サイクルすべてで）。副作用を持つレジスタを読んでいるとデータが失われる
- 2A07 では、no-operation サイクル中に別のアドレス（おそらく DMA アドレス）がバスに出ていると推測される
- DMA が完了すると、CPU は停止時に試みていたリードを実行する

no-operation サイクルは 3 種類（等価）: **halt サイクル**、**DMC 専用の dummy サイクル**、**オプションの alignment サイクル**。

一般的な挙動:

```
* 正常に停止:
 (halted) CPU がアドレス A を読む       ← DMA halt サイクル
 (halted) [DMA が発生]
          CPU がアドレス A を読む       ← CPU 実行再開

* ライトにより停止が遅れる:
          CPU がライト                  ← DMA が停止を試みる
          CPU がライト                  ← DMA が停止を試みる
 (halted) CPU がアドレス A を読む       ← DMA halt サイクル
 (halted) [DMA が発生]
          CPU がアドレス A を読む       ← CPU 実行再開

* DMA が non-access サイクルを持つ:
 (halted) CPU がアドレス A を読む       ← DMA halt サイクル
 (halted) CPU がアドレス A を読む       ← DMA は読み書きしない
 (halted) DMA がアドレス B にアクセス
          CPU がアドレス A を読む       ← CPU 実行再開
```

### 3.3 OAM DMA

$4014 にページ番号（アドレス上位バイト）を書くとトリガされる。**$4014 書き込みの次のサイクルで CPU を停止するようスケジュールされる。**

典型的な流れ: halt サイクル → （必要なら）alignment サイクル → 256 回の get/put ペア。

- 256 組の get/put はページ先頭から前方向にコピーする
- DMA は get サイクルでしか読めないので、読めるようになるまで alignment サイクルが必要になることがある
- **合計 513 または 514 サイクル**（alignment が必要かどうかで変わる）
- **OAM DMA は「最後に $4014 に書かれたページ」からコピーする。** `INC $4014` のような RMW 命令は CPU が停止する前に 2 回目の書き込みを済ませられるので、**2 回目のページからコピーされる**
- **OAM DMA は DMC DMA より優先度が低い。** OAM DMA 中に DMC DMA の get が起きると OAM DMA は一時停止する

```
* alignment 不要:
          (get) CPU が $4014 に書く
 (halted) (put) CPU がアドレス A を読む   ← halt サイクル
 (halted) (get) DMA が $xx00 を読む
 (halted) (put) DMA が $2004 に書く
              ...（256 回）
          (get) CPU がアドレス A を読む   ← 再開

* alignment 必要:
          (put) CPU が $4014 に書く
 (halted) (get) CPU がアドレス A を読む   ← halt サイクル
 (halted) (put) CPU がアドレス A を読む   ← alignment サイクル
 (halted) (get) DMA が $xx00 を読む
 (halted) (put) DMA が $2004 に書く
              ...（256 回）
```

### 3.4 DMC DMA

DMC ユニットのサンプルバッファに 1 バイトをコピーする。**「DPCM 再生が有効」「サンプルに残りバイトがある」「サンプルバッファが空」のすべてが成立したときにスケジュールされる。**

典型的な流れ: halt サイクル → dummy サイクル → （必要なら）alignment サイクル → get。

2 種類ある:

| 種類 | 発生条件 | 停止を試みるサイクル | 典型的な合計サイクル |
|---|---|---|---|
| **load** DMA | $4015 D4 がセットされた後（サンプルバッファが空のときのみ） | 書き込みの **2 APU サイクル後の get サイクル**（= 3 または 4 CPU サイクル目） | 3 |
| **reload** DMA | サンプルバッファが空になったことへの応答 | **put サイクル** | 4 |

- halt の後、DMC DMA は必ず dummy サイクル（何もしない）を行う
- 次のサイクルが get でなければ alignment に 1 サイクル使う
- その後に DMA リードを行う
- **通常 3 または 4 サイクル。** load / reload で停止を試みるサイクル種別が違うので、halt が奇数サイクル遅れなければ load は 3、reload は 4
- バグにより追加サイクルが発生することがある（§3.5）

```
* load DMA:
          (get) \ CPU が $4015 に書く   ← この APU サイクル中に DMC が有効化
          (put) /
          (get) CPU がリード
          (put) CPU がリード
 (halted) (get) CPU がアドレス A を読む  ← halt サイクル
 (halted) (put) CPU がアドレス A を読む  ← dummy サイクル
 (halted) (get) DMA がアドレス B を読む
          (put) CPU がアドレス A を読む  ← 再開

* reload DMA:
 (halted) (put) CPU がアドレス A を読む  ← halt サイクル
 (halted) (get) CPU がアドレス A を読む  ← dummy サイクル
 (halted) (put) CPU がアドレス A を読む  ← alignment サイクル
 (halted) (get) DMA がアドレス B を読む
          (put) CPU がアドレス A を読む  ← 再開
```

### 3.5 DMC DMA のバグ

「DMC 出力サイクルが終わるあたり（= サンプルバッファが空になり reload DMA がスケジュールされるタイミング）でサンプル再生が止まる」ことに関連した 2 つのバグがある。

止まり方には 2 通りある:

- **明示的**: $4015 D4 をクリアしてサンプルを止める
- **暗黙的**: reload DMA がスケジュールされる少し前に、サンプルバッファが空の状態で**ループしない 1 バイトサンプル**を開始する

「reload DMA がスケジュールされる 1 APU サイクル前（= halt 試行の 2 または 3 CPU サイクル前）」に再生が止まると、**DMA は開始されるが 1 サイクル後に中止される。** ライトサイクルで halt が遅れた場合、中止された DMA はそもそも発生しない。

> この領域は優先度が低い。第 1 弾では「load / reload の基本形」と「§3.6 のレジスタ競合」を実装し、バグは後回しにする（該当するのは非常に特殊な ROM のみ）。

### 3.6 レジスタ競合（実装必須）

**2A03 では、CPU が停止している間、no-operation な DMA サイクルごとに「停止したときのリードサイクル」を繰り返す。** 副作用を持つレジスタを読んでいた場合、データが失われる。

- OAM DMA では実質問題にならない（タイミング上の制約により）
- **DMC DMA では現実的な問題**で、通常は回避策が必要
- 対象レジスタの例: PPUSTATUS ($2002)、PPUDATA ($2007)、サウンドステータス ($4015)。DMC DMA と衝突すると**2 回以上の余分なリード**が起こる

**ジョイパッドの場合は機構が少し違う。** ジョイパッドは CPU からの直接線（joypad 1 /OE, joypad 2 /OE）でクロックされ、アドレスバスを経由しない。これらの出力イネーブルは CPU サイクル全体にわたってアサートされ、隣接サイクルでも同じジョイパッドレジスタを読んでいれば継続する。したがって**コントローラは「連続したリードのまとまり」ごとに 1 回だけリードを見る。**

- **RF Famicom では**、2A03 外部の追加ハードウェアが joypad /OE をクロックサイクルの半分の間だけ通すため、コントローラは**すべての CPU リードサイクルでクロックを見る**（連続まとまりごとではなく）

さらに複雑な要因: 2A03 のレジスタ活性化は、**2A03 のアドレスバスの bit 4–0 と、6502 コアのアドレスバスの bit 15–5 を組み合わせて**判定している。6502 コアは停止中も同じアドレスを保持するので、$4000–$401F を読んでいた場合、DMA のアドレスが意図せず 2A03 レジスタを活性化させてしまう。結果としてバス競合が起き、もう一方のジョイパッドから余分なリードが発生したり、逆に現在のジョイパッドの余分なリードを防いだりする。

**2A07 ではこれらの余分なリード問題が修正されている**（機構は未解明）。

競合の例:

```
* DMC DMA が $2007 リードと衝突（3 回の余分なリード）
 (halted) (put) CPU が $2007 を読む   ← halt
 (halted) (get) CPU が $2007 を読む   ← dummy
 (halted) (put) CPU が $2007 を読む   ← alignment
 (halted) (get) DMA がアドレス B を読む
          (put) CPU が $2007 を読む   ← 再開

* DMC DMA が $4016 リードと衝突（1 または 3 回の余分なリード）
 → コントローラのシフトレジスタが 1 bit 落ちる = Right が誤入力される
```

**回避策（ゲーム側）**: 同じ結果が 2 回連続で得られるまでジョイパッドを読み直す。または OAM DMA と同期したリードにする。

> Shogun Emulator の方針: **「DMC DMA 中の停止サイクルで、停止時に読んでいたアドレスを再度読む（副作用も発生させる）」を実装する。** これによりコントローラの bit 欠落が自然に再現され、回避策を持つゲームが正しく動く。設定で「忠実（デフォルト）/ 簡略（余分なリードを起こさない）」を選べるようにする。デバッグモードでは余分なリードが起きた瞬間をログに出す。

## 4. オープンバス

CPU がどのデバイスも活性化していないアドレスを読むと**オープンバス**になる。

### 4.1 CPU オープンバス

**標準的な NES では、オープンバスの読み出しは「このリードの直前にバスから読まれた最後の値」を繰り返す。**

| ケース | 返る値 |
|---|---|
| 絶対アドレス命令 | アドレスの上位バイト（オペランドの最後のバイト） |
| インデックス付きアドレッシング | オペランドから読んだベースアドレスの上位バイト（この時点でインデックスレジスタはまだ適用されていない） |
| インダイレクトアドレッシング | ポインタの上位バイトが最後にフェッチされる。Y インデックスはまだ適用されていない |
| DMC DMA が命令に割り込んだ場合 | 最後に読まれた値が変わりうる |

`LDA ($04), Y` の例（`$05,$04 = $73FA`、`Y = $31`、$742B には何もマップされていない）:

| サイクル | 動作 | リードアドレス | 読まれた値 |
|---|---|---|---|
| 1 | opcode リード | PC | $B1 |
| 2 | オペランドリード | PC | $04 |
| 3 | インダイレクト下位 | $0004 | $FA |
| 4 | インダイレクト上位 | $0005 | $73 |
| 5 | キャリー補正前のリード | $732B | **$73（オープンバス）** |
| 6 | キャリー補正後のリード | $742B | **$73（オープンバス）** |

**オープンバスはバイトの一部だけにも適用される。** コントローラポート（$4016, $4017）は bit 4–0 のみをデバイスが駆動し、bit 7–5 は直前のリードの対応ビット（通常はアドレス上位バイト $40 の `010`）を繰り返す。

オープンバスに依存するゲームの例:

| ゲーム | 依存内容 |
|---|---|
| Low G Man | $6000–$7FFF に WRAM を置いてしまうと、Chapter 1 Scene 3B のボス戦でクラッシュしたりブーメランでグリッチが出る |
| Battletoads & Double Dragon | 第 1 ステージ終盤で ~$600X を読む。$00 が返るとクラッシュ |
| Paperboy ほか Mindscape 製 | コントローラポートが正確に $41 でないとボタンを認識しない |
| Castlevania | イントロ直後に ~$7FFX を読む（無害） |

> **重要な設計判断**: iNES フォーマットには「WRAM が無い」ことを表す手段がなかったため、多くのエミュレータは $6000–$7FFF にデフォルトで WRAM を用意してしまう。**NES 2.0 の WRAM サイズフィールドを尊重し、指定が 0 ならオープンバスにする。** iNES しかない ROM では互換性のため WRAM を用意する（ただしログで警告する）。

一部のカートリッジはオープンバス領域の値に弱い非決定的な影響を与える（OR 効果で特に D7 を 1 にし、256 バイトページの終わり付近で頻度が高まる傾向）。**これは再現しない。**

### 4.2 PPU オープンバス

PPU は 2 本のデータバスを持つ（CPU 通信用の I/O バスと、ビデオメモリバス）。オープンバスの挙動は異なる。

**I/O バス**（→ `03_ppu.md` §4.1 と同じ内容）:

- どの PPU ポートに書いても（読み取り専用の $2002 を含め）値がこのバスに載る
- $2004 / $2007 の読み出しは OAM / VRAM / パレットからのバイトをこのバスに載せる
- $2002 の読み出しは bit 7–5 に値を載せ、残りは変えない
- **書き込み専用ポート（$2000, $2001, $2003, $2005, $2006）を読むと I/O バスの値が返る**

**ビデオメモリバス**: データバスがアドレスバス下位バイトとピン 31–38 で多重化されている。したがって**メモリが接続されていないアドレスを読むと通常アドレスの下位バイトが返る。** CNROM の一部構成でこれをコピープロテクトに使ったゲームがある。

### 4.3 電気的な根拠（なぜこうなるのか）

データバスは動的ラッチとして振る舞う。長い配線の容量により、一度置かれた電圧が「浮いた」ままもう一度読める。

本体内のデコーダ（Famicom 回路図の U3、74LS139）が M2 と CPU アドレス bit 15–13 から、カートリッジ ROM（$8000–$FFFF）、ワーク RAM（$0000–$1FFF）、PPU I/O（$2000–$3FFF）のイネーブルを作る。CPU 自身が $4015 と $4016–$4017 のリードをデコードする。**$4000–$4014 と $4018–$7FFF のリードをデコードする回路は本体内に存在しない。**

## 5. コンポーネント間同期の設計選択肢

NESdev Wiki の "Catch-up" ページが選択肢を整理している。

### 5.1 lock-step（サイクル単位切り替え）

各コンポーネントを 1 CPU サイクルぶん動かしてから次に切り替える。Nintendulator がこの方式（明快さと正確さを速度より優先）。

- **利点**: 実装が単純で、どんなレースコンディションも自然に再現される
- **欠点**: 遅い（ホスト CPU のキャッシュ効率が悪い）

### 5.2 catch-up

CPU を数十サイクル走らせてから PPU / APU を同期させる。実行効率最適化されたエミュレータの多く。

1. 「あるコンポーネントが別のコンポーネントに影響を与える次の時刻」を求める（CPU が PPU レジスタに書く、PPU が割り込みをアサートする、など）
2. **最も予測しにくいコンポーネント（NES では CPU）をその時刻まで走らせる**
3. 他のコンポーネントをその時刻まで走らせる

フレーム末（scanline 0 または 240 の開始時）にすべてを追いつかせ、完成したビデオサーフェスとオーディオストリームを OS に渡す。

**利点**: ホスト CPU のレジスタ/キャッシュにデータが留まるので速い。**条件**: 結果が「全部をサイクル単位で回したのと同じ（as-if）」になること。

### 5.3 予測（prediction）

各コンポーネントが「重要なこと」をする時刻を予測して、そこまで先に走らせる。

予測できるもの:

- 垂直ブランキング NMI
- sprite 0 ヒットを起こしうるスプライト 0 を含むスキャンライン
- オーバーフローフラグを立てうる「8 個以上のスプライトがあるスキャンライン」
- APU フレームカウンタと DMC 完了による IRQ
- APU レングスカウンタの状態
- 多くの場合、マッパー IRQ

「わずかに短めに見積もって走らせ、その後は I/O catch-up かサイクル単位に落とす」という実装がありうる。

### 5.4 タイムスタンプ

CPU が各レジスタに書いた時刻（サイクル）を覚えておき、他のコンポーネントがそのサイクルに書かれたものとして処理する。

ただし**タイムスタンプが予測を変える場合は、タイムスタンプではなく catch-up が必要**:

- PPU レジスタ（特に $2004）への書き込みは sprite 0 予測を変えうる
- マッパー / PPU レジスタへの書き込みはマッパー IRQ 予測を変えうる
- APU レジスタへの書き込みはフレーム IRQ 予測とレングスカウンタ予測を変えうる

### 5.5 スキャンライン単位

粗い予測とタイムスタンプ。CPU を 1 スキャンラインぶん走らせ、PPU とマッパーを 341 ドット走らせ、全スキャンライン終了後に APU を 1 フレームぶん走らせる。

古い PC や携帯機向け。「行儀のよい」ゲームは効率的に動くが**正確ではない**。

### 5.6 チェックポイントへの巻き戻し

NES では重要度が低い（複数 CPU が互いに割り込む系、Super NES + SA1 などで有効）。

ただし**入力遅延の削減**に応用できる: PC やモダンゲーム機の画像処理と LCD TV が 1 フレーム以上の遅延を入れるので、エミュレータが 1 フレーム以上先に走り、ボタンが変わったら数フレーム巻き戻して新しい入力で再実行する（いわゆる run-ahead）。

## 6. 実時間との同期

### 6.1 何に同期するか

| 方式 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| ビデオ同期（vsync） | ディスプレイの垂直同期に合わせる | 映像が滑らか、ティアリングなし | **ディスプレイが 60.000 Hz で NES が 60.0988 Hz なのでずれる。** オーディオバッファのアンダーラン/オーバーランが起きる |
| オーディオ同期 | オーディオバッファの消費速度に合わせる | **音のプチプチが出ない**（人間は音の途切れに映像のカクつきより敏感） | 映像がディスプレイと合わずティアリング/ジャダーが出る |
| 実時間同期 | 壁時計で 60.0988 Hz を刻む | 素直 | どちらもずれる |
| 動的リサンプル | オーディオ同期しつつ、映像はディスプレイに合わせ、サンプリングレートを微調整する | 両方きれい | 実装が複雑 |

**Shogun Emulator の方針: オーディオ駆動を基本にし、動的リサンプルで映像側のズレを吸収する。**

> **実測による裏付け（2026-09-21）**: `09a_fyne_performance_spike.md` の実測で、(1) Fyne のペイントループは vsync に固定され 60.00 fps で回る、(2) 固定レートのサンプル生成は 47,830〜48,256 /s とドリフトしてアンダーランを起こす、の 2 点が確認された。**「映像は vsync 固定、音は実クロックに追従」という非対称な現実に対して、オーディオを主クロックにする以外の選択肢は実質ない。**
>
> さらに 60 秒耐久試験（`09a` §4.4）で、**オーディオ駆動の実現方法が重要**だと判明した。「壁時計のティッカーで 1 フレームぶん進める」方式は音切れ 137 回、±0.5% フィードバック補正を足しても 6 回残る。**リングバッファの高水位でエミュレータをブロックさせる「バックプレッシャ方式」だけが音切れ 0 回**になり、CPU 負荷 10 倍でも崩れなかった。

理由: 人間は音の途切れ（クリック、プチノイズ）に対して、映像の 1 フレームのズレよりはるかに敏感である。またデバッグ機能（ステップ実行、ブレークポイント）でエミュレーションが止まる場面が頻繁にあるため、「オーディオバッファが枯れたら無音を出す」という挙動が明示的に必要になる。オーディオを主クロックにすると、この切り替えが素直に書ける。

### 6.2 実行速度の可変（project.md の要件）

要求: 2 倍、1.5 倍、1.2 倍、1/2 倍、1/4 倍など。

実装方針:

- **「1 秒間に進める CPU サイクル数」を倍率で変える**（エミュレータのタイムベースを変える）
- オーディオは 2 通りの扱いがある:
  1. **ピッチを変える**（サンプリングレート変換の比率を変えない）— 実装が単純。早送りで音が高くなる
  2. **ピッチを保つ**（タイムストレッチ）— 実装が重い
  3. **早送り中はミュートする** — 多くのエミュレータがこれ
- → **デフォルトは「1.0 倍以外ではピッチが変わる」+「4 倍以上ではミュート」**。設定で「早送り中は常にミュート」も選べるようにする
- ステップ実行・ブレークポイント中はオーディオを無音にする（バッファに 0 を流し続ける）

### 6.3 フレームスキップと遅延

- デバッグウィンドウ（BG / スプライト / パレット / メモリダンプ）はエミュレーションスレッドと別に更新する。**フレーム末にスナップショットを取り、UI スレッドが読む**
- project.md は「リアルタイムにメモリと同期したい」と書いている。**毎フレーム全体をコピーするのは 2 KiB + 8 KiB 程度なので問題ない**（CHR は最大 8 KiB のウィンドウ）。メモリダンプは 64 KiB のアドレス空間なので、可視範囲だけを読む

## 7. 実装方針と、その理由

### 7.1 lock-step を選ぶ

**第 1 弾では lock-step（§5.1）を採る。**

理由:

1. project.md がデバッグ機能（サイクル単位のステップ実行、ブレークポイント、メモリの書き換わり検出）を強く要求している。catch-up 方式では「今この瞬間の PPU の状態」が常に正確とは言えず、デバッガの表示が嘘になる
2. Go は十分速い。NTSC の 1 フレームは約 29780 CPU サイクル × 3 PPU ドット ≈ 89342 PPU ステップ。60 fps で約 536 万 PPU ステップ/秒。現代の CPU では余裕がある
3. 正確さのバグは「なぜ動かないか」の切り分けが極端に難しい。最初から正確な方式で作り、速度が問題になったら計測して最適化する（早すぎる最適化を避ける）

構造:

```go
// 概念スケッチ
func (b *Bus) tick() {
    b.ppu.Step()   // 1 ドット
    b.ppu.Step()
    b.ppu.Step()
    b.apu.Step()   // 1 CPU サイクル
    b.mapper.Tick(1)
    b.cycles++
}

func (b *Bus) Read(addr uint16) uint8  { b.tick(); return b.read(addr) }
func (b *Bus) Write(addr uint16, v uint8) { b.tick(); b.write(addr, v) }
```

`Read` / `Write` が必ず `tick()` を伴うので、CPU 側は「1 サイクル = 1 バスアクセス」の原則を守るだけでよい（→ `02_cpu_6502.md` §8）。

PAL の 3.2 ドット/サイクルは、`ppuDotAccumulator += 32; for ppuDotAccumulator >= 10 { ppu.Step(); ppuDotAccumulator -= 10 }` のような分数カウンタで扱う。

### 7.2 DMA は CPU の外側に置く

DMA は「CPU を停止させる」機構なので、CPU の中ではなくバス層（または専用の DMA コントローラ）に置く。

```go
// 概念スケッチ
type DMAController struct {
    oamPending   bool
    oamPage      uint8
    dmcPending   bool
    // get / put の位相
    isGetCycle   bool
}
```

CPU のメインループは各サイクルの頭で「DMA が停止を要求しているか」を見る。停止できるのはリードサイクルのみ（§3.2）。

### 7.3 オープンバスは「最後にバスから読んだ値」を 1 変数で持つ

```go
type Bus struct {
    lastBusValue uint8   // CPU オープンバス用
    // ...
}
```

- `read(addr)` がマップされたデバイスから値を得たら `lastBusValue = value`
- マップされていなければ `return b.lastBusValue`
- $4016/$4017 は「下位 5 bit をデバイスから、上位 3 bit を `lastBusValue` から」合成する

PPU の I/O バスラッチは PPU 内部に別途持つ（§4.2）。

### 7.4 テストで検証する

このあたりの挙動は**テスト ROM でしか検証できない**。`08_test_roms_and_validation.md` で対応する ROM を特定する。とくに:

- `cpu_interrupts_v2` — 割り込みの遅延・ハイジャック
- `ppu_vbl_nmi` — VBlank フラグ / NMI のタイミング
- `dmc_dma_during_read4` — DMC DMA とレジスタ読み出しの競合
- `oam_read` / `oam_stress` — OAM の挙動
- `sprite_overflow_tests` — スプライトオーバーフローバグ

# オーディオ出力・映像出力の実装調査（Go）

> 調査日: 2026-09-21 / バージョンは Go module proxy と各プロジェクトの README で確認した実測値

## 1. 背景・目的

`04_apu.md` で APU の内部動作は決まった。本書は「APU が出したサンプル列を実際にスピーカーから鳴らす」部分と、「PPU が出した 256×240 のフレームを画面に出す」部分を扱う。

`09_go_gui_frameworks.md` の選定結果に依存する部分があるので、**フレームワークに依存しない層（オーディオ）と依存する層（映像）を分けて書く。**

## 2. オーディオ出力

### 2.1 ライブラリ選定: `github.com/ebitengine/oto/v3` v3.5.1

**これ以外の選択肢は実質ない。** Ebitengine のオーディオも内部で oto を使っている。

対応プラットフォームと Cgo 要件（README より）:

| プラットフォーム | Cgo | バックエンド |
|---|---|---|
| Windows | **不要** | WASAPI |
| macOS | **不要** | AudioToolbox.framework（自動リンク） |
| Linux | **不要** | PulseAudio（pure-Go の `github.com/jfreymuth/pulse`）。PulseAudio サーバに到達できないときは **ALSA にフォールバック**（`libasound.so.2` を実行時に動的ロード。ビルド時に ALSA の開発ヘッダは不要だが、実行時に `libasound.so.2` が存在する必要がある） |
| FreeBSD / OpenBSD | 不要 | PulseAudio（BSD はテストが十分でない） |
| WebAssembly | 不要 | Web Audio |

> **R1（シングルバイナリ）への影響**: Linux では PulseAudio または `libasound.so.2` が実行環境に必要。これは「デスクトップ Linux なら事実上必ずある」ものなので許容範囲。ただし README に明記しておく。
> FreeBSD で `CGO_ENABLED=0` としてクロスコンパイルする場合は `-gcflags="github.com/ebitengine/purego/internal/fakecgo=-std"` が追加で必要（当面 FreeBSD は対象外）。

### 2.2 API の形

```go
// Context はプログラム内に 1 個だけ
ctx, ready, err := oto.NewContext(&oto.NewContextOptions{
    SampleRate:   44100,
    ChannelCount: 2,
    Format:       oto.FormatSignedInt16LE,
    BufferSize:   0, // 0 でプラットフォームのデフォルト
})
<-ready

// Player は io.Reader からバイト列を読んで再生する
player := ctx.NewPlayer(myAPUReader)
player.SetBufferSize(bytesFor(50 * time.Millisecond))
player.Play()
```

主要なメソッド:

| メソッド | 用途 |
|---|---|
| `Context.NewPlayer(io.Reader) *Player` | プレイヤーを作る。**1 つの `io.Reader` を複数のプレイヤーで使ってはいけない** |
| `Context.Suspend()` / `Resume()` | OS がアプリを中断したときの対応 |
| `Player.SetBufferSize(int)` | バッファサイズ = レイテンシの制御 |
| `Player.BufferedSize() int` | **現在バッファに溜まっているバイト数。これが同期の鍵**（§2.4） |
| `Player.Play()` / `Pause()` / `SetVolume(float64)` | 再生制御 |
| `Player.Err() error` | エラー取得 |

### 2.3 APU からサンプルを取り出す構造

oto が `io.Reader` を引くモデルなので、**「oto のオーディオスレッドが Read を呼んだときに、必要なサンプル数ぶんエミュレータを進める」**構造にできる。これが `07_timing_and_synchronization.md` §6.1 で選んだ「オーディオ駆動」の実体。

```go
// 概念スケッチ
type audioSource struct {
    emu *emu.Emulator
    mu  sync.Mutex
    buf []int16   // リングバッファ
}

func (a *audioSource) Read(p []byte) (int, error) {
    need := len(p) / 4 // 16 bit ステレオ = 4 バイト/サンプル
    a.mu.Lock()
    defer a.mu.Unlock()
    for a.available() < need {
        a.emu.RunUntilAudioSamples(need)  // エミュレータを進めてサンプルを生成
    }
    return a.drain(p), nil
}
```

ただし注意点がある。

- **oto の Read はオーディオコールバック相当のスレッドから呼ばれる。** ここでエミュレーション全体（PPU も含む）を回すと、GUI スレッドとのデータ共有が難しくなる
- **より安全な構造**: エミュレータは独自のゴルーチンで回し、生成したサンプルをリングバッファに書く。`Read` はリングバッファから読むだけにする。バッファが枯れたら無音（ゼロ）を返す
- エミュレータ側の速度は「リングバッファの充填率」を見て調整する（§2.4）

**採用する構造（`09a` §4.4 の実測で確定）**:

```
[エミュレーションゴルーチン] --サンプル--> [リングバッファ] --Read--> [oto の再生スレッド]
        ^                                        |
        |                                        |
        +-- 高水位に達したら sync.Cond でブロック --+
            （Read が消費したら Broadcast で起こす）
                    ↑ これが唯一のクロック源
        |
        +--フレーム--> [フレームバッファ（ダブルバッファ）] --> [GUI スレッド]
                        （GUI は自分の vsync で pull する）
```

**壁時計のティッカーでエミュレーションを駆動してはいけない。** 60 秒の耐久試験でティッカー駆動は 137 回の音切れを起こし、±0.5% のフィードバック補正を足しても 6 回残った。バックプレッシャ方式は 0 回（`09a` §4.4）。

### 2.4 同期とレイテンシ

目標: **音が途切れず、かつ入力遅延が小さい。**

| 項目 | 値 | 根拠 |
|---|---|---|
| サンプリングレート | 48000 Hz | 現代の OS の標準。リサンプル段が 1 つ減る |
| oto のバッファ | **25 ms** | `09a` §4.2 で 20 ms でも動くことを確認。高水位 2 倍で合計 50 ms に収まる |
| リングの高水位 | **oto バッファの 2 倍（50 ms 相当）** | `09a` §4.4 の D1/D2/D3 比較。等倍だと一瞬の処理落ちが音切れになる |
| リングの容量 | 高水位の 2 倍 | 書き込み側がブロックする前の余地 |
| 合計レイテンシ | **約 50 ms**（3 フレーム相当） | ゲームとして許容できる範囲 |

速度調整の方法:

1. **バックプレッシャ（採用）**: エミュレータはリングが高水位に達したらブロックする。オーディオデバイスが消費した量だけ進む。**補正計算が不要で、CPU 負荷 10 倍でも崩れない**（実測）
2. **フレーム落ち/重複**: 映像側で吸収する。オーディオを主にするので映像側が調整される
3. **±0.5% 動的リサンプル（オプション）**: バックプレッシャではエミュレータ速度がオーディオデバイスの実クロックに従う（実測 +0.055%）。「NES と厳密に同じ速度」を優先する設定のときだけ、この差を動的リサンプルで吸収する

**NES のフレームレートは 60.0988 Hz なので、60.000 Hz のディスプレイとは 1 分あたり約 6 フレームずれる。** オーディオ駆動なら音は正しく、映像が 1 分に 6 回ティアリング/ジャダーする。これを許容するか、映像同期にしてオーディオをリサンプルするかは設定にする。

### 2.5 APU 出力のリサンプリング

APU は CPU クロック（約 1.789773 MHz）ごとに値が変わる。これを 48 kHz に落とす（約 37 分の 1）。

**素朴なデシメーション（37 サンプルおきに 1 個取る）はエイリアシングでノイズになる。** 正しい手順:

1. CPU クロックごとにミキサー出力を計算する（`04_apu.md` §5.1 のルックアップテーブル）
2. **ローパスフィルタをかける**（`04_apu.md` §5.3 の 14 kHz ローパス + 90 Hz / 440 Hz ハイパスがちょうどアンチエイリアシングを兼ねる）
3. 目標レートへダウンサンプルする

実装段階:

- **第 1 段階**: 1 次 IIR フィルタ（ハイパス 2 段 + ローパス 1 段）+ 線形補間。実装が数十行で済み、実機のフィルタ特性にも合っている
- **第 2 段階**（必要なら）: ポリフェーズ FIR による帯域制限リサンプル

> **判断**: 実機自体が緩いアナログフィルタを通しているので、**1 次 IIR + 線形補間で十分に実用的な音質になる。** `apu_mixer` と `volume_tests` の実機録音と比較して評価する（→ `08_test_roms_and_validation.md`）。

## 3. 映像出力

### 3.1 PPU からフレームバッファへ

PPU は 1 ドットずつ「5 bit のパレットインデックス」を生成する（`03_ppu.md` §8）。エミュレータ内部では:

```go
// PPU の出力（1 フレーム = 256×240）
type Frame struct {
    // パレットインデックス（0–63）+ エンファシス 3 bit を含む 0–511 の値として保持する。
    // 色変換は表示直前に行う（パレットを差し替えられるようにするため）
    Pixels [256 * 240]uint16
}
```

**パレットインデックスのまま持ち、RGB 変換は表示直前に行う。** 理由:

- ユーザーがパレットファイル（`.pal`）を差し替えられる（`03_ppu.md` §10.3）
- デバッグウィンドウで「このピクセルのパレットインデックスは何か」を表示できる
- グレースケール / エンファシスの適用をあとから変えられる

### 3.2 拡大表示

| 方式 | 内容 | 用途 |
|---|---|---|
| 整数倍 nearest neighbor | 1x, 2x, 3x, 4x… | **デフォルト。ドット絵がぼけない** |
| アスペクト比補正 | NES の実際のピクセルは正方形でない（NTSC で約 8:7） | オプション。「1 ピクセル = 8:7」にすると実機のブラウン管に近い |
| 線形補間 | ぼかす | 好みで |
| CRT シェーダ / NTSC フィルタ | 走査線、にじみ | 将来。要 GPU シェーダ |

**オーバースキャン**: 実機の TV では上下左右が隠れる。NTSC の「名目上の可視高さ」は 224 スキャンライン（`03_ppu.md` §2）。多くのゲームは画面端にゴミを出すので、**デフォルトで上下 8 px を隠す**のが一般的。設定で 0〜16 px を調整できるようにする。

### 3.3 フレームバッファの受け渡し（スレッド間）

エミュレーションゴルーチンと GUI スレッドは別。**ダブルバッファ + アトミックなスワップ**にする。

```go
// 概念スケッチ
type FrameQueue struct {
    mu       sync.Mutex
    complete *Frame   // 完成済みで GUI がまだ読んでいないフレーム
    working  *Frame   // PPU が今書いているフレーム
    spare    *Frame
}
```

- エミュレータがフレームを完成させたら `complete` に置く（前の `complete` が読まれていなければ**上書きする** = フレーム落ち）
- GUI は描画のたびに `complete` を取り出す
- これにより「エミュレータが GUI を待たない」「GUI がエミュレータを待たない」を両立する

### 3.4 フレームワークごとの描画方法

`09_go_gui_frameworks.md` の選定に依存する。

| フレームワーク | 方法 | 注意点 |
|---|---|---|
| **Fyne（採用）** | `canvas.NewImageFromImage(img)` を `canvas.Image` として持ち、`img.Pix` を書き換えて `Refresh()` | **`ScaleMode` を `canvas.ImageScalePixels`（nearest）にする。** `image.RGBA` を再利用してアロケーションを避ける。**`Refresh()` はダーティ化のみで 0.01 ms、実描画は Fyne の vsync ループが行う**（`09a` §3）。非メインゴルーチンからは **`fyne.Do` 経由が必須**（`09a` §5.1） |
| Ebitengine | `ebiten.Image.WritePixels([]byte)` → `screen.DrawImage` | 最も素直。`DrawImageOptions.Filter = ebiten.FilterNearest` |
| Gio | `paint.NewImageOp(img)` → `op.Add` | `NewImageOp` が毎フレームテクスチャをアップロードする。同じ `image.Image` を使い回すとキャッシュされる可能性があるので注意 |
| Wails v3 | `ImageData` を canvas に `putImageData`、または WebGL テクスチャ | **Go → JS のフレーム転送が最大の課題**（184 KB/フレーム × 60 fps）。IPC ではなくローカル HTTP ストリームや SharedArrayBuffer を検討 |

### 3.5 デバッグビューアの描画

| ビューア | サイズ | 内容 |
|---|---|---|
| パターンテーブル | 128×128 × 2（または 128×256） | 慣習どおり 16×16 タイルのグリッド（`03_ppu.md` §5） |
| ネームテーブル | 512×480 | 4 枚を 2×2 に並べ、現在のスクロール枠を重ねる |
| スプライト（OAM） | 64 個を一覧 + 拡大表示 | 各スプライトのタイル、属性、座標を数値でも出す |
| パレット | 32 エントリ + 64 色の全パレット | クリックで色を変更できるようにする |

いずれも「パレットインデックス → RGB」の同じ変換関数を通す。**エミュレータ本体と同じコードパスを使うこと**（表示が食い違うとデバッグできない）。

## 4. 実装方針のまとめ

| 項目 | 決定 |
|---|---|
| オーディオライブラリ | `github.com/ebitengine/oto/v3` v3.5.1 |
| サンプリングレート | 48000 Hz（設定で 44100 も可） |
| フォーマット | 16 bit 符号付きリトルエンディアン、ステレオ（NES はモノラルだが左右に同じ値を入れる） |
| バッファ | デフォルト 50 ms、設定可 |
| リサンプル | 1 次 IIR フィルタ（実機相当）+ 線形補間。速度調整は ±0.5% の動的リサンプル |
| 同期 | オーディオ駆動（`07_timing_and_synchronization.md` §6.1） |
| フレームバッファ | パレットインデックス（uint16）で保持、表示直前に RGB 変換 |
| 拡大 | 整数倍 nearest がデフォルト。アスペクト比補正はオプション |
| オーバースキャン | デフォルトで上下 8 px を隠す。0〜16 px で設定可 |
| スレッド間 | ダブルバッファ + フレーム落ち許容 |

### 4.1 実測で確認済みの事項（2026-09-21）

`09a_fyne_performance_spike.md` のスパイクにより、本書の設計は次のとおり裏付けられた。

| 本書の設計 | 実測結果 |
|---|---|
| 60 fps で拡大描画できる | **実ペイント 60.00 fps（768×720）、59.83 fps（1536×1440）。拡大率による劣化なし** |
| フレームバッファ生成のコストは無視できる | **0.082 ms/frame**（60 fps の予算 16.67 ms の 0.5%） |
| 50 ms バッファで音が途切れない | **20 ms でもアンダーラン 0** |
| 充填率フィードバックによる動的リサンプルが必要（§2.4） | **必要であることが実証された。** 固定レート生成（1 フレーム = 800 サンプル）は 47,830〜48,256 /s とドリフトし、放置するとアンダーランする |

加えて、設計を変更すべき事実が 2 つ判明した。

1. **`oto.NewContext` はプロセスで 1 回しか呼べない**（2 回目は `oto: context is already created`）。アプリ起動時に 1 個だけ作る。サンプリングレートの変更は `Context` の作り直しが必要なので、**設定変更時は再起動を求める**（またはバッファサイズ変更のみに限定する）
2. **再生開始前のプライミングが必須。** 埋めずに `Play()` すると起動時に 100 ms の無音が入る（実測）

また、Fyne 側の重要な制約:

3. **`canvas.*.Refresh()` は非同期**（ダーティ化のみ、0.01 ms）。「Refresh したから画面に出た」とは限らない。**スクリーンショットとテスト用のフレームハッシュは、画面キャプチャではなく自前のフレームバッファから取る**
4. **Fyne v2.8 では、メインゴルーチン以外からの UI 操作は `fyne.Do` / `fyne.DoAndWait` 経由が必須**（次のメジャーリリースで安全網が外れる）。エミュレータは独自ゴルーチンで回すので、UI 更新は 1 箇所のヘルパに集約する

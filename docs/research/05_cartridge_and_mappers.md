# カートリッジ・ROM フォーマット・マッパー調査

> 調査日: 2026-09-20 / 一次情報源: NESdev Wiki（https://www.nesdev.org/wiki/）
> 本書はハードウェアと公開仕様の事実をまとめたものであり、既存エミュレータの実装は参照していない（クリーンルーム）。

## 1. 背景・目的

NES のカートリッジは「バンク切り替え回路」「追加 RAM」「IRQ 生成」「拡張音源」などを内蔵しており、これらをまとめて**マッパー**と呼ぶ。ROM ファイル（.nes）のヘッダにマッパー番号が入っている。

本書は次の判断に使う。

- ROM ローダを iNES / NES 2.0 のどちらまで対応させるか
- マッパーのインタフェース（Go の interface）をどう設計するか
- 最初にどのマッパーを実装するか（カバレッジの観点）
- セーブデータ（バッテリーバックアップ）をどう永続化するか

結論: **NES 2.0 まで対応し、マッパー 0 / 1 / 2 / 3 / 4 / 7 / 66 を第 1 弾として実装する。** 理由は §7。

## 2. .nes ファイルフォーマット（iNES）

Marat Fayzullin の iNES エミュレータが作ったデファクト標準。後に NES 2.0 で拡張された。

ファイル構造（この順）:

1. ヘッダ（16 バイト）
2. トレーナー（存在すれば 0 または 512 バイト）
3. PRG-ROM データ（16384 × x バイト）
4. CHR-ROM データ（存在すれば 8192 × y バイト）
5. PlayChoice INST-ROM（存在すれば 0 または 8192 バイト）
6. PlayChoice PROM（16 バイト Data + 16 バイト CounterOut。しばしば欠けている）

一部の ROM イメージはファイル末尾に 128 バイト（ときに 127 バイト）のタイトルを持つ。

### 2.1 ヘッダ

| バイト | 内容 |
|---|---|
| 0–3 | 定数 `$4E $45 $53 $1A`（ASCII "NES" + MS-DOS EOF） |
| 4 | PRG-ROM サイズ（16 KiB 単位） |
| 5 | CHR-ROM サイズ（8 KiB 単位。0 なら CHR-RAM を使う基板） |
| 6 | Flags 6 — マッパー下位ニブル、ミラーリング、バッテリー、トレーナー |
| 7 | Flags 7 — マッパー上位ニブル、VS/PlayChoice、NES 2.0 識別子 |
| 8 | Flags 8 — PRG-RAM サイズ（ほとんど使われない拡張） |
| 9 | Flags 9 — TV システム（ほとんど使われない拡張） |
| 10 | Flags 10 — TV システム、PRG-RAM の有無（非公式） |
| 11–15 | 未使用パディング（0 埋めが正しいが、リッパーが名前を書いていることがある） |

**Flags 6**:

```
 76543210
 ||||||||
 |||||||+- ネームテーブル配置: 0 = 垂直配置（"水平ミラーリング"）CIRAM A10 = PPU A11
 |||||||                       1 = 水平配置（"垂直ミラーリング"）CIRAM A10 = PPU A10
 ||||||+-- 1: バッテリーバックアップ PRG-RAM（$6000–$7FFF）等の不揮発メモリを持つ
 |||||+--- 1: $7000–$71FF に置く 512 バイトのトレーナーが PRG データの前にある
 ||||+---- 1: 代替ネームテーブルレイアウト（意味はマッパー依存）
 ++++----- マッパー番号の下位ニブル
```

**Flags 7**:

```
 76543210
 ||||||||
 |||||||+- VS Unisystem
 ||||||+-- PlayChoice-10（CHR データの後に 8 KiB のヒント画面データ）
 ||||++--- 2 に等しければ Flags 8–15 は NES 2.0 形式
 ++++----- マッパー番号の上位ニブル
```

**Flags 8**: PRG-RAM サイズ（8 KiB 単位。0 は互換性のため 8 KiB と解釈）。

**Flags 9**: bit 0 = TV システム（0: NTSC, 1: PAL）。残りは予約。**ほぼどのエミュレータも見ていない**（ROM 側がほぼ使っていないため）。

**Flags 10**（非公式）:

```
 76543210
   ||  ||
   ||  ++- TV システム（0: NTSC, 2: PAL, 1/3: 両対応）
   |+----- PRG RAM（$6000–$7FFF）（0: あり, 1: なし）
   +------ 0: バス競合なし, 1: バス競合あり
```

### 2.2 ネームテーブル配置ビットの扱い（重要な落とし穴）

- ハードワイヤードな基板では bit 0 が CIRAM A10 の接続先（PPU A10 = 水平配置 / PPU A11 = 垂直配置）を指定する
- **MMC1 / MMC3 / AxROM などマッパーがミラーリングを制御する場合、bit 0 は無視される**
- bit 3（"代替ネームテーブルレイアウト"）の意味はマッパー依存で、現在の用途と歴史的（非推奨の）用途がある
  - 4 画面バリアントの指定: MMC3（Rad Racer 2）、マッパー 206（Gauntlet）
  - UNROM 512 は `%....1..0` で 1 画面、`%....1..1` で 4 画面
  - マッパー 218（Magic Floor）は 4 通りの CIRAM 構成を持つ
  - 歴史的に「bit 3 は常に 4 画面を意味する」と信じられていたため、**bit 3 が立った ROM でゲームがミラーリング制御レジスタに書くと壊れるエミュレータが多い**

> Shogun Emulator の方針: ミラーリングは「マッパーが決める」を基本にする。ハードワイヤードなマッパーだけがヘッダの bit 0 を初期値として使う。bit 3 は「マッパーが 4 画面をサポートしていれば 4 画面」とし、それ以外では**警告ログを出して無視する**。

### 2.3 トレーナー

初期の RAM カートリッジ（マッパー ASIC を模倣できず CHR-RAM が 32 KiB しかないもの）や、DOS の Nesticle 向けに、マッパーレジスタ変換や CHR-RAM キャッシュのコードが入っている。**オリジナルの ROM カートリッジの無改変ダンプには存在しない。**

### 2.4 ヘッダのゴミ問題（"DiskDude!"）

古い iNES はバイト 7–15 を無視していたため、ROM 管理ツールがここにメッセージを書いた。よくあるのが `"DiskDude!"` で、これがあるとマッパー番号に 64 が加算されてしまう。

**経験則**: 最後の 4 バイトがすべて 0 でなく、かつヘッダが NES 2.0 でない場合、エミュレータはマッパー番号の上位 4 bit をマスクするか、ROM の読み込みを拒否すべき。

### 2.5 フォーマット判別手順（Wiki 推奨）

1. バイト 7 AND $0C == $08 で、バイト 9 を考慮したサイズが実ファイルサイズを超えないなら **NES 2.0**
2. バイト 7 AND $0C == $04 なら **archaic iNES**
3. バイト 7 AND $0C == $00 で、バイト 12–15 がすべて 0 なら **iNES**
4. それ以外は **iNES 0.7 または archaic iNES**

世代比較:

| 項目 | archaic iNES | iNES | NES 2.0 |
|---|---|---|---|
| バイト 7 | 未使用 | マッパー上位ニブル、Vs. | + NES 2.0 署名、PlayChoice |
| バイト 8 | 未使用 | PRG-RAM 総サイズ（線形） | マッパー最上位ニブル、サブマッパー |
| バイト 9 | 未使用 | TV システム | ROM サイズ上位ビット |
| バイト 10 | 未使用 | 未使用 | PRG-RAM サイズ（対数、バッテリー有無別） |
| バイト 11 | 未使用 | 未使用 | VRAM サイズ（対数、バッテリー有無別） |
| バイト 12 | 未使用 | 未使用 | TV システム |
| バイト 13 | 未使用 | 未使用 | Vs. PPU バリアント |
| バイト 14 | 未使用 | 未使用 | その他 ROM |
| バイト 15 | 未使用 | 未使用 | デフォルト拡張機器 |
| 対応マッパー | 0–15 | 0–255 | 0–4095 |

## 3. NES 2.0

iNES の曖昧さを解消するために kevtris が作り、NESdev コミュニティが保守している拡張。2010 年代から広く採用された。**後方互換**（NES 2.0 ヘッダの ROM は NES 2.0 非対応エミュレータでも、NES 2.0 専用機能を要求しなければ動く）。

判別:

```go
iNESFormat := h[0]=='N' && h[1]=='E' && h[2]=='S' && h[3]==0x1A
NES20Format := iNESFormat && (h[7]&0x0C) == 0x08
```

### 3.2 ROM サイズの指数-乗数表記

PRG-ROM サイズは「バイト 4（LSB）+ バイト 9 の bit 0–3（MSB）」の 12 bit。

- MSB ニブルが $0–$E: 単純に 16 KiB 単位のサイズ（$000–$EFF = 0〜62,898,176 バイト）
- MSB ニブルが $F: **指数-乗数表記**

```
 1111 EEEE EEMM
      |||| ||++- 乗数。実値は MM*2+1（1, 3, 5, 7）
      ++++-++--- 指数（2^E）、0–63

実サイズ = 2^E × (MM*2+1) バイト
```

CHR-ROM も同様（バイト 5 が LSB、バイト 9 の bit 4–7 が MSB）。

指数-乗数表記は、単純表記で正しく表せないサイズのときだけ使ってよい。どちらでも表せない奇妙なサイズのデータは表せるサイズまでパディングする。

> 実装メモ: Galaxian（NROM で 8 KiB PRG-ROM）がこの表記の代表例。iNES では 16 KiB 単位しか表せないので、iNES ダンプはすべてオーバーダンプになっている。

### 3.3 その他 ROM 領域

CHR-ROM 領域の後、ファイル末尾まで。サイズはヘッダに明示されず、「ファイル全体 − 16 − トレーナー − PRG-ROM − CHR-ROM」で求める。

現在定義されている用途:

- PlayChoice 10: 8 KiB INST ROM + 16 バイト PROM Data + 16 バイト PROM Counter Out（計 3 個）
- VT369: NES-on-a-chip に埋め込まれた 4 KiB ROM
- iNES マッパー 86 サブマッパー 1: 音声データ
- NES 2.0 マッパー 355: プロテクト用 PIC16C54 マイコンの内蔵 ROM
- NES 2.0 マッパー 561 / 562: iNES の慣習（512 バイト、$7000）に合わないトレーナー

## 4. マッパーの一般的な機能

カートリッジ基板が行う処理:

- **CHR / PRG チップを NES のアドレス空間にマッピング**
  - （多くの場合）**バンク切り替え**: アドレス空間より大きいデータを扱う
  - （多くの場合）バッテリーバックアップ RAM または EEPROM でセーブデータを保持
- **（常に）ネームテーブルミラーリング**: 本体は CIRAM 2 枚ぶんしかないが 4 枚ぶんアドレスされる
  - （まれに）カートリッジ側の CHR-RAM/ROM でネームテーブル CIRAM を補完/置換（4 画面）
- （よくある）**割り込みの生成**。特に PPU が特定のスキャンラインに達したときのタイミング
- （まれに）追加音源。Famicom はカートリッジポート経由で音を混ぜられた。NES は改造しないと不可
- （まれに）属性テーブルのマッピングを変えて細かい属性制御を提供（MMC5）
- （まれに）高速乗算などの雑機能

分類:

- **ディスクリートロジック**（74 シリーズ IC の組み合わせ）。一部は**バス競合**の影響を受ける
- **ASIC ベース**。Nintendo は MMC（Memory Management Controller）、Konami は VRC（Virtual ROM Controller）と呼ぶ

命名:

- ディスクリートロジックは基板名で呼ぶ（"UNROM"）
- ASIC は ASIC 名で呼ぶ（"MMC1", "FME-7"）。ただし ASIC を変わった使い方をする基板は基板名（"TQROM", "TLSROM", "NES-EVENT"）
- エミュレーションコミュニティは iNES 由来の番号で呼ぶ（"mapper 002"）

### 4.1 バス競合（bus conflict）

ディスクリートロジックマッパーでは、CPU が $8000–$FFFF に書き込むとき、PRG-ROM も同じバスに値を出してしまうことがある。結果として**書き込まれる実効値は「書いた値 AND その番地の ROM の内容」**になる（AND 型バス競合）。

- NES 2.0 のサブマッパーでバス競合の有無を明示できる（例: UxROM・CNROM・AxROM のサブマッパー 0 = 不明、1 = 競合なし、2 = AND 型）
- オリジナルの UxROM 基板はバス競合の影響を受け、該当ゲームはソフト側で回避している
- **AxROM は「サブマッパー 0 なら競合をエミュレートすべきでない」**とされている（AOROM の一部は CE ピンの工夫で競合を防いでいるため、競合を有効にするとグリッチする）

> 方針: デフォルトはバス競合なし。NES 2.0 のサブマッパーで「AND 型」と明示されている場合だけ有効にする。設定で強制的に on/off できるようにする。

### 4.2 ROM 末尾を超えるバンク

**ほとんどのマッパーで、PRG/CHR ROM の末尾を超えるバンクは前のバンクのミラーになる。** UNROM のバンク 8–15 はバンク 0–7 のミラー。2 の冪でない ROM サイズではもっと複雑になる。

実装: `bankIndex % bankCount` でよい（バンク数が 2 の冪の場合はマスク）。2 の冪でない場合の正確な挙動はマッパー依存なので、当面はモジュロで実装しログを残す。

## 5. 基本マッパーの仕様

### 5.1 マッパー 0: NROM

基板: NES-NROM-128 / NES-NROM-256（128/256 は**キロビット**）、HROM, RROM, RTROM, SROM, STROM。

| 領域 | 内容 |
|---|---|
| CPU $6000–$7FFF | バンクなし PRG-RAM（Family BASIC のみ。2 KiB または 4 KiB をミラー） |
| CPU $8000–$BFFF | PRG-ROM の最初の 16 KiB |
| CPU $C000–$FFFF | PRG-ROM の最後の 16 KiB（NROM-256）または $8000–$BFFF のミラー（NROM-128） |
| PPU $0000–$1FFF | 8 KiB CHR-ROM |

- すべてのバンクは固定。**レジスタなし**
- ミラーリングはハンダパッド固定（H または V）
- バス競合はあるが、マッピング機能がないのでソフトから見れば無関係
- Family BASIC は 2 KiB（V3 は 4 KiB）の PRG-RAM をバッテリーバックアップで持つ。多くのエミュレータは battery フラグが立っていれば 8 KiB を $6000–$7FFF にマップする
- 非ライセンス品やホームブリューが mapper 0 + 8 KiB CHR-RAM を使うことがある（公式基板では配線変更が必要）。**多くのエミュレータは正しく扱う**

### 5.2 マッパー 2: UxROM

基板: NES-UNROM, NES-UOROM, HVC-UN1ROM。例: Mega Man, Castlevania, Contra, Duck Tales, Metal Gear。

| 領域 | 内容 |
|---|---|
| CPU $8000–$BFFF | 16 KiB 切り替え可能 PRG-ROM バンク |
| CPU $C000–$FFFF | 16 KiB PRG-ROM バンク、**最後のバンクに固定** |
| PPU $0000–$1FFF | 8 KiB CHR-RAM（CHR-ROM は持たない） |

バンク選択レジスタ（$8000–$FFFF への書き込み）:

```
 7  bit  0
 ---- ----
 xxxx pPPP
      ||||
      ++++- CPU $8000–$BFFF の 16 KiB PRG-ROM バンクを選択
            （UNROM は bit 2–0、UOROM は bit 3–0 を使う）
```

- エミュレータ実装は通常「バス競合なしの完全な 8 bit バンク選択レジスタ」として扱う。これにより互換基板にも使える
- 8 bit 全部を使って 4 MiB PRG-ROM にするには NES 2.0 ヘッダが必要（iNES では実質 2 MiB まで）
- サブマッパー: 0 = バス競合不明、1 = 競合なし、2 = AND 型競合
- 関連: マッパー 94（UN1ROM、Senjou no Ookami のみ）、マッパー 180（Crazy Climber。$8000 側が固定で $C000 側が切り替わる）

### 5.3 マッパー 3: CNROM

| 領域 | 内容 |
|---|---|
| CPU $6000–$7FFF | 2 KiB PRG-RAM を 3 回ミラー（Hayauchi Super Igo のみ） |
| CPU $8000–$FFFF | 32 KiB バンクなし PRG-ROM |
| PPU $0000–$1FFF | 32 KiB CHR-ROM への 8 KiB 切り替えウィンドウ |
| ミラーリング | 固定（ハンダパッドで H/V） |

バンク選択（$8000–$FFFF への書き込み）:

```
通常（最大 32 KiB CHR-ROM）
 D~[..DC ..BA]
      ||   ||
      ||   ++- CHR A14..A13（8 KiB バンク）
      |+------ Diode 2 への出力
      +------- Diode 1 への出力

オーバーサイズ（最大 128 KiB）
 D~[.... DCBA]
```

**オリジナルの CNROM 基板は常に AND 型バス競合の影響を受ける。** サブマッパーで実際にエミュレートすべきかどうかを示す。

関連: マッパー 185 は「CHR-ROM が 8 KiB しかなく、正しいバンク番号を選ばないと CHR-ROM が無効になる」コピープロテクト用途。サブマッパー 4–7 で CS1/CS2 の正解値を示す。

### 5.4 マッパー 7: AxROM

基板: NES-AMROM, NES-ANROM, NES-AN1ROM, NES-AOROM。

| 項目 | 内容 |
|---|---|
| PRG-ROM | 最大 256 KiB、32 KiB バンク |
| PRG-RAM | なし |
| CHR | 8 KiB RAM、バンク切り替えなし |
| ミラーリング | **1 画面、マッパー選択可能** |
| バス競合 | AMROM / AOROM のみ |

バンク選択（$8000–$FFFF）:

```
 7  bit  0
 ---- ----
 xxxM xPPP
    |  |||
    |  +++- CPU $8000–$FFFF の 32 KiB PRG-ROM バンクを選択
    +------ 4 つのネームテーブルすべてに使う 1 KiB VRAM ページを選択
```

- サブマッパー 0 = バス競合の挙動未定義だが**エミュレータは競合をエミュレートすべきでない**、1 = 競合なし、2 = AND 型
- 一部のエミュレータは bit 3 で最大 512 KiB のオーバーサイズ AxROM をサポートする
- 関連: BNROM は AMROM と同じだが H/V 固定ミラーリング

### 5.5 マッパー 66: GxROM

基板: NES-GNROM, NES-MHROM。例: Doraemon, Dragon Power, Gumshoe, Super Mario Bros. + Duck Hunt（MHROM）。

| 領域 | 内容 |
|---|---|
| CPU $8000–$FFFF | 32 KiB 切り替え可能 PRG-ROM バンク |
| PPU $0000–$1FFF | 8 KiB 切り替え可能 CHR-ROM バンク |

バンク選択（$8000–$FFFF）:

```
 7  bit  0
 ---- ----
 xxPP xxCC
   ||   ||
   ||   ++- 8 KiB CHR-ROM バンクを選択
   ++------ 32 KiB PRG-ROM バンクを選択
```

バス競合あり。Jaleco のマッパー 140 はレジスタの位置が違うだけでよく似ている（混同しやすい）。

### 5.6 マッパー 1: MMC1（SxROM）

1987 年 4 月に登場した Nintendo の ASIC。NesCartDB に登録された 390 タイトルで使われている（Wiki の infobox 値）。

| 領域 | 内容 |
|---|---|
| CPU $6000–$7FFF | 8 KiB PRG-RAM バンク（オプション） |
| CPU $8000–$BFFF | 16 KiB PRG-ROM バンク（切り替えまたは先頭固定） |
| CPU $C000–$FFFF | 16 KiB PRG-ROM バンク（末尾固定または切り替え） |
| PPU $0000–$0FFF | 4 KiB 切り替え可能 CHR バンク |
| PPU $1000–$1FFF | 4 KiB 切り替え可能 CHR バンク |

最大: PRG-ROM 256 KiB（512 KiB）、PRG-RAM 32 KiB、CHR 128 KiB。バス競合なし。

#### シリアルインタフェース（MMC1 の最大の特徴）

ピン数を減らすため **MMC1 はシリアルポートで設定する。** CPU $8000–$FFFF が共通のシフトレジスタにつながっている。

- **bit 7 がセットされた値（$80–$FF）を $8000–$FFFF のどこかに書くと、シフトレジスタが初期状態にクリアされ、さらに Control レジスタに `Control OR $0C` が書かれる**（= $C000–$FFFF が最後のバンクに固定される）
- レジスタの値を変えるには、bit 7 をクリアし bit 0 に値の 1 bit を入れた書き込みを 5 回行う（**値の下位ビットから**）
- 最初の 4 回は bit 0 をシフトレジスタにシフトインするだけ
- **5 回目の書き込みで、bit 0 とシフトレジスタの内容が、アドレスの bit 14–13 で選ばれた内部レジスタにコピーされ、シフトレジスタがクリアされる**
- **アドレスが意味を持つのは 5 回目だけ**。しかもそのときも bit 14–13 しか見ない（マッパーは下位アドレスビットを見ていない）

```asm
; A の値を切り替え可能 PRG-ROM バンクに設定する
setPRGBank:      ; A          SR
  sta $E000      ; 000edcba → a1000
  lsr a
  sta $E000      ; 0000edcb → ba100
  lsr a
  sta $E000      ; 00000edc → cba10
  lsr a
  sta $E000      ; 000000ed → dcba1   ← 1 が最後の位置にシフトされて SR が満杯
  lsr a
  sta $E000      ; 0000000e   dcba1 → edcba（レジスタへコピーして SR をクリア）
  rts
```

**連続サイクル書き込み（consecutive-cycle writes）**: シリアルポートが連続するサイクルで書かれた場合、**最初以外の書き込みは無視される。** 実際には RMW 命令（元の値を書いてから変更後の値を書く）でのみ起こる。

リセットの慣習:

```asm
resetMapper:
  lda #$80
  sta $8000
  rts
```

または 2 バイト節約のため負の値に INC する（INC は 2 回書き込むので、**両方の書き込みで負になる値**を対象にすべき。たとえば INC の opcode $EE 自身）:

```asm
resetMapper:
  inc resetMapper   ; $EE → $EF、どちらも bit 7 が立っている
  rts
```

一部のゲームは 4 個のレジスタすべてにリセット書き込みをする（開発基板のディスクリート実装が各レジスタごとに別のシフトレジスタを持っていたためと推測される）。

#### 内部レジスタ

**Load レジスタ（$8000–$FFFF）**:

```
 7  bit  0
 ---- ----
 Rxxx xxxD
 |       |
 |       +- シフトレジスタにシフトインするデータビット（LSB first）
 +--------- 立てて書くとシフトレジスタをリセットし、Control に (Control OR $0C) を書く
```

**Control（内部、$8000–$9FFF）**:

```
 4bit0
 -----
 CPPMM
 |||||
 |||++- ネームテーブル配置
 |||     0: 1 画面、スクリーン A
 |||     1: 1 画面、スクリーン B
 |||     2: 水平配置（"垂直ミラーリング"、PPU A10）
 |||     3: 垂直配置（"水平ミラーリング"、PPU A11）
 |++--- PRG-ROM バンクモード
 |       0, 1: $8000 で 32 KiB 切り替え（バンク番号の下位ビットを無視）
 |       2: 先頭バンクを $8000 に固定し、$C000 の 16 KiB を切り替え
 |       3: 最後のバンクを $C000 に固定し、$8000 の 16 KiB を切り替え
 +----- CHR-ROM バンクモード（0: 8 KiB 単位で切り替え, 1: 4 KiB を 2 つ独立に切り替え）
```

> 電源投入時の状態: 「すべての MMC1 が最後のバンクで起動する（PRG バンクモード 3）」というテスト結果もあるが、別のテストではこれは不安定だという結果も出ている。多くの市販ゲームは 32 KiB ごとにリセットベクタを持つが 16 KiB ごとには持たないので、モード 2 でランダムに起動することはなさそう。

**CHR バンク 0（内部、$A000–$BFFF）**:

```
 4bit0
 -----
 CCCCC
 +++++- PPU $0000 の 4 KiB または 8 KiB CHR バンクを選択（8 KiB モードでは下位ビット無視）
```

**CHR バンク 1（内部、$C000–$DFFF）**: PPU $1000 の 4 KiB CHR バンク（8 KiB モードでは無視）。

**PRG バンク（内部、$E000–$FFFF）**:

```
 4bit0
 -----
 RPPPP
 |||||
 |++++- 16 KiB PRG-ROM バンクを選択（32 KiB モードでは下位ビット無視）
 +----- MMC1A: 0 = 固定バンクが A17..A14 に影響 / 1 = 固定バンクは A16..A14 のみに影響し、
                bit 3 が $8000–$FFFF 全域で A17 を直接制御
        MMC1B: 0 = PRG-RAM 有効 / 1 = PRG-RAM 無効
```

上位ビットは PRG-ROM バンクを選ばないので、このレジスタでアドレスできるのは 256 KiB まで。512 KiB は CHR バンキング側のラインを再利用して実現される。

CHR が 8 KiB（ROM でも RAM でも）のカートリッジでは、下位ビットだけを使う（バンク番号が 1 と AND される）。

#### SxROM の配線バリアント

| 基板 | 違い |
|---|---|
| SEROM / SHROM / SH1ROM | 32 KiB PRG-ROM 用。PRG A14 を MMC1 につながず NES に直結。**$E000 レジスタは完全に無機能**で、32 KiB 全体がバンクなしで $8000–$FFFF に現れる。互換性のためエミュレータは電源投入時に PRG バンク 0 に切り替えてもよい |
| SNROM | CHR が 8 KiB のみ。**CHR バンク選択の上位ライン（CHR A16 = バンク番号の bit 4）を PRG-RAM の追加チップイネーブルとして使う**（0: 有効, 1: オープンバス） |

iNES マッパー 155 は MMC1A リビジョン、マッパー 1 は MMC1B（またはリビジョン不明）。サブマッパー 5 = SEROM/SHROM/SH1ROM、6 = Famicom Network System の 2ME、7 = Kaiser KS-7058。マッパー 105 は NES-EVENT 基板。

> NES 2.0 なしの場合、PRG-RAM サイズは仮定するしかない。**32 KiB にしておけば既知の全タイトルと互換。**

### 5.7 マッパー 4: MMC3（TxROM）

1988 年第 4 四半期に登場。NesCartDB 登録タイトル数で MMC1 に次ぐ（実質的に MMC1 と並んで最多）。

| 領域 | 内容 |
|---|---|
| CPU $6000–$7FFF | 8 KiB PRG-RAM バンク（オプション） |
| CPU $8000–$9FFF（または $C000–$DFFF） | 8 KiB 切り替え可能 PRG-ROM バンク |
| CPU $A000–$BFFF | 8 KiB 切り替え可能 PRG-ROM バンク |
| CPU $C000–$DFFF（または $8000–$9FFF） | 8 KiB PRG-ROM バンク、**最後から 2 番目**に固定 |
| CPU $E000–$FFFF | 8 KiB PRG-ROM バンク、**最後**に固定 |
| PPU $0000–$07FF（または $1000–$17FF） | 2 KiB 切り替え可能 CHR バンク |
| PPU $0800–$0FFF（または $1800–$1FFF） | 2 KiB 切り替え可能 CHR バンク |
| PPU $1000–$13FF …（4 本） | 1 KiB 切り替え可能 CHR バンク × 4 |

レジスタは 4 対（$8000–$9FFF, $A000–$BFFF, $C000–$DFFF, $E000–$FFFF）。**偶数アドレスが下位レジスタ、奇数アドレスが上位レジスタ。** すべて書き込み専用。

機能的には 2 つの独立ユニット:

- メモリマッピング: $8000, $8001, $A000, $A001
- スキャンラインカウント: $C000, $C001, $E000, $E001

**Bank select（$8000–$9FFE、偶数）**:

```
 7  bit  0
 ---- ----
 CPMx xRRR
 |||   |||
 |||   +++- 次に Bank Data に書くときに更新するバンクレジスタ
 |||         000: R0 → PPU $0000–$07FF（または $1000–$17FF）の 2 KiB CHR
 |||         001: R1 → PPU $0800–$0FFF（または $1800–$1FFF）の 2 KiB CHR
 |||         010: R2 → PPU $1000–$13FF（または $0000–$03FF）の 1 KiB CHR
 |||         011: R3 → PPU $1400–$17FF（または $0400–$07FF）の 1 KiB CHR
 |||         100: R4 → PPU $1800–$1BFF（または $0800–$0BFF）の 1 KiB CHR
 |||         101: R5 → PPU $1C00–$1FFF（または $0C00–$0FFF）の 1 KiB CHR
 |||         110: R6 → $8000–$9FFF（または $C000–$DFFF）の 8 KiB PRG
 |||         111: R7 → $A000–$BFFF の 8 KiB PRG
 ||+------- MMC3 では無機能（MMC6 で使う）
 |+-------- PRG-ROM バンクモード
 |           0: $8000–$9FFF 可変、$C000–$DFFF が最後から 2 番目に固定
 |           1: $C000–$DFFF 可変、$8000–$9FFF が最後から 2 番目に固定
 +--------- CHR A12 反転
             0: $0000–$0FFF に 2 KiB × 2、$1000–$1FFF に 1 KiB × 4
             1: $1000–$1FFF に 2 KiB × 2、$0000–$0FFF に 1 KiB × 4
```

CHR バンクマップ:

| PPU バンク | $8000.D7 = 0 | $8000.D7 = 1 |
|---|---|---|
| $0000–$03FF | R0 | R2 |
| $0400–$07FF | R0 | R3 |
| $0800–$0BFF | R1 | R4 |
| $0C00–$0FFF | R1 | R5 |
| $1000–$13FF | R2 | R0 |
| $1400–$17FF | R3 | R0 |
| $1800–$1BFF | R4 | R1 |
| $1C00–$1FFF | R5 | R1 |

2 KiB バンクは偶数バンクしか選べない（最下位ビット無視）。

PRG バンクマップ:

| CPU バンク | $8000.D6 = 0 | $8000.D6 = 1 |
|---|---|---|
| $8000–$9FFF | R6 | (−2) |
| $A000–$BFFF | R7 | R7 |
| $C000–$DFFF | (−2) | R6 |
| $E000–$FFFF | (−1) | (−1) |

(−1) = 最後のバンク、(−2) = 最後から 2 番目。

**R6 / R7 / $8000 の値は電源投入時不定なので、リセットベクタは $E000–$FFFF を指していなければならない。**

**Bank data（$8001–$9FFF、奇数）**: 新しいバンク値。R6/R7 は上位 2 bit を無視（MMC3 の PRG アドレスラインは 6 本）。R0/R1 は最下位ビットを無視。

**Nametable arrangement（$A000–$BFFE、偶数）**: bit 0 = 0 で水平（A10）、1 で垂直（A11）。4 画面 VRAM ハードワイヤのカートリッジでは無効。

**PRG RAM protect（$A001–$BFFF、奇数）**:

```
 7  bit  0
 ---- ----
 RWxx xxxx
 ||
 |+-------- 書き込み保護（0: 許可, 1: 拒否）
 +--------- PRG RAM チップイネーブル（0: 無効, 1: 有効）
```

bit 7 で無効化すると PRG RAM 領域の読み出しはオープンバスを返す。**多くのエミュレータは MMC6 との非互換を避けるためこれを実装しない。**

**IRQ latch（$C000–$DFFE、偶数）**: IRQ カウンタのリロード値。カウンタが 0 のとき（または $C001 でリロードが要求されたとき）、**次の PPU アドレス立ち上がりエッジ**（おそらく現在のスキャンラインの PPU サイクル 260）でこの値がコピーされる。

**IRQ reload（$C001–$DFFF、奇数）**: 何を書いても IRQ カウンタが即座にクリアされ、次の立ち上がりエッジでリロードされる。

**IRQ disable（$E000–$FFFE、偶数）**: MMC3 の割り込みを無効化し、pending な割り込みを acknowledge する。

**IRQ enable（$E001–$FFFF、奇数）**: MMC3 の割り込みを有効化する。

#### MMC3 の IRQ の詳細（実装の難所）

**スキャンラインカウンタは完全に PPU A12 に基づく。** M2 の立ち下がり 3 回ぶん low が続いた後の立ち上がりエッジでトリガする（ノイズフィルタ）。

原理: レンダリング有効時、PPU はドット 0–255 と 320–340 でネームテーブルと BG パターンをフェッチし、ドット 256–319 でスプライトパターンをフェッチする（スプライトが見えていなくても）。

- BG が左パターンテーブル（$0000）、スプライトが右（$1000）を使う場合、フィルタされた A12 は BG フェッチ中は low、スプライトフェッチ中は high になり、**1 スキャンラインにちょうど 1 回、1 フレームに 241 回振動する**
- $2006/$2007 で VBlank 中に PPU $1000–$1FFF にアクセスすると余計に振動する（MMC3 + CHR-RAM のゲームは非常に少ないので稀）

カウンタ動作:

- IRQ がクロックされたとき（フィルタ済み A12 の 0→1）、カウンタ値をチェックする。0 またはリロードフラグが true なら $C000 のラッチ値をリロード、そうでなければデクリメント
- IRQ カウンタが 0 で IRQ が有効なら IRQ をトリガする
- **「代替リビジョン」は 1→0 の遷移をチェックする**（デクリメントでもリロードでも）

PPU A12 に関する注意:

| 状況 | クロックされるタイミング |
|---|---|
| 8×8 スプライト、BG = $0000、スプライト = $1000 | 対象スキャンラインの可視部分が終わった直後、**PPU サイクル 260** |
| 8×8 スプライト、BG = $1000、スプライト = $0000 | 前のスキャンラインの **PPU サイクル 324**。ただしプリレンダー行が 1 フレームおきにカウンタを 2 回デクリメントするので IRQ が 1 行ぶれる（Wario's Woods で見える） |
| 8×16 スプライト | **PPU A12 を明示的に追跡する必要がある。** クロック回数とタイミングは各スキャンラインのスプライト構成に依存する。特定の組み合わせでは最大 4 回デクリメントされたり、IRQ が 8 ピクセルの倍数ぶん遅れたり早まったりする |

重要な性質:

- **スキャンラインカウンタは止められない。** PPU バス上の A12 がトグルする限りデクリメントとリロードを続ける
- **カウンタへの直接アクセスはない。** できるのは「リロード値を更新して即座にリロードを要求する」だけ
- $E000 への書き込みは IRQ 生成を止めるだけで、カウンタは走り続ける
- $C000 への書き込みはカウンタの値を即座に変えない。リロード時にだけ使われる
- **IRQ 間のスキャンライン数は N+1**（N = $C000 に書いた値）。1（Sharp MMC3B, MMC3C）または 2（MMC3A, 非 Sharp MMC3B）から 256 スキャンラインまで
- **BG とスプライトで異なるパターンテーブルを使っていないとカウンタは正しく動かない**
- $2006 への書き込みでもクロックされうる（レンダリング中かどうかに関係なく）

**$C000 = $00 のときの挙動差（リビジョン差）**:

| 製造元 | 挙動 | 通称 |
|---|---|---|
| NEC 製 MMC3 | $C000 = $00 のとき IRQ を 1 回だけ生成。カウンタが 0 に**デクリメントされた**ときに IRQ を出す。$C000 が $00 のまま $C001 に書くともう 1 回生成される | "alternate" / "old" |
| Sharp 製 MMC3 | $C000 = $00 のとき毎スキャンライン IRQ を生成。カウンタが 0 に**等しい**ときに IRQ を出す | "normal" / "new" |

同じゲームが両バージョンで製造されていることもある。Star Trek: 25th Anniversary など一部の後期ゲームは Sharp の挙動に依存する。

> Shogun Emulator の方針: デフォルトは Sharp（"normal"）挙動。設定で "alternate" も選べるようにする。**$C001 への書き込みが「2 回のタイマークロックを挟まずに」行われたときにブレークするデバッガオプション**を用意する（Wiki が「デバッグエミュレータにあるとよい」と書いている。この挙動は完全に理解されておらず、どのエミュレータも実装していない）。

バリアント:

| マッパー | 基板 | 違い |
|---|---|---|
| 118 | TKSROM, TLSROM | 上位バンク選択ラインを VRAM A10 に直結（柔軟なネームテーブル制御） |
| 119 | TQROM | CHR ROM と CHR RAM を同時に使う（バンクごとに選択） |
| 206 | DxROM（Namco 108 / MIMIC-1） | MMC3 より前の Namco 製。IRQ もネームテーブル制御もない。$8000 の下位 3 bit と $8001 の下位 6 bit のみ実装 |
| 37, 47 | Nintendo 製マルチカート | |
| 4 サブマッパー 5 | Waixing | T9552 チップが PRG/CHR アドレスラインをスクランブルする |

Acclaim の MC-ACC は独自の MMC3 変種で、A12 フィルタの代わりに**÷8 プリスケーラを立ち下がりエッジでクロックする**。

## 7. 実装方針と、その理由

### 7.1 対応フォーマット

**iNES + NES 2.0 の両方に対応する。** NES 2.0 は PRG-RAM / CHR-RAM サイズ、リージョン、サブマッパーを曖昧さなく指定できるので、実装の分岐を「ヘッダの値」に素直に落とせる。iNES しかない ROM には §2.5 の判別手順と §2.4 のゴミヘッダ対策を入れる。

.fds と UNIF は当面非対応（`13_...` の将来計画に回す）。

### 7.2 マッパーの実装優先順位

実装コストとカバレッジのバランスから次の順序にする。

| 順 | マッパー | 理由 |
|---|---|---|
| 1 | 0（NROM） | レジスタなし。ROM ローダと PPU の検証に使えるテスト ROM の多くが NROM |
| 2 | 2（UxROM） | 1 レジスタ。バンク切り替えの基本形 |
| 3 | 3（CNROM） | CHR バンク切り替えの基本形 |
| 4 | 7（AxROM） | 1 画面ミラーリングの検証 |
| 5 | 66（GxROM） | PRG + CHR 同時切り替え |
| 6 | 1（MMC1） | タイトル数最多。シリアルインタフェースという特殊な形 |
| 7 | 4（MMC3） | タイトル数 2 位。**スキャンライン IRQ の実装が PPU の A12 通知機構を確立する** |

マッパー 0/1/2/3/4/7 でライセンス NES タイトルの大部分をカバーできる（NesCartDB のタイトル数上位は MMC1、MMC3、UxROM、NROM、CNROM、AxROM の順）。MMC5 と VRC 系はその後。

### 7.3 Go の interface 設計

MMC3 の A12 カウンタ、MMC2/MMC4 のタイルフェッチ検出、MMC5 のネームテーブルフェッチ検出があるため、**マッパーは「CPU バスアクセス」と「PPU バスアクセス」の両方を観測できなければならない。**

```go
// 概念スケッチ。詳細設計は docs/specifications で確定させる。
type Mapper interface {
    // CPU バス
    ReadPRG(addr uint16) (value uint8, handled bool)  // handled=false ならオープンバス
    WritePRG(addr uint16, value uint8)

    // PPU バス
    ReadCHR(addr uint16) uint8
    WriteCHR(addr uint16, value uint8)

    // ネームテーブルのアドレス変換（CIRAM / カートリッジ VRAM / CHR-ROM）
    MapNametable(addr uint16) NametableTarget

    // PPU がアドレスバスに値を出したことの通知（MMC3 の A12、MMC5 のフェッチ検出）
    NotifyPPUAddress(addr uint16)

    // CPU サイクルの経過通知（VRC4 / FME-7 の CPU サイクル IRQ）
    Tick(cpuCycles int)

    // IRQ ライン
    IRQAsserted() bool

    // 状態の保存 / 復元（セーブステート、バッテリーバックアップ）
    SaveState() []byte
    LoadState([]byte) error
    BatteryRAM() []byte
}
```

重要な点:

- `NotifyPPUAddress` は **PPU が実際にバスに出したアドレス**を渡す（§3.1 のバス多重化を考慮し、2 サイクルのアクセスのうち 1 サイクル目のアドレス）
- `ReadPRG` の `handled` により、マップされていない領域のオープンバスを正しく表現する
- バス競合は「WritePRG に入る前に値を ROM の内容と AND する」層をマッパー実装の外側に置く（サブマッパーに応じて有効化）

### 7.4 セーブデータの永続化

- バッテリーバックアップ RAM は ROM ファイル名 + `.sav` として、OS ごとの適切なデータディレクトリに保存する（設定ファイルと同じ場所ではなく、「セーブデータ」用のディレクトリ → `12_config_and_packaging.md`）
- **初回は不定値**が正しいが、エミュレータは一貫した初期状態（$00）にしてよい（Wiki の記述どおり）
- 書き込みのたびに保存するのは重いので、「変更があったらデバウンスして保存」「終了時に保存」の両方を行う

# デバッガ機能の設計調査

> 調査日: 2026-09-21
> **クリーンルーム方針**: 既存 NES エミュレータのソースコードは参照していない。デバッガ UI の「慣習」は NESdev Wiki に文書化されたもの（パターンテーブルの表示順など）と、一般的なデバッガ（gdb / IDE / ディスアセンブラ）の常識に基づく。

## 1. 背景・目的

project.md はデバッグ機能を非常に詳細に要求している。これらは「あとから付ける」のが最も難しい部分なので、**エミュレータコアの設計段階でフックを入れておく必要がある。**

要求の一覧（project.md より）:

| ID | 要求 |
|---|---|
| D1 | スプライト、BG、パレットを視覚的に見る別ウィンドウ（それぞれ別ウィンドウ、メニューから開く） |
| D2 | ROM が高速に書き換える場合があるので、**リアルタイムにメモリと同期したい** |
| D3 | スプライト、BG、パレットを**その場で書き換えるエディタ** |
| D4 | メモリ 16 進ダンプ。**現在実行している場所が示される**、**書き換わった瞬間に書き換わった場所がフラッシュする** |
| D5 | メモリの**値を直接書き換えるエディタ** |
| D6 | 逆アセンブル機能。ニーモニック表示、**現在実行されている場所がハイライト** |
| D7 | ブレークポイント、ステップ実行 |
| D8 | 実行速度の調整（2 倍、1.5 倍、1.2 倍、1/2 倍、1/4 倍など） |
| D9 | debug モードでできる限り多くのログを出力。Config で指定したフォルダに保存。CLI 起動時は stdout も指定可能 |

## 2. エミュレータコアに必要なフック

**これが本書の最重要部分。** 後付けできないものを列挙する。

### 2.1 バスアクセスフック

```go
// 概念スケッチ
type BusHooks struct {
    // すべての CPU リード/ライトで呼ばれる（nil なら呼ばない = 本番モードのオーバーヘッドゼロ）
    OnCPURead  func(addr uint16, value uint8)
    OnCPUWrite func(addr uint16, value uint8, old uint8)
    OnPPURead  func(addr uint16, value uint8)
    OnPPUWrite func(addr uint16, value uint8, old uint8)
}
```

用途: D2（リアルタイム同期）、D4（書き換わった場所のフラッシュ）、D7（メモリアクセスブレークポイント）。

**性能への配慮**: `if hooks.OnCPUWrite != nil` の分岐 1 個ぶんのコスト。Go のインライン展開で吸収される範囲。デバッグウィンドウが 1 つも開いていないときは nil にする。

### 2.2 命令境界フック

```go
// 命令のフェッチ直前に呼ばれる
OnInstructionStart func(pc uint16, state CPUState)
```

用途: D6（現在位置ハイライト）、D7（PC ブレークポイント、ステップ実行）、D9（実行トレースログ）、そして **`08_test_roms_and_validation.md` の nestest.log 比較**。

`CPUState` は A / X / Y / P / S / PC / 累積サイクル数 / PPU の (scanline, dot) を含む。**nestest.log の形式をそのまま出せる構造にする。**

### 2.3 フレーム境界フック

```go
OnFrameComplete func(frame *Frame, stats FrameStats)
```

用途: D2（ビューアの更新タイミング）、映像出力。

### 2.4 変更追跡（ダーティ管理）

D2 と D4 のために「どこが変わったか」を効率的に知る必要がある。

**方式**: 各メモリ領域に「変更フレーム番号」の配列を持つ。

```go
type ChangeTracker struct {
    // 1 バイトごとに「最後に書き込まれたフレーム番号」を持つ
    lastWriteFrame []uint32
    currentFrame   uint32
}

// 表示時: currentFrame - lastWriteFrame[i] が小さいほど強くフラッシュさせる
func (t *ChangeTracker) Heat(i int) float32 {
    age := t.currentFrame - t.lastWriteFrame[i]
    if age > 30 { return 0 }
    return 1 - float32(age)/30
}
```

- メモリコスト: 内蔵 RAM 2 KiB → 8 KiB の追跡配列。VRAM 2 KiB、OAM 256 B、パレット 32 B、PRG-RAM 8 KiB。**合計でも 50 KiB 程度で済む**
- 「30 フレームで消えるヒートマップ」にすると、project.md の「書き換わった瞬間にフラッシュする」が自然に実現できる
- フラッシュの持続時間は設定可能にする

**なぜヒートマップにするのか**: 「変更フラグ（bool）」だと「1 フレームだけ光って消える」ので人間の目には見えない。逆に「変更したら光ったまま」だと画面が全部光る。**時間で減衰させるのが唯一実用的**。

## 3. D1 / D2 / D3: PPU ビューア

### 3.1 パターンテーブル（CHR）ビューア

表示（NESdev Wiki の慣習、`03_ppu.md` §5）:

- 2 枚の 16×16 タイルグリッド、または 1 枚の 16×32 グリッド
- 各テーブルは 128×128 ピクセルの正方形
- タイルは左から右、上から下（$00 が左上、$0F が右上、$FF が右下）
- **8×16 スプライト用の並べ替えオプション**: 1 行目 = $00, $02, …, $1E / 2 行目 = $01, $03, …, $1F

追加機能:

- タイルにマウスオーバーで「タイル番号、CHR アドレス、現在のバンク番号」を表示
- 適用するパレット（BG 0–3 / スプライト 0–3）を選べる。**デフォルトは「グレースケール（パレット無視）」にする**（タイルの形が見やすい）
- 現在のバンク構成（マッパーが何を $0000/$1000 にマップしているか）を表示
- **拡大率を 1x〜8x で変えられる**

編集（D3）:

- タイルをクリックして 8×8 のピクセルエディタを開く
- 4 色（透明 + 3 色）のパレットで描く
- **CHR-ROM は実機では書き込めない。** そこで「CHR オーバーレイ層」を用意する（§6）

### 3.2 ネームテーブル（BG）ビューア

- 4 枚の論理ネームテーブルを 2×2（512×480 ピクセル）で表示
- **現在のミラーリング設定を反映する**（同じ内容が 2 箇所に出る）
- **現在のスクロール枠（256×240）を線で重ねて描く**。これが最も有用な機能
- タイルにマウスオーバーで「ネームテーブルアドレス、タイル番号、属性値、適用パレット」を表示
- 属性グリッド（16×16 ごとの境界）のオーバーレイを ON/OFF できる
- ピクセルグリッド / タイルグリッドのオーバーレイ

編集（D3）:

- タイルをクリックしてタイル番号を変更（パターンテーブルから選ぶ）
- 属性領域をクリックしてパレット番号を変更
- **VRAM への直接書き込みなので実機の挙動と矛盾しない**

### 3.3 スプライト（OAM）ビューア

- 64 スプライトを一覧（8×8 のグリッドに配置、または縦リスト）
- 各スプライトについて: インデックス、Y、タイル番号、属性（パレット / 優先度 / 反転）、X、**実際に描画されたか**
- 8×16 モードでは 2 タイルぶんを表示
- **画面上のどこにいるかを示すオーバーレイ**（メイン画面にスプライトの矩形を描くオプション）
- **スキャンラインごとのスプライト数**を表示（9 個以上ならオーバーフローの警告）
- sprite 0 を強調表示（タイミング源として重要）

編集（D3）:

- 各フィールドを数値で編集（OAM への直接書き込み）
- ドラッグで X / Y を変更

### 3.4 パレットビューア

- **パレット RAM 32 エントリ**を BG 4 組 + スプライト 4 組として表示
- backdrop 色（$3F00）を明示する
- **NES の 64 色全体**を 4×16 のグリッドで表示。$0D に「使用非推奨」マークを付ける（`03_ppu.md` §10.2）
- 各エントリのアドレスと値（$00–$3F）を表示
- **エンファシスとグレースケールの適用結果**をプレビューできる

編集（D3）:

- エントリをクリックして 64 色から選ぶ
- **$3F00 / $3F10 が同じストレージであることを UI に反映する**（片方を変えるともう片方も変わる。`03_ppu.md` §10.1）

### 3.5 リアルタイム同期（D2）

project.md の「ROM によってはこれを高速に書き換える処理をしている場合があるので、リアルタイムにメモリと同期したい」への対応。

**方式**: フレーム末（`OnFrameComplete`）に、開いているビューアに関係するメモリをスナップショットして UI スレッドに渡す。

| ビューア | 必要なデータ | サイズ |
|---|---|---|
| パターンテーブル | 現在マップされている CHR 8 KiB | 8 KiB |
| ネームテーブル | VRAM 2 KiB（+ 4 画面なら 4 KiB） | 2–4 KiB |
| OAM | 256 B | 256 B |
| パレット | 32 B | 32 B |

**合計で最大 12 KiB 程度。毎フレームコピーしても 60 fps で 720 KB/s。まったく問題にならない。**

さらに、**フレーム内で変化した場合の扱い**:

- MMC3 などがスキャンラインごとに CHR バンクを切り替える場合、「フレーム末の状態」は画面の一部しか表していない
- 対応: 「スキャンラインを指定してその時点の状態を見る」モードを用意する。指定スキャンラインでスナップショットを取る
- これは**実際のゲームのデバッグで必須**（ステータスバーと本体で別の CHR バンクを使うゲームが多い）

## 4. D4 / D5: メモリ 16 進ダンプ

### 4.1 表示

```
        00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F  ASCII
$0000:  00 01 A5 FF 00 00 00 00  12 34 56 78 00 00 00 00  ..¥.....４Vx....
$0010:  ...
```

- 1 行 16 バイト（設定で 8 / 16 / 32）
- **PC が指すバイトをハイライト**（D4）
- **最近書き換わったバイトを色で示す**（§2.4 のヒートマップ。赤 → 徐々に通常色へ）
- スタックポインタが指す位置を別色で示す
- ゼロページ（$0000–$00FF）とスタックページ（$0100–$01FF）を視覚的に区切る

### 4.2 対象メモリ空間の切り替え

| 空間 | 範囲 | 備考 |
|---|---|---|
| CPU アドレス空間 | $0000–$FFFF | **読み出しに副作用があるレジスタ（$2002, $2004, $2007, $4015, $4016, $4017）は「副作用なしのピーク」で読む**。これが極めて重要 |
| 内蔵 RAM | $0000–$07FF | ミラーを畳んで表示 |
| PPU アドレス空間 | $0000–$3FFF | CHR / ネームテーブル / パレット |
| OAM | $0000–$00FF | |
| PRG-ROM（生） | ファイル上のオフセット | バンク切り替えと無関係に全体を見る |
| CHR-ROM（生） | 同上 | |
| PRG-RAM / セーブ RAM | $6000–$7FFF | |

**「副作用なしのピーク」の実装が必須。** デバッガがメモリを表示するためにレジスタを読んでゲームの動作を壊す、というのは絶対に避けなければならない。

```go
// バスには 2 系統のリードを用意する
func (b *Bus) Read(addr uint16) uint8  { /* 副作用あり。CPU が使う */ }
func (b *Bus) Peek(addr uint16) uint8  { /* 副作用なし。デバッガが使う */ }
```

### 4.3 編集（D5）

- 16 進の桁を直接タイプして上書き
- ASCII 側からも編集
- **書き込みも副作用の有無を選べるようにする**（`Poke` = 副作用なし、`Write` = 副作用あり）。レジスタへの書き込みをテストしたい場合があるため

### 4.4 検索・ウォッチ

- バイト列 / 文字列の検索
- **ウォッチリスト**: アドレスを登録して値を常時表示（ゲームの変数を追うのに使う）
- **アドレスに名前を付けられる**（ラベル）。ラベルは ROM のハッシュごとに保存する

### 4.5 ウィジェットの選択

`09_go_gui_frameworks.md` で Fyne を選んだ場合、**`widget.TextGrid` がセル単位の前景色・背景色を持つのでそのまま使える。** 64 KiB = 4096 行なので、可視範囲だけを `TextGrid` に流し込み、スクロールバーは自前で管理する（または `widget.List` の各行に `TextGrid` を置く）。

## 5. D6 / D7: 逆アセンブラとブレークポイント

### 5.1 逆アセンブラ

表示:

```
        C000  4C F5 C5     JMP $C5F5
>       C5F5  A2 00        LDX #$00
        C5F7  86 00        STX $00
   *    C5F9  86 10        STX $10
```

- `>` = 現在の PC、`*` = ブレークポイント
- アドレス / 機械語バイト列 / ニーモニック / オペランド
- **非公式命令は別色で表示し、別名を併記する**（`02_cpu_6502.md` §7.1）
- 分岐先・ジャンプ先をラベル名で表示（ラベルがあれば）
- 実効アドレスとその現在値をコメントとして表示（`LDA $0300,X  ; = $0305 = #$42`）

**6502 の逆アセンブルの本質的な難しさ**: データとコードが区別できない。

対策:

1. **実行済みアドレスの記録**（コードカバレッジ）。実行されたバイトを「コード」として記録し、命令境界を確定させる
2. 未実行領域は「線形逆アセンブル」で推定表示し、**推定であることを視覚的に示す**（薄い色）
3. ユーザーが「ここはデータ」「ここはコード」とマークできる。マークは ROM ハッシュごとに保存
4. バンク切り替えがあるので、**アドレスだけでなく「どのバンクの」かを記録する**（PRG-ROM のファイルオフセットで記録するのが正解）

### 5.2 ブレークポイント（D7）

| 種類 | 条件 |
|---|---|
| 実行 | PC が指定アドレスに達した |
| リード | 指定アドレスを読んだ |
| ライト | 指定アドレスに書いた |
| 範囲 | 指定範囲へのアクセス |
| 条件付き | 上記 + 「A == $42」のような条件式 |
| PPU | 指定スキャンライン / ドットに達した |
| イベント | NMI / IRQ / リセット / スプライト 0 ヒット / マッパー IRQ |

**PPU ブレークポイントとイベントブレークポイントは NES 特有で、極めて有用。** 「スプライト 0 ヒットの瞬間に止める」ができると、画面分割のバグが一気に追える。

実装: `OnInstructionStart` と `BusHooks`、PPU の `Step()` 内でブレークポイント条件を評価する。**ブレークポイントが 1 つも設定されていないときはチェックをスキップする**（性能のため）。

### 5.3 ステップ実行（D7）

| 操作 | 内容 |
|---|---|
| Step Into（1 命令） | 1 命令実行して止まる |
| Step Over | JSR の場合は戻ってくるまで実行 |
| Step Out | 現在のサブルーチンから RTS するまで実行 |
| **Step Cycle（1 CPU サイクル）** | 1 CPU サイクルだけ進める。**DMA や PPU との相互作用を追うのに必須** |
| **Step Scanline** | 次のスキャンラインの先頭まで |
| **Step Frame** | 次のフレームの先頭まで |
| Run to Cursor | 逆アセンブル画面でカーソル位置まで |

`07_timing_and_synchronization.md` §7.1 で lock-step を選んだので、**Step Cycle が自然に実装できる。** これが lock-step を選ぶ大きな理由のひとつ。

> **セーブステートとの関係（`14_savestate_and_movie.md` §3.3）**: CPU は「自然なコード + tick コールバック」方式で実装するため、**サイクル単位ステップの途中ではスナップショットが取れない**（状態がホストのコールスタックにある）。この状態でセーブステートを要求されたら、**現在の命令を完了させてから保存し、UI に「命令境界（$XXXX）まで進めてから保存しました」と明示する。** 黙って少しずれた状態を保存しないこと。
>
> また、**外部コマンド（保存/復元/ステップ/速度変更）はすべて命令境界でのみ処理する**（`14` §3.4）。これによりロックなしで安全に扱える。

### 5.4 CPU 状態の表示

- A / X / Y / PC / S / P（フラグは `NV-BDIZC` 形式で、立っているものを大文字、寝ているものを小文字か `-` で）
- 累積 CPU サイクル数
- 現在のスキャンライン / ドット
- スタックの中身（$01FF から S まで）を逆アセンブルのリターンアドレスとして解釈して表示
- 保留中の割り込み（NMI / IRQ の各ソース）

### 5.5 コールスタック

JSR / RTS を追跡してコールスタックを再現する。**割り込みで入った場合も区別して表示する。**
6502 は JSR/RTS 以外でもスタックを操作できるので完全ではない。**推定であることを示す。**

## 6. D3 の実装上の難所: CHR-ROM の編集

**CHR-ROM は実機では書き込めない。** パターンテーブルエディタで書き換えた内容をどう扱うか。

方式: **CHR オーバーレイ層**

```go
type CHRAccess struct {
    rom     []uint8            // 元の CHR-ROM（不変）
    ram     []uint8            // CHR-RAM（あれば）
    overlay map[uint32]uint8   // デバッガによる上書き（CHR-ROM のファイルオフセット → 値）
    overlayEnabled bool
}

func (c *CHRAccess) Read(addr uint16) uint8 {
    off := c.mapToROMOffset(addr)
    if c.overlayEnabled {
        if v, ok := c.overlay[off]; ok { return v }
    }
    return c.rom[off]
}
```

- **オーバーレイは ON/OFF できる。** OFF にすれば実機どおりの動作を確認できる
- オーバーレイは保存・読み込みできる（`.chrpatch` のような形式）。**ROM 本体は絶対に書き換えない**
- PRG-ROM の編集も同じ仕組みで扱う（逆アセンブル画面からのパッチ）

**なぜこの設計にするのか**: ROM ファイルを直接書き換えると、(1) 元に戻せない、(2) ROM のハッシュが変わってセーブデータや設定と紐付かなくなる、(3) ユーザーが「エミュレータが自分の ROM を壊した」と感じる。オーバーレイなら全部避けられる。

## 7. D8: 実行速度の調整

| 倍率 | 用途 |
|---|---|
| 1/4x, 1/2x | スローモーション（難しい場面の観察、バグの再現） |
| 1.0x | 通常 |
| 1.2x, 1.5x, 2x | 軽い早送り |
| 4x, 8x, 無制限 | テスト ROM の実行、長いイントロのスキップ |
| 一時停止 | |
| コマ送り | 1 フレームずつ |

実装は `07_timing_and_synchronization.md` §6.2。

UI: **メニュー + キーボードショートカット + 現在の倍率の常時表示。** ショートカットは「+ / −」で倍率変更、「Space」で一時停止、「.」でコマ送りが直感的（多くのメディアプレイヤーとエミュレータの慣習）。

## 8. D9: デバッグログ

### 8.1 出力先

| 起動方法 | デフォルト | 指定方法 |
|---|---|---|
| GUI | Config で指定したフォルダ | 設定 GUI |
| CLI | Config のフォルダ | `--log-dir`、`--log=stdout`、`--log=stderr` |

project.md の「コマンドラインで起動しているときに、stdout も指定可能にする」に対応。

### 8.2 ログのカテゴリとレベル

「できる限り多くのログ」を出すと、1 フレームで数万行になる。**カテゴリ別に ON/OFF できないと使えない。**

| カテゴリ | 内容 | 想定される量 |
|---|---|---|
| `trace.cpu` | 全命令のトレース（nestest.log 形式） | 約 30 万行/秒 |
| `trace.cpu.bus` | 全バスアクセス | 約 180 万行/秒 |
| `ppu.register` | PPU レジスタへのアクセス | 数百〜数千行/フレーム |
| `ppu.timing` | スキャンライン / VBlank / NMI | 数百行/フレーム |
| `apu.register` | APU レジスタへのアクセス | 数十〜数百行/フレーム |
| `apu.frame` | フレームカウンタ | 4 行/フレーム |
| `mapper` | バンク切り替え、IRQ | 数十〜数千行/フレーム |
| `dma` | OAM DMA / DMC DMA | 数行/フレーム |
| `input` | コントローラの読み取り | 数十行/フレーム |
| `warn.compat` | **実機で未定義・非推奨の挙動**（不安定な非公式命令、$0D の使用、レンダリング中の $2007 アクセス、OAMADDR 破損など） | まれ |
| `error` | エミュレータ内部のエラー | まれ |

**`warn.compat` が最も価値が高い。** 「このゲームは不安定な挙動に依存している」と分かると、バグの原因追跡が劇的に速くなる。

### 8.3 形式

- **デフォルトはテキスト（人間が読む）**
- **`trace.cpu` は nestest.log と同一形式**（`08_test_roms_and_validation.md` §4 の比較にそのまま使える）
- 構造化ログ（JSON Lines）オプション。`log/slog` を使う。ただし `trace.cpu` は自前のフォーマッタにする（slog は 30 万行/秒には向かない）
- ログローテーション（サイズと世代数を設定）

### 8.4 性能への配慮

**ログが無効なときのオーバーヘッドをゼロにする。**

```go
// ダメな例: 引数の評価が常に起こる
log.Trace("PC=%04X A=%02X", pc, a)

// 良い例: レベルチェックを先に行う
if dbg.TraceCPU {
    dbg.writeTrace(pc, state)
}
```

Go では `if` 1 個なのでインライン化される。**構造体のフィールドを bool で持ち、ポインタ経由の関数呼び出しにしない。**

### 8.4.1 巻き戻し（rewind）との併用

`14_savestate_and_movie.md` §8 で巻き戻しを第 1 弾に含めることが決まった。デバッグ用途では「ブレークポイントで止まったが、原因はその手前にある」という場面が多いので、**巻き戻し + サイクル単位ステップの組み合わせが最も強力な調査手段になる。**

巻き戻しは「10 フレームごとのセーブステート + 記録した入力での前方再生」で実装するため、**決定論が必須**（`14` §6）。デバッグログやビューアの開閉が実行結果に影響してはいけない。

### 8.5 リングバッファトレース（推奨機能）

「ずっとトレースを出す」のは重すぎるが、「クラッシュの直前 10 万命令を見たい」ことは多い。

**方式**: 常に固定サイズのリングバッファ（メモリ上）に最新 N 命令のトレースを書き、ブレークポイントやクラッシュ時にだけファイルへ吐く。

- N = 100 万命令で、1 命令 32 バイトなら 32 MB。許容できる
- **これがあると「なぜ止まったか」の調査が圧倒的に楽になる**

## 9. ウィンドウ構成の提案

D1 の「それぞれ別ウィンドウ」に従う場合:

| ウィンドウ | 内容 |
|---|---|
| メイン | ゲーム画面 + メニューバー + ステータスバー（FPS、倍率、ROM 名） |
| CPU デバッガ | 逆アセンブル + レジスタ + スタック + コールスタック + ブレークポイント一覧 + ステップ操作 |
| メモリビューア | 16 進ダンプ（複数開けるようにする。CPU 空間と PPU 空間を同時に見たい） |
| パターンテーブル | CHR ビューア/エディタ |
| ネームテーブル | BG ビューア/エディタ |
| スプライト | OAM ビューア/エディタ |
| パレット | パレットビューア/エディタ |
| APU | チャンネル状態 + オシロスコープ（優先度低） |
| ログ | ログビューア（フィルタ付き） |
| 設定 | 設定 GUI（キーバインド含む） |

**ウィンドウの位置・サイズ・開閉状態を設定ファイルに保存して復元する。** これがないと毎回並べ直すことになり、実際には使われなくなる。

> **なぜこれが使いやすいのか**: デバッグは「複数の情報を同時に見る」作業である。CPU の逆アセンブルとネームテーブルとメモリダンプを同時に見て、はじめて「なぜ画面が壊れているか」が分かる。1 つのウィンドウでタブを切り替える設計だと、この「同時に見る」ができない。これが project.md が別ウィンドウを要求している理由だと解釈する。

## 10. 実装順序の提案

デバッグ機能は「エミュレータが動く前に作ると開発を加速する」ものと「動いてから作るもの」に分かれる。

| 段階 | 機能 | 理由 |
|---|---|---|
| **最初（CPU 実装と同時）** | CPU トレースログ（nestest.log 形式）、レジスタ表示、逆アセンブラ | **nestest.log との比較に必須**。これなしに CPU を正しく実装するのは不可能 |
| CPU 完成後 | ブレークポイント、ステップ実行、メモリダンプ（表示のみ） | PPU 実装のデバッグに使う |
| PPU 実装と同時 | パターンテーブル / ネームテーブル / パレットビューア | **PPU のバグは画面を見ても分からない。中間状態を見る必要がある** |
| PPU 完成後 | スプライトビューア、PPU ブレークポイント | |
| APU 実装後 | APU ビューア | |
| 最後 | 各種エディタ（D3 / D5）、ログビューア、ウィンドウ状態の保存 | 開発には不要だがユーザー向けに必要 |

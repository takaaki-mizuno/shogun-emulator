## 8.2 直列化の基盤

```go
package state

const magic = "SHGS"

type Writer struct {
    buf      []byte
    sections []sectionHeader
}

// Section は名前付きのセクションを開始する。呼び出しは入れ子にできる。
func (w *Writer) Section(name string) func()

func (w *Writer) U8(v uint8)
func (w *Writer) U16(v uint16)
func (w *Writer) U32(v uint32)
func (w *Writer) U64(v uint64)
func (w *Writer) Bool(v bool)
func (w *Writer) Bytes(v []uint8)

type Reader struct { /* ... */ }

// Section は名前が一致するセクションへ入る。一致しなければ第 2 戻り値が false になる。
func (r *Reader) Section(name string) (end func(), ok bool)

func (r *Reader) U8() uint8
// 以下同様

// Fail は読み出し側が見つけた不整合を記録する。値は読めても内容が
// 矛盾している場合に使う。
func (r *Reader) Fail(err error)

func (r *Reader) Err() error
```

セクションに名前と長さを持たせる。読み出し側が知らないセクションを長さ分読み飛ばせる。

`Reader` はエラーを内部に蓄積する。各読み出しメソッドはエラーを返さず、`Err` で最後に確認する。呼び出し側のコードが読み出しの順序だけを表すようにするためである。

### 8.2.1 ヘッダ

| フィールド | 型 | 内容 |
|---|---|---|
| マジック | `[4]uint8` | `"SHGS"` |
| フォーマットバージョン | `uint16` | |
| エミュレータバージョン | 可変長文字列 | `--version` と同じ値 |
| コミットハッシュ | 可変長文字列 | |
| ROM ハッシュ | `[20]uint8` | PRG + CHR の SHA-1 |
| マッパー番号 | `uint16` | |
| サブマッパー | `uint8` | |
| リージョン | `uint8` | |
| 初期状態 | `InitState` | 決定論のため（§8.5） |
| 累積 CPU サイクル数 | `uint64` | |
| 累積フレーム数 | `uint64` | |
| オーバーレイのハッシュ | `[8]uint8` | 「06 カートリッジとマッパー設計」§6.8 の `Overlay.Hash` |
| スクリーンショット | 可変長 | PNG。設定で省略できる |

```go
package state

type Header struct {
    FormatVersion uint16
    Version       string
    Commit        string
    ROMHash       [20]uint8
    Mapper        uint16
    Submapper     uint8
    Region        string
    Init          Init
    Cycles        uint64
    Frames        uint64
    OverlayHash   [8]uint8
    Screenshot    []uint8
}

func (h *Header) Write(w *Writer)
func (h *Header) Read(r *Reader) error
func (h *Header) Verify(want *Header) error

// ReadHeader はステートのバイト列からヘッダだけを読む。
func ReadHeader(b []uint8) (Header, error)
```

`ReadHeader` はスロットの一覧表示に使う。本体を組み立てずに保存時刻・累積フレーム数・スクリーンショットを取り出せる。

### 8.2.2 検証

ロード時に次を検証する。いずれかが一致しないときエラーを返し、理由を含める。

| 項目 | 不一致時の扱い |
|---|---|
| マジック | エラー |
| フォーマットバージョン | エラー |
| エミュレータバージョン | エラー |
| コミットハッシュ | エラー |
| ROM ハッシュ | エラー |
| マッパー番号・サブマッパー | エラー |
| リージョン | エラー |
| オーバーレイのハッシュ | `warn.compat` にログを出してロードを続ける |

オーバーレイのハッシュが違ってもロードを続けるのは、タイルを編集したあとで編集前のステートを読み込む操作がデバッグで普通に起こるためである。

エミュレータバージョンの一致を要求するのは、精度を高めるたびに保存する状態が増え、古い形式との対応が保てなくなるためである。

バッテリーバックアップの `.sav` ファイルは単純なバイト列であり、バージョンによらず読める。

### 8.2.3 サイズ

| 項目 | サイズ |
|---|---|
| 内蔵 RAM | 2 KiB |
| CIRAM | 2–4 KiB |
| OAM・secondary OAM・パレット | 約 0.3 KiB |
| PRG-RAM | 0–32 KiB |
| CHR-RAM | 0–8 KiB |
| 各コンポーネントのレジスタ | 約 1 KiB |

スロットへ保存するステートは圧縮しない。巻き戻し用のリングに保持するステートは `compress/flate` で圧縮する（§8.6）。

## 8.3 スナップショットを取る位置

CPU は命令の途中でホストのコールスタックに状態を持つ（「03 CPU 設計」§3.1）。したがってスナップショットを取れるのは命令境界のみである。

**スナップショット点は「次の命令の opcode フェッチの直前」とする。**

この位置では次が成り立つ。

| 条件 |
|---|
| CPU の状態がすべてフィールドにある |
| DMA は要求されていても開始前である |
| 割り込みは pending フラグとして保持されている |
| PPU・APU・マッパーは元からフィールドのみで状態を表す |

### 8.3.1 コマンドキュー

外部からの要求を命令境界でのみ処理する。

```go
package emu

type command interface{ isCommand() }

type cmdSaveState      struct{ out chan saveResult; screenshot bool }
type cmdLoadState      struct{ data []byte; done chan error }
type cmdStep           struct{ kind StepKind; count int }
type cmdSetSpeed       struct{ factor float64 }
type cmdReset          struct{ hard bool; done chan error }
type cmdSetInput       struct{ port int; buttons uint8 }
type cmdRewind         struct{ frames int; done chan error }
type cmdStartRecording struct{ path string; done chan error }
type cmdStopRecording  struct{ done chan error }
type cmdPlayMovie      struct{ m *movie.Movie; done chan error }
type cmdStopMovie      struct{ done chan error }
type cmdSetRewinding   struct{ on bool }

func (e *Emulator) run() {
    for {
        e.drainCommands()      // 命令境界
        e.nes.StepInstruction()
    }
}
```

この構造により、実行中のステート保存・復元と速度変更をロックなしで行える。

### 8.3.2 サイクル単位ステップ実行との関係

サイクル単位ステップで命令の途中に止まっている状態でセーブステートを要求された場合、現在の命令を完了させてから保存する。保存後に UI へ「命令境界（`$XXXX`）まで進めてから保存した」ことを表示する。

## 8.4 保存する状態

各編に定めた一覧を参照する。

| コンポーネント | 参照先 |
|---|---|
| CPU | 「03 CPU 設計」§3.9 |
| PPU | 「04 PPU 設計」§4.11 |
| APU | 「05 APU 設計」§5.12 |
| カートリッジ | 「06 カートリッジとマッパー設計」§6.9 |
| 入力 | 「07 入力設計」§7.7 |

バスと全体の状態を次に示す。

| 項目 | 省いたときの症状 |
|---|---|
| 内蔵 RAM 2 KiB | 復元が成立しない |
| `openBus` | コントローラポートの上位 3 bit が変わり、特定のプログラムがボタンを認識しない |
| DMA の get/put 位相 | DMA のサイクル数が 1 ずれる |
| OAM DMA の pending・ページ・転送インデックス | 転送途中のステートで転送が中断する |
| DMC DMA の pending・種別・サブステップ | 同上 |
| CPU 停止中に読んでいたアドレス | レジスタ競合の再現が変わる |
| PPU ドットアキュムレータ | PAL で PPU の進み方がずれる |
| 累積 CPU サイクル数・フレーム数 | トレース出力とムービーのフレーム索引が合わなくなる |

リサンプラのフィルタ状態、オーディオリングバッファ、フレームバッファは保存しない。エミュレーション状態ではないためである。ロード後にフィルタをリセットし、リングを高水位まで埋め、フレームバッファを次のフレーム完成まで前の内容のままにする。

同じ初期状態と同じ入力から同じ結果を得ることを保証する。

### 8.5.1 ホスト側の制約

「01 全体アーキテクチャ設計」§1.7 の表に従う。

### 8.5.2 実機で値が定まらない状態

電源投入時に実機で値が定まらない状態を、すべて `InitState` から決定する。

```go
type InitState struct {
    RAMPattern      RAMPattern   // Zero, FF, Pattern, Random
    RAMSeed         uint64
    CPUPPUAlignment int          // 0..2
    DMAGetPutPhase  int          // 0..1
    PPUVBlankFlag   bool
}
```

`InitState` が決定する対象を次に示す。

| 対象 | 決定方法 |
|---|---|
| 内蔵 RAM の初期値 | `RAMPattern` と `RAMSeed` |
| PRG-RAM の初期値（`.sav` がないとき） | `$00` |
| OAM の初期値 | `RAMPattern` と `RAMSeed` |
| パレット RAM の初期値 | `RAMPattern` と `RAMSeed` |
| CIRAM の初期値 | `RAMPattern` と `RAMSeed` |
| CHR-RAM の初期値 | `RAMPattern` と `RAMSeed` |
| PPUSTATUS の VBlank フラグ | `PPUVBlankFlag` |
| CPU と PPU のアライメント | `CPUPPUAlignment` |
| DMA の get/put 初期位相 | `DMAGetPutPhase` |

固定値とする対象を次に示す。

| 対象 | 値 |
|---|---|
| APU Noise の LFSR | 1 |
| APU フレームカウンタの LFSR 相当の内部カウンタ | 0 |
| APU DMC の内部カウンタ | 0 |
| APU Triangle の位相 | 0 |
| MMC1 の PRG バンクモード | 3（末尾バンクを `$C000` に固定） |
| MMC3 の R0–R7 とバンク選択 | 0 |
| OAM の DRAM 減衰 | 再現しない |
| PPU I/O ラッチの減衰 | 保持時間を 36 フレーム分として再現する（「04 PPU 設計」§4.4.1） |

`RAMPattern` の既定値は `Random` とする。未初期化 RAM に依存するプログラムの挙動を開発中に観測できる。`RAMSeed` を記録するため再現性は保たれる。

設定 `--deterministic` を指定したとき、`RAMPattern` を `Zero`、`CPUPPUAlignment` を 0、`DMAGetPutPhase` を 0、`PPUVBlankFlag` を false に固定する。

## 8.6 巻き戻し

```go
package emu

type rewindBuffer struct {
    states   []compressedState   // リングバッファ
    inputs   []frameInput        // 各フレームの入力
    interval int                 // ステートを保存するフレーム間隔
    capacity int                 // 保持するフレーム数
}
```

| 項目 | 既定値 |
|---|---|
| ステートの保存間隔 | 10 フレーム |
| 保持時間 | 60 秒（3606 フレーム） |
| 圧縮 | `compress/flate` |

巻き戻しの手順を次に示す。

1. 目標フレームの直前に保存されたステートをロードする
2. 記録された入力を使って目標フレームまで前方再生する
3. 前方再生中は映像と音声を出力しない

前方再生が成立するのは決定論が保証されているためである。

遡った後は、目標フレームより後に保存したステートを捨てる。遡った先から進めたときの入力は記録したものではなく、そのときの入力になるためである。記録中のムービーも同じフレームまで切り詰め、再記録回数を 1 増やす（§8.7.5）。

入力の記録はムービー記録と同じ構造を使う（§8.7.2）。巻き戻しが有効な間、常に直近 60 秒分の入力を保持する。入力はフレーム番号を保持フレーム数で割った余りを添字とするリングに置く。

押している間だけ遡るホットキーでは、1 フレームずつ遡りながら 1 フレーム分の時間を待つ。待たずに遡ると、キーを押した瞬間に記録の先頭まで戻る。

## 8.7 入力ムービー

### 8.7.1 入力のラッチ点

**ムービーのフレーム N の入力は、エミュレートされたフレーム N の scanline 0 / dot 0 でラッチされ、そのフレーム中は変化しない。**

プログラムが `$4016` へ strobe を書いたとき、この値が読まれる。実機の strobe 時読み出しの挙動（「07 入力設計」§7.2）は変わらない。

ラッチはムービーを扱っているときだけでなく、通常の実行でも行う。記録した値と実際に使われた値を同じにするためである（「07 入力設計」§7.3）。

実際に取り込むのは、フレーム境界を越えた最初の命令境界である。CPU の命令の途中では状態を触れない（§8.3）。プログラムがコントローラを読むのは VBlank 中であり、取り込みはそれより前に終わる。

### 8.7.2 ファイル形式

ヘッダと入力ログの 2 部構成とする。

| ヘッダのフィールド | 内容 |
|---|---|
| マジック | `"SHGM"` |
| フォーマットバージョン | |
| エミュレータバージョンとコミットハッシュ | |
| ROM ハッシュ | PRG + CHR の SHA-1 |
| ROM ファイル名 | 表示のみに使う |
| リージョン、マッパー番号、サブマッパー | |
| `InitState` | 全フィールド |
| 開始方法 | `power-on` または `savestate` |
| 埋め込みセーブステート | 開始方法が `savestate` のとき |
| ポート 1 と 2 のデバイス種別 | |
| 総フレーム数 | |
| 再記録回数、作者、コメント | |
| チェックサム間隔 | フレーム数。0 で無効 |

入力ログのレコードを次に示す。

```go
type recordKind uint8

const (
    recordInput recordKind = iota
    recordReset
    recordHardReset
    recordChecksum
)
```

| レコード | 内容 | サイズ |
|---|---|---|
| 入力 | 種別 + ポート 1 と 2 のボタン状態 | 3 バイト |
| リセット | 種別のみ | 1 バイト |
| ハードリセット | 同上 | 1 バイト |
| チェックサム | 種別 + 状態のハッシュ | 9 バイト |

すべてのレコードが種別バイトで始まる。入力レコードに種別バイトを付けないと、続く 2 バイトが入力かイベントかを区別できない。ボタン状態はどの値も取りうるため、値で見分けることもできない。

入力レコードはフレーム番号の昇順に並ぶ。フレーム番号は暗黙であり、レコードに含めない。リセットのレコードはそのフレームの入力レコードの直前に、チェックサムのレコードは直後に置く。再生側は同じ順序で読み、フレームの開始時にイベントを適用してから入力を使う。

標準コントローラ 2 個で毎フレーム記録する場合、60 fps で毎秒 180 バイトになる。圧縮しない。

**フォーマットバージョン 2**。入力以外で Machine State を変えた操作（介入）を記録するレコードを加える。介入の定義は「14 Agent Interface 設計」§14.16.2 に従う。

```go
const (
    recordInput recordKind = iota
    recordReset
    recordHardReset
    recordChecksum
    recordPoke        // バージョン 2
    recordSetRegister // バージョン 2
    recordFreeze      // バージョン 2
    recordUnfreeze    // バージョン 2
    recordOverlay     // バージョン 2
)
```

介入のレコードはすべて、種別バイトの直後に **フレームの開始から数えた CPU サイクル数**（4 バイト、リトルエンディアン）を持つ。多バイトの値はすべてリトルエンディアンとする。

| レコード | バイト配置 | サイズ |
|---|---|---|
| ポーク | 種別 + サイクル数（4） + 空間（1。「09 デバッガ設計」§9.4.5 の空間の番号） + アドレス（4。空間内のオフセット） + 値（1） + フラグ（1。bit 0 が副作用の有無） | 12 バイト |
| レジスタの設定 | 種別 + サイクル数（4） + レジスタ（1。0: A、1: X、2: Y、3: S、4: PC、5: P） + 値（2。PC 以外は下位 1 バイトだけを使う） | 8 バイト |
| Freeze | 種別 + サイクル数（4） + CPU アドレス（2） + バイト数（1。1–4） + 値（4。下位から使う） | 12 バイト |
| Freeze の解除 | 種別 + サイクル数（4） + CPU アドレス（2） | 7 バイト |
| オーバーレイの切り替え | 種別 + サイクル数（4） + 有効（1。0 または 1） | 6 バイト |

フレーム N の介入のレコードは、フレーム N の入力レコード（チェックサムのレコードがあればその後）の後に、サイクル数の昇順で置く。同じサイクル数のレコードは記録した順に置く。

| 再生側の処理 |
|---|
| フレームの開始時にリセットのレコードを適用し、入力を使う（バージョン 1 と同じ） |
| 介入のレコードは、フレームの開始からの CPU サイクル数が記録の値以上になった最初の命令境界で適用する。サイクル数 0 の介入は、フレームの開始時の入力の取り込みの直後に適用する |
| 適用は記録時と同じ経路（`Emulator.Poke` など）で行う。再生中の編集を断る規則（「09 デバッガ設計」§9.4.8）は、再生そのものが行う適用には及ばない |

サイクル数 `0xFFFFFFFF` は「フレームの終わり」を表す。記録の最後のフレームの後（次のフレームの開始を待っている間）に行った介入に使い、再生では記録の終わりで適用する。

リセットとハードリセットは、利用者のムービー記録と常時記録の両方に記録する（次のフレームの入力レコードの前に置く）。

サイクル数を持たせるのは、Agent-Paced の Instance がフレームの途中（`exec.step_unit` で止めた位置）で書き込むことがあり、フレームの開始時に適用すると結果が変わるためである。

書き出すフォーマットバージョンは、介入のレコードを 1 つも含まないとき 1、含むとき 2 とする。介入を含まないムービーをバージョン 1 のまま保つことで、既存のテスト用ムービーと期待値（「12 テスト設計」§12.8）をそのまま使えるためである。読み込みはバージョン 1 と 2 の両方を受け付ける。

### 8.7.3 desync の検出

チェックサム間隔ごとに状態のハッシュを記録する。既定値は 60 フレームとする。

ハッシュの対象を次に示す。

| 対象 |
|---|
| 内蔵 RAM |
| CIRAM |
| OAM |
| パレット RAM |
| PRG-RAM |
| CPU のレジスタ（A, X, Y, S, PC, P） |
| 累積 CPU サイクル数 |

再生時にハッシュを比較する。一致しないとき、設定 `movie.stopOnDesync` が true なら再生を停止し、フレーム番号と一致しなかった対象を報告する。false なら報告して続行する。

設定 `movie.verifyChecksums` が false のとき比較しない。挙動を変更した後の古いムービーを、desync の報告なしに最後まで再生するために使う。

Re-Reach（「14 Agent Interface 設計」§14.15.3）の再生ではチェックサムを比べない。ROM を作り直した後の再生であり、状態が一致しないのが当然だからである。

ハッシュに画面出力を含めないのは、状態が一致していれば画面も一致するためである。状態の比較のほうが原因の切り分けに直接つながる。

### 8.7.4 バージョンの不一致

ヘッダのエミュレータバージョンが現在のバージョンと異なるとき、警告をログに出して再生を続ける。desync を検出した時点で §8.7.3 に従う。

テスト用のムービーは、エミュレーションの挙動を変更したときに記録し直す。

### 8.7.5 記録時の扱い

| 対象 | 扱い |
|---|---|
| 連射 | 適用後の状態を記録する（「07 入力設計」§7.5） |
| 巻き戻し操作 | ムービーには記録しない。巻き戻した時点以降のレコードを破棄し、再記録回数を 1 増やす |
| セーブステートのロード | ムービーの記録を停止する |
| 速度倍率の変更 | 記録しない。エミュレート時間には影響しないためである |

### 8.7.6 常時記録

Agent Interface の Instance は、入力と介入を常に記録する（「14 Agent Interface 設計」§14.16.1）。記録の内容と形式は入力ムービーと同じであり、次の点だけが異なる。

| 項目 | 利用者のムービー記録（§8.7） | 常時記録 |
|---|---|---|
| 開始 | 利用者の操作 | ROM の読み込み・電源投入・セーブステートのロードのたび。ロード以降は埋め込みセーブステートから始める |
| セーブステートのロード | 記録を停止する（§8.7.5） | 新しい記録を始める |
| 巻き戻し | 巻き戻した時点以降を捨て、再記録回数を 1 増やす | 同じ |
| 介入 | 記録中の編集を断る（「09 デバッガ設計」§9.4.5） | 編集を断らず、介入のレコードとして記録する |
| 保存 | ファイルへ書く | メモリに持つ。`repro.export` で書き出す（「14 Agent Interface 設計」§14.16.3） |

利用者のムービー記録と常時記録は同時に動いてよい。両方が動いているとき、編集は利用者のムービー記録の規則に従って断る。

## 8.8 動画の書き出し

エミュレーションの画と音を、手元のプレイヤーで再生できる動画ファイルに書き出す。入力ムービー（§8.7）とは別の機能である。入力ムービーは入力だけを持ち、再生にはエミュレータと ROM が要る。

GUI では入力ムービーを「操作の記録」と呼ぶ。「ムービー」という語は動画と取り違えやすいためである。ファイルの拡張子（`.movie`）と形式は変えない。

### 8.8.1 ファイル形式

| 項目 | 内容 |
|---|---|
| 入れ物 | MP4（ISO/IEC 14496-12）。`moov` をファイルの末尾に置く通常の形式（フラグメント形式にしない） |
| 映像 | Motion JPEG。サンプル記述は `jpeg`。各フレームを 1 枚の JPEG とし、すべて同期サンプル（キーフレーム）とする |
| 映像の大きさ | 表示する画（オーバースキャンを除いた範囲）を設定 `video.recordScale` 倍（1–3、既定 2）に最近傍で拡大した大きさ |
| JPEG の品質 | 90 |
| 映像の時間単位 | 1,000,000（マイクロ秒）。フレーム `i` の開始時刻を `round(i × 1,000,000 ÷ フレームレート)` とし、隣り合う開始時刻の差を長さとする |
| 音声 | 無圧縮の PCM。サンプル記述は `sowt`（符号付き 16 ビット、リトルエンディアン）。48,000 Hz、ステレオ（左右に同じ値） |
| 音声のサンプル | PCM の 1 フレーム（4 バイト）を 1 サンプルとする。映像の 1 フレームに対応する PCM を 1 つのチャンクにまとめる |

H.264 と AAC を使わないのは、Go だけで書けるエンコーダに実績のあるものが無いためである。Motion JPEG は標準ライブラリの `image/jpeg` で、MP4 は `github.com/Eyevinn/mp4ff` で書ける。macOS の QuickTime Player（AVFoundation）で、映像のデコードと音声の読み出しができることを確かめてある。ファイルは H.264 より大きい（2 倍で 1 分あたり数十 MB）。

拡大してから圧縮するのは、プレイヤーの拡大がドットをぼかすためである。アスペクト比の補正とデバッグ用の重ね表示（オーバーレイ、スプライトの矩形）は入れない。

### 8.8.2 記録する内容

| 対象 | 扱い |
|---|---|
| 映像 | `emu.FrameBuffer` へ渡すすべてのフレーム。一時停止中は増えない |
| 音声 | APU の出力を録画専用のリサンプラで 48,000 Hz にしたもの |
| 速度 | 早送りとスローに関係なく、エミュレーションの時間で記録する。再生すると等速になる |
| 巻き戻し | 巻き戻しで表示したフレームも記録する |

録画専用のリサンプラは、速度倍率を 1 に固定し、消音を適用しない。音声出力の経路のリサンプラ（「05 APU 設計」§5.10）は速度に合わせて出力量を変え、音声を無効にした実行（headless や `--no-audio`）では作られない。APU の出力を 2 つのリサンプラへ分けて渡す。フィルタの構成は設定 `audio.filterProfile` に従う。

映像のフレーム `i` に対応する音声の量は、`round((i + 1) × 48,000 ÷ フレームレート) − round(i × 48,000 ÷ フレームレート)` とする。リサンプラが作った量が足りないときは 0 で埋め、多いときは超えた分を次のフレームへ回す。巻き戻しやステートの読み込みで APU の出力が途切れても、映像と音声がずれない。

録画は Machine State を変えない。録画の有無で状態のハッシュ（§8.1）は変わらない。

### 8.8.3 書き出しの経路

```go
package mp4rec

type Options struct {
    Scale       int           // 1–3
    FrameRate   float64       // リージョンのフレームレート
    Overscan    video.Overscan
    PictureHeight int
}

func Create(path string, pal *video.Palette, opts Options) (*Writer, error)
func (w *Writer) WriteFrame(f *video.Frame, pcm []int16) error // エミュレーションゴルーチン
func (w *Writer) Close() error
```

| 処理 | 実行する場所 |
|---|---|
| フレームの複製と PCM の受け取り | エミュレーションゴルーチン |
| パレットの適用・拡大・JPEG の圧縮・ファイルへの書き込み | 書き出し用のゴルーチン |
| `moov` の書き込み | `Close` |

`WriteFrame` はフレームを複製して書き出し用のゴルーチンへ渡す。受け渡しの列は 8 フレーム分とし、満ちているときは空くまで待つ。フレームを捨てると動画が途切れるため、エミュレーションを遅らせることを選ぶ。

ファイルは先頭に `ftyp` と `mdat` の見出しを書き、サンプルのデータを追記する。各サンプルの大きさとファイル内の位置だけをメモリに持ち、`Close` で `mdat` の大きさを書き直して、末尾に `moov` を書く。映像のデータをメモリにため込まないため、録画の長さでメモリの使用量が増えない。`mdat` の大きさは 64 ビットで表す。

途中で書き込みに失敗したときは録画を止め、エラーを知らせる。それまでに書いた分は `moov` が無く再生できないため、ファイルを消す。エミュレーションは止めない。失敗のエラーは `Emulator` が覚えて `Status.Video.Error` に載せ、次の `StopRecordingVideo` が返す（返した時点と、次の録画を始めた時点で消える）。GUI は録画中の表示が消えたときにこのエラーを出し、「操作の記録から書き出す」はこのエラーを返して成功と知らせない。headless は終了コード 1 で終える（「11 設定と CLI 設計」§11.5.2）。

`Create` は受け取ったパレットを写して持つ。GUI は設定の保存でパレットをその場で書き換えるため、書き出し用のゴルーチンが同じ表を読み続けると競合する。

### 8.8.4 録画の操作

| 操作 | 内容 |
|---|---|
| 録画の開始 | 保存先を選ぶダイアログを出し、次のフレームから記録を始める。既定の名前は `<ROM 名>-<日時>.mp4`、既定の場所は `paths.videoDir`（「11 設定と CLI 設計」§11.2） |
| 録画の停止 | 書き出しを閉じる。ROM を閉じたとき、別の ROM を開いたとき、アプリケーションを終了したときも閉じる |
| 操作の記録から書き出す | 入力ムービーを選び、動画を書き出す。下で述べる |

録画中はステータスバーに `● 録画中 <分>:<秒>` を出す。時間は記録したフレーム数とフレームレートから求める。

「操作の記録から書き出す」は、表示中のエミュレータとは別の `Emulator` を作り、開いている ROM を読み込み、入力ムービーを速度の上限なしで再生しながら録画する。音声デバイスは開かない。ROM のハッシュがムービーと合わないとき、ROM を開いていないときは書き出さずにエラーを出す。進み具合（フレーム数と総フレーム数）をダイアログに出し、取り消せる。取り消したときは書きかけのファイルを消す。

CLI では `--record-video PATH` で録画する（「11 設定と CLI 設計」§11.5.1）。`--headless --movie PATH --record-video OUT` はムービーの終わりまで実行して動画を書き出す。

### 8.8.5 テスト

| テスト | 確かめること |
|---|---|
| 書き出しの往復 | 書いた MP4 を mp4ff で読み、映像のフレーム数・各フレームの JPEG の大きさ（幅と高さ）・長さ・音声のサンプル数が期待どおりである |
| 決定論 | 同じフレームと PCM から同じバイト列ができる |
| 音声の量 | フレームごとの音声の量が §8.8.2 の式に合い、足りないときに 0 で埋める |
| ムービーからの書き出し | 入力ムービーから書いた動画のフレーム数がムービーの総フレーム数と一致し、書き出しの前後で表示中のエミュレータの状態のハッシュが変わらない |
| 状態への影響 | 録画しながら進めた状態のハッシュが、録画しないときと一致する |
| 途中の書き込みの失敗 | ファイルの大きさの上限（RLIMIT_FSIZE、macOS と Linux）で本物の書き込みの失敗を起こす。録画が止まって `Status.Video.Error` が載り、エミュレーションは続き、`StopRecordingVideo` と書き出しがエラーを返してファイルが残らず、headless が終了コード 1 で終わる |

QuickTime Player での再生は CI で確かめられないため、手元で確かめる。

## 8.9 スロットとファイル

| 操作 | 対象 |
|---|---|
| クイックセーブ | 現在選択中のスロット |
| クイックロード | 同上 |
| スロットの選択 | 0–9 |
| 名前を付けて保存 | 任意のパス |

スロットのファイル名は `<rom-hash>/<slot>.state` とする。保存先は「11 設定と CLI 設計」§11.2 に定める。書き出しは一時ファイルへ書いて `rename` する。

スロット一覧の表示に、保存時刻・累積フレーム数・スクリーンショットを用いる。
